# Myne Markdown Dialect — v0.1

> Normative specification of the markdown dialect Myne v0.1 reads and writes. Companion to [`protocol.md`](protocol.md) (cryptographic format) and [`wikilink.md`](wikilink.md) (wikilink-specific syntax). This document binds every Myne client.

## 1. Scope

This specification defines:

- which markdown syntax Myne v0.1 **parses** as structured AST nodes,
- which syntax Myne v0.1 **renders** with editor decorations,
- which syntax Myne v0.1 **emits** when authoring new content,
- the file extension and frontmatter conventions on disk after decryption,
- round-trip stability guarantees with imported Obsidian vaults.

This document does **not** define:

- The `[[wikilink]]` family — see [`wikilink.md`](wikilink.md).
- The encrypted `.myn` blob format — see [`protocol.md`](protocol.md) §9.2.
- Editor implementation details (CodeMirror 6 extension wiring, decoration kinds, slash command shape) — see `agent-tooling/features/editor-mvp/rfc.md` and the editor-mvp PRDs.

## 2. Dialect identity

Myne v0.1 adopts **GFM (GitHub-Flavored Markdown) plus a footnote extension plus a wikilink extension plus YAML frontmatter recognition**. Internally referred to as **D1**. The dialect is:

- **The smallest pin that covers Myne v0.1's editor decoration commitments** (tables, task lists, footnotes, wikilinks, frontmatter).
- **Byte-stable round-trip** with notes imported from Obsidian vaults: a note written by Obsidian, imported into Myne, and never edited inside Myne, must serialize back to the same bytes when exported. (Obsidian conventions Myne does not natively render — `> [!callout]` syntax in v0.1, `^block-id` markers — are still preserved at the byte level. See §6.)
- **Forward-incompatible by design** with a later major version. A later version will pin its own dialect. Cross-major migration is out of scope per `protocol.md` §10.1; the same applies here.

## 3. Recognized syntax categories

The parser recognizes the union of CommonMark + GFM extensions + footnote extension + wikilink extension + YAML frontmatter. Concretely:

### 3.1 Block elements (CommonMark base)

- ATX headings `# H1` … `###### H6` (only ATX is canonical for new writes; Setext `===` / `---` underline form is recognized on parse for round-trip and, since MYND-146, **rendered** with a cursor-aware decoration — the title takes H1/H2 typography and the underline line hides off-cursor — but is still **never emitted**. Rendering ≠ emitting: the bytes are preserved per §6 C1 and a new heading still writes the ATX form.)
- Paragraphs (text separated by blank lines)
- Indented code blocks (4-space indent) — recognized for round-trip but **never emitted**; new code blocks always use fenced form
- Fenced code blocks (`` ``` `` or `~~~`) with optional language label (` ```ts `)
- Block quotes (`> ` prefix)
- Bullet lists (`- ` / `* ` / `+ `; canonical emit form for new writes is `- `). Since MYND-208 **rendered** with a cursor-aware decoration: the marker becomes a muted bullet glyph (`•` top level, `◦` nested) with a hanging indent off-cursor, the raw marker revealed on-cursor. The alternate markers (`*`/`+`) and the source nesting whitespace are preserved; **never emitted**, bytes preserved per §6 C1. (Task-list items `- [ ]` keep their checkbox decoration, §3.3, until a caret enters that run or a selection overlaps it, at which point the whole `- [ ]` lifts to source like every other construct on this list.)
- Ordered lists (`1. ` / `1) `; canonical emit form is `1. `) — since MYND-208 the `n.` marker is **rendered** muted (cursor-aware) off-cursor, revealed on-cursor; non-canonical numbering and `1)` form preserved, never emitted.
- Horizontal rules (`---` / `***` / `___`; canonical emit form is `---`)
- HTML blocks (raw HTML — recognized at parse). Since MYND-209 a **curated safe subset** is **rendered**: block `<p>` and `<details>`/`<summary>` (the latter natively interactive, with WebView-only ephemeral open state) are sanitized through DOMPurify under an ultra-tight allowlist and rendered as block widgets, cursor-aware (raw HTML revealed on-cursor; bytes preserved per §6 C1). Everything off the allowlist (incl. `<script>`/`<iframe>`/`<img>`) is NOT rendered and stays plain text. See §8.
- Definition lists (Pandoc-style `Term` then `: Definition`) — **recognized and rendered** since MYND-152 (scope reversal, `decisions.md` 2026-05-30; previously §7 out-of-scope). The pinned v0.1 subset is **tight only**: a single term line immediately followed (no blank line between) by one or more definition lines, each `:` + a space + the definition text (a bare `:` is an empty definition); multiple consecutive `:` lines attach as multiple definitions of that term. **Not** in the subset (preserved byte-stably as ordinary paragraphs, not parsed as definition lists): the blank-line-separated "loose" form, lazy continuation lines (a definition wrapping onto a non-`:` line), and multiple terms sharing one definition block. Rendered with a cursor-aware decoration (term styled, definitions indented, leading `:` hidden off-cursor); **never emitted** — no authoring affordance produces a definition list, and bytes are preserved per §6 C1. The custom parser node is informative in §8.
- **Block / multi-line comment** (Myne extension, MYND-315): a line that **starts** (after ≤3 spaces) with `%%` opens a block comment that runs until the next `%%`, which may close on the same line (`%% note %%`) or on a later line (multi-line). The comment is an **editor-only note-to-self**: it is **rendered dimmed** in the editor (a de-emphasis decoration mutes the whole span — it stays VISIBLE as a comment, never hidden; Myne's editor is the live surface, so "hidden in render" means hidden in the **output/export**, not in the editor) and is **stripped from lossy projections** (HTML / PDF / stripped-TXT) and excluded from document statistics via the §6 transform. **Termination is required**: a block-opening `%%` with **no** closing `%%` anywhere after it is **inert** — it stays an ordinary paragraph and hides nothing (the normative unterminated-comment rule, §6; a deliberate divergence from Obsidian's unterminated-`%%`-swallows-to-EOF behavior, chosen to avoid a "half my note vanished" surprise). **Never emitted** — no authoring affordance produces a `%%` comment, and the source bytes are preserved per §6 C1 (recognize-and-render-only; the `.md` export keeps `%%` verbatim). The companion inline form is §3.2; the exclusion zones are §3.7.5; the custom parser node is informative in §8.

### 3.2 Inline elements (CommonMark base)

- Emphasis: `*italic*`, `_italic_`, `**bold**`, `__bold__` (canonical emit forms: `*italic*` and `**bold**` — see §5)
- Inline code: `` `code` ``
- Inline links: `[text](url)` and `[text](url "title")`
- Reference links: `[text][ref]` (and collapsed `[text][]` / shortcut `[ref]`) + `[ref]: url` — recognized for round-trip and, since MYND-148, **rendered** with a cursor-aware decoration: a resolved usage shows its visible text as a link and the resolved `[ref]: url` definition line hides off-cursor; a dangling reference (no matching definition) stays plain text. Still **never emitted** — new links use inline form, bytes preserved per §6 C1. A `[ref]: url` definition is matched to its uses by CommonMark reference rules (case-folded, internal whitespace collapsed). See also the shared **link reference definition** collector consumed by reference images (§7, MYND-149/MYND-164).
- Autolinks: `<https://example.com>` (CommonMark form) and bare `https://example.com` (GFM extension)
- Hard line breaks: trailing two spaces or `\` at line end: since MYND-208 the trailing marker is **hidden** off-cursor (render-only, no `↵` glyph, per PRODUCT.md), revealed on-cursor; bytes preserved per §6 C1. **Never hidden on a list item** (`decisions.md` 2026-09-05): a list row's whole label sits on one line, so a marker that is in the file and not on screen makes live view and the source disagree about its length. Prose is unchanged.
- Backslash escapes (`\*`, `` \` ``, `\\`, `\#`, …) — since MYND-208 the leading `\` is **hidden** off-cursor so the escaped character reads cleanly (e.g. `\*` renders `*`), revealed on-cursor; render-only, bytes preserved per §6 C1.
- Raw inline HTML (recognized; rendered as plain text)
- **Highlight** (Myne inline extension, MYND-156): `==text==` — **rendered** with a muted `--highlight` wash (cursor-aware: `==` markers hidden off-cursor, revealed on-cursor). The one hand-rolled inline config (the bundle has no highlight). Canonical emit `==text==` via the highlight toolbar button (§5). **Multi-color** highlight (decisions.md 2026-06-15) does NOT extend the `==…==` syntax (which carries no color and stays default-yellow); a non-yellow highlight is authored as the portable embedded form `<mark class="hl-<color>">text</mark>` (the toolbar's color swatches emit it), rendered via the §8 embedded-HTML path with the wash keyed off the `hl-*` class. The class vocabulary is closed and enforced at the sanitizer (§8), which is the single source of truth for its members.
- **Subscript / superscript** (MYND-156): `~x~` / `^x^` — **rendered** (`.cm-sub` / `.cm-sup`, cursor-aware), reusing the `@lezer/markdown` Subscript/Superscript configs. Single-run, space-free (Pandoc-style); disjoint from GFM strikethrough `~~…~~` and footnote `[^id]`. Recognize-and-render-only — **never emitted**, bytes preserved per §6 C1.
- **Emoji shortcodes** (MYND-156): `:name:` (via the `@lezer/markdown` Emoji config) — a mapped name **renders** as the unicode glyph (lazy-loaded name→glyph map); an unmapped `:name:` stays literal text. The `:` autocomplete inserts the unicode glyph directly (so authoring emits a plain glyph, not the `:shortcode:`). The `:name:` source is render-only — never rewritten in the buffer (§6 C1).
- **Math** (MYND-48): inline `$…$` (a custom `InlineMath` Lezer node) and block `$$…$$` (a decoration, not a node) — **rendered** via lazy-loaded KaTeX, cursor-aware (raw LaTeX revealed on-cursor; invalid LaTeX shows source + a subtle hint, never KaTeX's red node). The inline **`$`-disambiguation** (Pandoc/Obsidian): the opening `$` must not be followed by whitespace or a digit (`$5` is currency), the closing `$` must not be preceded by whitespace, `$$` is block, and a `$…$` run does not cross a line break — so tests.md's `Currency: $ € £ …` stays text. Math does not parse inside code spans/fences. InlineMath is a leaf node, so `#tags`/emphasis do not parse inside it (§3.7.5). Render-only, never emitted; bytes preserved (§6 C1).
- **Comment** (Myne extension, MYND-315): `%%text%%` — an **editor-only note-to-self**. The `%%`-delimited span is **rendered dimmed** in the editor (a de-emphasis decoration mutes the span — it stays VISIBLE as a comment, never hidden); it is **stripped from lossy projections** (HTML / PDF / stripped-TXT) and excluded from document statistics via the §6 transform. **Termination is required**: a `%%` with no closing `%%` is **inert** — it stays literal text and hides nothing (the unterminated-comment rule, §6). The companion block / multi-line form is §3.1. One of the two hand-rolled inline configs (with highlight; the bundle has no comment construct). Recognize-and-render-only — **never emitted** (no slash/toolbar affordance, like sub/sup), and the source bytes are preserved per §6 C1 (the `.md` export keeps `%%` verbatim). Disjoint from `==highlight==` and from `#tags` (a `%` is in the inline-tag deny-list, §3.7.2). Does not parse inside code spans/fences, wikilinks, or math leaves (§3.7.5).

### 3.3 GFM extensions

- Tables: pipe-delimited with `|---|` alignment row. Per-column alignment via `:---`, `---:`, `:---:`.
- Task lists: `- [ ]` / `- [x]` (lowercase `x` is canonical emit; uppercase `X` recognized for round-trip)
- Strikethrough: `~~text~~`
- Autolinked URLs (no angle brackets required)

### 3.4 Footnote extension

- Inline footnote reference: `[^N]` (where `N` is an identifier — typically an integer, but any non-whitespace string is permitted)
- Footnote definition: `[^N]: definition text` (typically grouped at end of document; position is not normative)

### 3.5 Wikilink extension

The full grammar lives in [`wikilink.md`](wikilink.md). At a glance, the parser recognizes:

- `[[Note]]` — title-only link
- `[[Note|Display]]` — title with display alias
- `[[Note#Heading]]` — heading anchor
- `[[Note^block-id]]` — block reference (recognized for round-trip; not emitted)
- `[[vault/relative/path.md|Display]]` — vault-relative path with alias (Myne-native authoring form per §4 of [`wikilink.md`](wikilink.md))
- `[[Projects/]]` — **folder-target wikilink** (trailing slash): resolves to that folder's index note (the in-folder note carrying `folder_index: true`, §3.6.1) — see [`wikilink.md`](wikilink.md) §2 form 11 / §5.5
- `![[Note]]` and `![[image.png]]` — embed forms (rendered as labeled chips; no transclusion engine in v0.1)

### 3.6 YAML frontmatter

A document **may** begin with a YAML metadata block delimited by `---` lines:

```
---
title: Some Title
tags: [foo, bar]
---

# Note body starts here
```

The frontmatter block must:
- begin on line 1 (no preceding blank lines or content),
- open with a line consisting of exactly `---`,
- close with a line consisting of exactly `---`,
- contain valid YAML 1.2 between the delimiters.

Frontmatter is recognized as a structured block and rendered as a code block in the v0.1 baseline editor. The Properties **editing UI** (editable key-value grid) is deferred to a post-v0.1 release. Unknown frontmatter fields are preserved on write — Myne never strips fields it does not recognize.

**Derived property-index read parse (MYND-271, Saved Views).** Separately from the editor's single-pass recognizer (§8) and from the deferred Properties *editing* UI, Myne runs a **read-only, derived** parse of the YAML frontmatter *body* to populate the typed property index that the Saved Views feature queries (the `vault.indices` / `MYI1` projection, [`protocol.md`](protocol.md) §9.8). This parse is strictly **non-mutating**: it never rewrites note bytes (the §6 C1 round-trip guarantee and the unknown-field-preservation rule above are unchanged), it never writes back to the note, and it does **not** promote an editable Properties UI. It reads every arbitrary `key → value` pair and assigns each value exactly one Myne type — `string` / `number` / `date` / `list` / `checkbox` — per the value-typing / coercion ruleset in §3.6.4. The Myne-managed canonical fields keep their value-strict semantics (`trashed:` / `archived:` / `deleted:` RFC 3339, `template:` / `folder_index:` / `conflict:` canonical-`true`, §3.6.1) — the derived parse *observes* those values, it does not relax them. The resulting index is a derived, rebuildable cache, never a source of truth: the `.myn` files remain authoritative and a user who walks away keeps plain markdown (`vision.md` portability commitment). See [`decisions.md`](../decisions.md) 2026-06-14 "Saved Views property-index: pull the deferred §3.6/§8 YAML-body parse forward" and "Saved Views is a read-only derived projection over plain markdown, not a database".

#### 3.6.1 Myne-managed canonical frontmatter fields

Myne writes thirteen canonical fields to YAML frontmatter from the host, all via the dialect surgery module, **with one exception added 2026-08-16**: an approved agent edit (myne-md/myne#529) rewrites a note body wholesale through the ordinary `note_save`/`MY01` path, so it can emit any field in this table, including `trashed:`. It is not a second surgery implementation and does not bypass a check the surgery module performs; it is a body rewrite the user approved in a diff, which is the same class as a hand edit. The fields that get extra treatment are the five `isLiveNote` reads — `trashed:`, `deleted:`, `archived:`, `template:`, `conflict:` — because writing any of them takes a note out of the working set and is indistinguishable from any other edit at the diff layer: the host refuses such an edit inside a bulk approval, so it always carries its own act (`design-notes.md` 2026-08-16, entry 0515, which is this carve-out's authority). This clause named `trashed:` alone until myne-md/myne#531 review round seven; trash was never the class, only its most familiar member, and `deleted:` is the worse one since it hides a note from Trash and Archive as well as from the sidebar. The `<filename>` alias may not contain `]`, character-for-character the alias grammar the shared form-C scanner uses, so a cover and the same embed in a note body parse identically. That restriction is inherited from form C rather than introduced here, and it is one-sided: the emitter interpolates a filename verbatim, so an attachment whose name contains `]` can be written as a cover and will then read back as no cover at all. A **local-only** (un-synced) delete stays the hard cryptographic-erase `unlink` — the tombstone is the under-sync reroute only. **Absent** = live. Tombstoned notes are excluded client-side from sidebar / folder-tree / search exactly like `trashed:`. The tombstone is GC'd at the tombstone horizon (`sync-protocol.md` §11). Tombstone-state lives inside the AEAD blob — no on-disk-layout change (`protocol.md` §9.1 stays flat) (MYND-426) | `src/dialect/surgery.ts::patchDeletedField` | Delete-under-sync reroute (`src/notes/deleteNote.ts::tombstoneNote` / `deleteNoteRouted`) only — never body autosave |
| `conflict` | **value-strict boolean** — only the canonical `true` form marks the note a sync conflict copy; any other value (`1`, `yes`, `True`, quoted `"true"`) or absence = ordinary note (mirroring `template:` / `folder_index:`) | **Phase 2 keep-both conflict copy (SYNC-11).** When the same note is edited concurrently on two devices, the engine materializes the remote revision as a **new** `.myn` carrying `conflict: true` + `conflict_of:` so **both survive** — never a silent overwrite. A conflict copy is **excluded** from the live sidebar, folder-tree, full-text search, and the backlink resolver (`src/notes/sidebarState.tsx` `liveCache` / `resolverCache`) — surfaced **only** in the Conflicts view, reached via a count badge. **Absent** = ordinary note. "Keep as separate" clears the markers (the copy re-enters the live set); "Discard" deletes it. Conflict-state lives inside the AEAD blob — no on-disk-layout change (MYND-427) | `src/notes/conflictCopy.ts` (generic `patchFrontmatterField`, **not** a dedicated `patch*Field`) | Engine keep-both resolution + the Conflicts view keep/discard actions — never body autosave |
| `conflict_of` | YAML string — the **`note_uuid` of the original** the conflict copy forked from | Pairs with `conflict: true`: names the note this copy diverged from so the Conflicts view groups copies by original (`conflictRecordsByOriginal`). Meaningful only on a `conflict: true` note; absent on ordinary notes; cleared together with `conflict:` on resolve. Lives inside the AEAD blob — no on-disk-layout change (MYND-427) | `src/notes/conflictCopy.ts` (generic `patchFrontmatterField`) | Set when the engine materializes a conflict copy; cleared on resolve — never body autosave |

Mechanics — shared across the eight dedicated-surgery fields (the seven above plus `deleted:`; the conflict pair `conflict:` / `conflict_of:` instead rides the generic `patchFrontmatterField`, so its value is not value-strict-collapsed the same way):

- Fields are **unprefixed** (no `myne_` namespace). Obsidian Templater/Linter and the wider markdown ecosystem use unprefixed `updated:` and `title:` for these purposes; Myne aligns with the convention so a user who walks away from Myne sees fields every other editor recognizes (`PRODUCT.md` design principle 5 — plain-markdown portability).
- Each writer follows the same 3-state surgery matrix: state A (no FM block) → prepend `---\n<key>: <value>\n---\n\n` (canonical Obsidian-Templater shape with one trailing blank line); state B (FM exists, key absent) → insert `<key>: <value>\n` at the end of the FM block (just before the closing `---`); state C (FM exists, key present) → replace the value byte-by-byte, preserving trailing comments, preserving quote style (`unquoted`, `'single'`, `"double"`), and collapsing YAML block-scalar form (`<key>: |\n  …\n`) to single-line canonical form. The state-C collapse is justified by the fields being Myne-managed — a user who wants multi-line content in these fields uses a different field name.
- **`patchFolderField`, `patchTrashedField`, `patchTemplateField`, `patchFolderIndexField`, `patchArchivedField`, and `patchDeletedField` extend the matrix with a 4th operation — state D (delete-field)** — for move-to-root (folder), restore (trashed), convert-template-to-note (template), undesignate-as-folder-note (folder_index), unarchive (archived), and clear-tombstone (deleted): it removes only the target line (key + value + that line's trailing comment + newline); if ≥1 residual key or comment remains, the FM block is kept; if the block becomes truly empty (no key, no comment), the whole block is removed so the output is byte-identical to an FM-less note (symmetric with `buildInitialPlaintext(null) === ""`). A lone user comment keeps the block — Myne removes its own field and the void it left, never user structure.
- **The thirteen managed fields compose on one blob without clobbering** (per the §3.6 unknown-field-preservation rule): each writer touches only its own line, so a single note can carry any combination — e.g. `template: true` + `trashed: <ts>` simultaneously (a deleted template, restorable from Trash, re-entering the template set on restore), or `folder: Projects/` + `folder_index: true` (the visible index note of the Projects folder), or `conflict: true` + `conflict_of: <uuid>` (a keep-both copy). Setting or deleting one managed field preserves every other managed field, user-authored field, and comment byte-for-byte. The one **semantic** (not byte-level) exclusion is `archived:` ⊥ `trashed:`: the surgery composes them freely, but the archive/trash **action layer** clears one when setting the other so a note is never simultaneously archived and trashed (MYND-331).
- **A Properties-widget row for a Myne-managed field renders READ-ONLY when the app's own write owns that row's value and refusing the edit loses the user nothing** (myne-md/myne#872; [`decisions.md`](../decisions.md) 2026-10-15 "The Properties widget renders a managed frontmatter row read-only"). Ownership is the field's own read (`readFolderIndexFromFmBody`, `readTemplateFromFmBody`, `readConflictFromFmBody`, `readTrashedFromFmBody`, `readArchivedFromFmBody`, `readDeletedFromFmBody`, `readDoneFromFmBody`, `readUpdatedFromFmBody`, `readFolderFromFmBody`), so the widget's answer cannot drift from the app's; the second half of the condition is what the per-field exemptions below discharge. The row is still **rendered**, because the line is in the file and the widget replaces the whole frontmatter block, so a hidden field would be a byte the user can neither see nor reach; it carries the value bytes verbatim and no control beside them. The question is asked **per row**, not per key: the readers stop at the first matching line while the widget draws one row per line, so a note carrying a managed key twice would otherwise render the junk line read-only and leave the canonical line's row writable, or the reverse, depending on which came first. That applies to the **write** direction too: a row's value edit and key rename are committed against the byte range that row was rendered from, never against a first-match lookup of its key, so an editable junk row cannot write the canonical line beside it. A managed key whose value its reader does **not** recognise is not state the app acts on, so it stays an ordinary editable row, exactly like a dangling `cover:` (§3.6.1), which keeps a hand-edited or imported malformed value fixable in the interface. Six qualifications belong to the rule. **Only a scalar row** can be affected, since no field here has a sequence value. **The spelling must be canonical**: every reader is anchored and case-sensitive, so `Folder_Index:` is the user's line and stays editable, even though the importer's managed-field reject list is case-insensitive for its own question. **`folder:` additionally requires a value the app can read**: its line reader returns any non-empty scalar, while the app keeps the field only when its own YAML read resolves the value to a string, so a `folder: 123` is the user's line rather than state. **`done:` is read-only only on a note whose `kind: task` marker makes it clearable**, because the completion action refuses a non-task note before it touches the field and un-completion is the only path that deletes it. And **two fields are exempt**, each for its own reason: `conflict_of:` has no value-strict reader (it accepts any non-empty scalar), and `kind:` is the one managed field no action can CLEAR, so a read-only row would strand a marker the panel and the app alike could not remove. Both exemptions are stated rather than implied, and both are rows the widget still writes. `updated:` is inside the rule for the adjacent reason its own prose gives: autosave owns it and a hand edit is overwritten on the next save, so the row refuses an edit it cannot keep. `cover:` keeps its landed conditional rule, and `title:` stays promoted to the note-title field. A value edit on a row no reader recognises can still author a canonical value by hand, which is the same route the dangling-`cover:` rule leaves open on purpose.
- Other frontmatter fields (`tags:`, user-authored fields) are preserved per the §3.6 "Unknown frontmatter fields are preserved on write" rule.
- `created_at` is **not** stored in frontmatter — it is derived from the UUIDv7 filename's millisecond time component per [`protocol.md`](protocol.md) §9.1 (already public-accepted leak; no new commitment violation, no frontmatter write needed).
- The set of Myne-managed canonical frontmatter fields is forward-incompatible-by-design with a later major version: a later version may rename, drop, or supersede `updated:` / `title:` / `folder:` / `trashed:` / `template:` / `folder_index:` / `kind:` / `archived:` / `done:` / `cover:` / `deleted:` / `conflict:` / `conflict_of:` per its own dialect specification.

- **`updated`** is owned by autosave: a user who manually sets `updated:` to a custom value sees it overwritten on the next save — autosave is Myne's responsibility. Users who want a manually-managed timestamp use a different field name (e.g., `last_reviewed:`).
- **`title`** is written by note CREATE (`src/notes/createNote.ts::initialNotePlaintext` → `patchTitleField`, an empty `title: ""` on every new note so it has a field to be named in, `decisions.md` 2026-09-05; the value is a quoted empty scalar, and a reader normalises it back to "no title"), by the rename action (`src/notes/renameNote.ts` → `patchTitleField`, the same 3-state matrix as `updated:`) and, at import time, by the **Obsidian importer** (filename → `title:` when the imported file has none: §6 sanctioned transform, [`decisions.md`](../decisions.md) 2026-06-09); body autosave does NOT write `title:`. The body's first `# H1` line is **not** a title source or a title write target: a note with no FM `title:` reads as "Untitled" until named or imported, and the read path (`note_titles_batch` / `loadNoteBatch`) derives the title from `title:` only. `patchFirstH1Line` remains a structural-transform primitive in `src/dialect/surgery.ts` (e.g. for the editor's heading-cycle command) but is no longer invoked by rename. A note with no `folder:` is **root / unfiled**. The value is a virtual path. The on-disk layout never reflects it (`protocol.md` §9.1 stays flat `notes/<uuid>.myn`), so the folder structure travels inside the encrypted blob (AS3) and survives a plaintext export. Deliberately-created folders that hold no note are persisted separately in `vault.prefs` (`protocol.md` §9.5.2 `deliberate_folders`), not in any note's frontmatter. See [`decisions.md`](../decisions.md) 2026-05-29 "Native folder hierarchy" (MYND-144).
- **`trashed`** is owned by the trash + restore actions only — body autosave does NOT write `trashed:`. The trash action (`src/notes/trashNote.ts::trashNote`) writes `trashed: <now>` (RFC 3339 UTC) via `patchTrashedField` then re-encrypts through the existing `note_update` IPC; the restore action (`restoreNote`) **deletes** the field (state D). There is no dedicated `note_trash`/`note_restore` backend command — trash/restore are TS orchestrators over `note_update`, exactly like `folder:` is rewritten by `moveNote` (`decisions.md` 2026-06-03). Unlike the other three, `trashed:` is **value-strict**: Myne treats the note as trashed only when the value parses as a valid RFC 3339 timestamp — a user's own `trashed: true` / non-timestamp value leaves the note live. The field is unprefixed for canonical-field consistency, but unlike `updated:` / `title:` it carries **no** Obsidian ecosystem convention (Obsidian uses OS-level trash, not a frontmatter flag); value-strictness plus the MYND-51 importer's flag-don't-rewrite rule contain the field-name collision footgun. A Myne-native note that a user has manually given a valid-RFC 3339 `trashed:` is the residual accepted risk (it would be filed to trash). Trashed notes are excluded client-side from sidebar enumeration, folder-tree reconstruction, and full-text search; only the Trash panel reads them. See [`decisions.md`](../decisions.md) 2026-05-07 "Note delete UX" (the deferral this implements) + the v0.2 vault-internal soft-trash entry (MYND-133).

The convert-to-template action (`src/notes/templates.ts::convertNoteToTemplate`) writes `template: true` via `patchTemplateField` then re-encrypts through the existing `note_update` IPC; convert-back (`convertTemplateToNote`) **deletes** the field (state D); creating a template (`createTemplate`) mints a new note already carrying the flag via the existing `note_create` IPC. Like `trashed:`, `template:` is **value-strict**: Myne treats the note as a template only when the value is the canonical, unquoted boolean `true` — a user's own `template: 1` / `template: "true"` / `template: yes` leaves the note an ordinary note. The field is unprefixed for canonical-field consistency, but carries **no** Obsidian ecosystem convention (Obsidian designates a template by *folder*, not a frontmatter flag); value-strictness contains the field-name collision footgun. A template is the **inverse-visibility twin** of trash: a `template:`-flagged note is excluded client-side from sidebar enumeration, folder-tree reconstruction, and full-text search (the same exclusion machinery as `trashed:`), but — unlike a trashed note — is *surfaced* in the template picker and management UI. This is a documentation contract only: no `protocol.md` §9.1/§9.2 change, no new magic byte, no AAD/version bump — the marker rides the existing `.myn` envelope. There is no dedicated backend command — designate/undesignate are TS orchestrators over `note_update`, exactly like `template:` (`decisions.md` 2026-06-17). Like `template:`, `folder_index:` is **value-strict**: Myne treats the note as its folder's index only when the value is the canonical, unquoted boolean `true` — a user's own `folder_index: 1` / `folder_index: "true"` / `folder_index: yes` leaves the note an ordinary note. This is a documentation contract only: no `protocol.md` §9.1/§9.2 change, no new magic byte, no AAD/version bump — the marker rides the existing `.myn` envelope. This is a documentation contract only: no `protocol.md` §9.1/§9.2 change, no new magic byte, no AAD/version bump — the marker rides the existing `.myn` envelope. See [`decisions.md`](../decisions.md) 2026-06-17 "Archive: seventh canonical frontmatter field" (MYND-331).

#### 3.6.2 Folder path grammar

A `folder:` value is a slash-delimited path of **segments**. A folder segment and a note title are the **same structural object** — both are segments of the virtual wikilink target `<folder>/<title>.md` (see [`wikilink.md`](wikilink.md)) — so one segment grammar governs both, enforced by a single `src/dialect/folderPath.ts::isLegalSegment` predicate reused at folder-create, note-create, note-rename, and import-scan.

**Forbidden in a segment** (Myne-authored input): `/` and `\` (path delimiters — a `/` inside a title would forge a folder boundary); `|`, `#`, `^` (wikilink alias / heading-anchor / block-ref delimiters per [`wikilink.md`](wikilink.md) §2.1); `]]` and bare `[` / `]` (the unescapable wikilink terminator per §10); any C0 control character (U+0000–U+001F) or DEL (U+007F); leading or trailing whitespace; a trailing `.` (Windows trailing-dot-strip footgun); a whole-segment `.` or `..` (traversal); and the empty segment (`//`). Everything else is permitted — interior spaces, most punctuation, Unicode letters, and emoji — preserving Obsidian's permissive folder/title character set. Rich or "loud" display text belongs in the wikilink **alias** (`[[…|Display]]`), not in the title or folder segment, which stay resolution-safe.

**Enforcement is provenance-split** (generalizing §6 C1 + [`wikilink.md`](wikilink.md) §10 from the `]]`-only rule to the full grammar): Myne-authored input is **rejected at the UI** before it reaches the surgery layer, via the single `folderPath.ts::isLegalSegment` + `isLegalPathLength` gate (wrapped by `validateFolderNameInput` for typed input); imported content (Obsidian vaults) is **preserved byte-for-byte** (C1) but **flagged with a rename prompt** — never silently rewritten. The Myne-authored gate is live at the folder **create** and folder **rename** inputs (`useFolderManagement`, MYND-144). The same predicate is the intended gate for note-**title** create/rename and is the contract the MYND-51 importer's rename-**flag** path checks against — those consumers land with their own features. A folder **move** (drag-drop) introduces no new segment — it relocates a note under an already-gated folder path — so it carries no separate grammar check.

**Identity** is case-**insensitive**: two segments are the same folder when their **Unicode case-fold + NFC** forms match (`Projects/` ≡ `projects/`), reusing the §3.7.8 inline-tag identity rule. Raw bytes are preserved on disk for display and walk-away; folding is a comparison-key operation only (`folderPath.ts::foldSegment`). Case-sensitivity was rejected as a walk-away footgun — case-only-distinct folders collide when exported to a case-insensitive filesystem (macOS / Windows).

**Canonical forms.** The vault **root** is the **absence** of the `folder:` field (`folder: ""` is read as root and normalized to absent on write; `folder: "/"` is rejected). The canonical storage form carries a **trailing slash** (`Projects/`, `Projects/Myne/`); reads tolerate a missing trailing slash and duplicate / leading slashes (collapsed on normalization), but emission is always trailing-slash. The `.md` extension discriminates a root path-form wikilink target (`Foo.md`) from a title-only target (`Foo`); exactly one trailing `.md` is appended on derive and stripped on parse, so a note literally titled `Foo.md` round-trips (`Foo.md` → `Foo.md.md` → `Foo.md`).

**Caps.** A segment is ≤ 255 bytes UTF-8 (`NAME_MAX` on ext4 / APFS / NTFS); a total vault-relative path (folder + title + `.md`) is ≤ 1024 bytes (`PATH_MAX` on macOS); depth is bounded implicitly by path length, not separately capped (parallel to §3.7.4's unbounded tag nesting). Overflow is a Part-1 enforcement event (Myne-authored reject, import flag). Windows legacy `MAX_PATH` (260) and reserved device names (`CON`, `NUL`, `COM1`, …) are handled as a **documented walk-away caveat + import warning**, not part of the core grammar — keeping platform quirks out of the cross-client byte contract.

**Importer coordination (MYND-51).** The Obsidian importer writes folder structure to this same canonical `folder:` field; the field name and the trailing-slash form defined here are the contract the importer consumes / produces. (Whether the importer also persists *empty* source directories to `deliberate_folders` is an importer-side fidelity decision, out of scope here.)

#### 3.6.3 Importer ignore-set

The Obsidian importer (MYND-54) decides which directory entries become notes by **two rules**, applied to each entry the import walk encounters, in order:

1. **Dot-prefix rule (wins).** Any entry whose name begins with `.` — file *or* directory, at any depth — is skipped and surfaced only as a low-profile transparency count ("N config/hidden items ignored", shown when non-zero). The single rule subsumes `.obsidian/`, `.git/`, `.trash/`, `.DS_Store`, `.obsidian.vimrc`, and every other dotfile; there is no per-name ignore list.
2. **Extension rule** (non-dot entries only). Exactly one extension is imported as a note: `.md`. `.markdown` and `.mdx` are **not** importable (`.mdx` is JSX, not plain markdown — importing it would risk the parser and the §6 C1 round-trip contract); both fall to *non-markdown skipped*. `.canvas` files are skipped and reported on their **own** dedicated summary line — Obsidian Canvas is a whiteboard, a standing `vision.md` anti-feature, so skip-and-report upholds it rather than importing it. `.excalidraw` and `.excalidraw.md` files are likewise skipped onto their own dedicated summary line, and that arm is evaluated **before** the plain `.md` arm: an Obsidian Excalidraw drawing is a markdown *wrapper* around the plugin's serialized scene, so it ends in `.md` and would otherwise import as prose (MYND-633). Skipped, not converted — a converter has to handle both of Obsidian's scene encodings plus its embedded-image references, which is its own work. Every other non-`.md` extension is counted under *non-markdown skipped*. Extension matching is case-insensitive.

Each skipped class is counted in **its own** field, and the summary renders the dedicated lines separately from the hidden/config transparency count. A class that has no counting arm is not merely unreported: its entries land in whichever bucket the fallback names, so a dedicated line reads `0` while an unrelated count is silently inflated (myne-md/myne#223).

**Latent edge.** Because the dot-prefix rule is evaluated first, a note literally named `.foo.md` is treated as hidden and silently dropped. This is accepted as a low-probability edge and is recorded in the MYND-90 round-trip-fixture edge-case list.

Skipping an entry writes nothing, so the importer's C1 sanctioned-diff allowlist (§6) is unchanged by this rule. No glossary, protocol, or cryptographically load-bearing identifier is affected.

#### 3.6.4 Property value typing (coercion ruleset)

The derived property-index read-parse (§3.6) assigns **every** arbitrary frontmatter key's value exactly **one** of five Myne property types — `string` / `number` / `date` / `list` / `checkbox`. This subsection is the **normative, cross-client-stable** coercion ruleset: two independent Myne clients reading the same note MUST type every value identically. property-index is the **single type authority** for the Saved Views feature — the query engine, view model, render layer, and `.base` importer **consume** this typing and **never redefine** it. Pinned by the `property-coercion` golden vectors in the `myne-test-vectors` companion.

**Scope: frontmatter values *and* inline task-field values.** The type authority is not frontmatter-only. The inline task-field values of §3.8.3 are typed against the same authority — concretely, the `YYYY-MM-DD` full-date shape is defined here and consumed there, never redeclared. Without this scope statement, typing an inline `[due:: …]` would bring a second, undocumented type authority into existence, which is exactly the drift this subsection exists to prevent. The consume-never-redefine rule therefore binds the task-field parser, the task index, the task query keywords, and the chip renderer just as it binds the Saved Views consumers.

Two differences follow from the domains rather than from the rules, and are stated so they are not mistaken for drift: task fields admit a **wall-clock date-time that carries no offset**, which §3.6.4's date-time (which *requires* an offset) does not describe, and task fields **refuse** a value that does not type instead of falling back to `string`. Neither alters any coercion rule below.

The ruleset is **extraction-and-typing only** — it defines no evaluatable expression, no computed/derived field, and no formula (mirroring the closed-registry discipline of `protocol/src/template.rs`). Querying over the typed values is the query-engine sub-feature's concern, not this layer's.

**Step 1 — YAML 1.2 resolution.** The frontmatter body is parsed as YAML 1.2 (per §3.6). Each value resolves to a YAML node whose **core-schema tag** (`tag:yaml.org,2002:{seq,map,bool,int,float,null,str}`) is the basis for typing. The **YAML 1.2 core schema** (spec §10.2.1) is normative — deliberately *not* the legacy YAML 1.1 schema — so the "Norway problem" (`no` / `off` / `yes` resolving to booleans) does not occur: a core boolean is exactly one of `true | True | TRUE | false | False | FALSE`. (The reference implementation is `js-yaml` under `CORE_SCHEMA`; a conformant port uses any YAML 1.2 core resolver.)

**Step 2 — node-kind dispatch.**

| YAML node | Myne type |
|---|---|
| sequence (flow `[a, b]` or block `- a`) | **`list`** |
| mapping (nested object) | **`string`** (best-effort; see below) |
| scalar | per **Step 3** |

A nested **mapping** value is rare in note frontmatter and is **not** a structured Myne type in v0.1; it coerces to `string` (its flow-style serialization). Documented edge — querying nested objects is out of scope.

**Step 3 — scalar typing.** A scalar node is typed by the **first** matching rule, in this exact order:

1. **`checkbox`** — the YAML core-schema **boolean** tag (`tag:yaml.org,2002:bool`): an unquoted `true | True | TRUE | false | False | FALSE`. Normalized form: canonical `true` / `false`. (Quoting demotes to `string`; `yes` / `on` / `1` are **not** core booleans — they are `string` / `number`.)
2. **`number`** — the YAML core-schema **int** or **float** tag (`tag:yaml.org,2002:{int,float}`), restricted to a **finite** value. Core-schema int covers base-10 `[-+]?[0-9]+` (leading zeros permitted — `007` resolves to the integer 7), hexadecimal `0x[0-9a-fA-F]+`, and octal `0o[0-7]+`; core-schema float is `[-+]?(\.[0-9]+|[0-9]+(\.[0-9]*)?)([eE][-+]?[0-9]+)?`. The non-finite core floats (`.inf`, `-.inf`, `.nan`) coerce to `string`, not `number`. Normalized form: the **canonical decimal** of the parsed IEEE-754 binary64 value (`1.0` → `1`, `007` → `7`, `0x1A` → `26`, `4.5` → `4.5`) — numeric comparison uses the parsed double, so `1.0` and `1` compare equal. A user who wants a numeric-looking token kept as a literal string (`007`, a phone number) **quotes** it.
3. **`date`** — a scalar whose YAML resolution is a **string** *and* whose entire (whole-string-anchored) content matches **RFC 3339** `full-date` (`YYYY-MM-DD`) or `date-time` (`YYYY-MM-DDThh:mm:ss[.fff][Z|±hh:mm]`). YAML 1.2 core has **no** timestamp type, so dates arrive as strings and Myne applies this recognizer on top. Normalized form: the RFC 3339 source verbatim (trimmed). A `date-only` value compares as `00:00:00Z` (start of day, UTC); a `date-time` without an offset is treated as UTC. Quoting does **not** suppress date typing (see the asymmetry note).
4. **`string`** — the fallback: any scalar not matched above, including the empty / null scalar (`key:` with no value → `string` with the empty value). Normalized form: the YAML-resolved string **verbatim** — Myne does **not** apply Unicode normalization (no NFC/NFKC) to property values, preserving the author's exact bytes (consistent with the §6 C1 byte-stability philosophy; case-insensitivity, if any, is a query-layer choice).

**The quoting asymmetry (load-bearing tie-break).** Quoting forces a YAML **string** node, which removes the `bool`/`int`/`float` core tags — so quoting a value **demotes** it out of `checkbox` and `number`: `flag: true` → `checkbox`, `flag: "true"` → `string`; `v: 1.0` → `number`, `v: "1.0"` → `string`. But `date` recognition runs on the *resolved string* (YAML erases the quote distinction for plain vs. quoted strings), so quoting does **not** demote a date: `due: 2026-06-14` and `due: "2026-06-14"` both type as `date`. This asymmetry is intentional and is pinned by vectors.

**Worked tie-breaks** (each a `property-coercion` vector): `007` → `number` (7 — core base-10 int permits leading zeros; quote it for the literal string); `0x1A` → `number` (26 — core hex int); `2026` → `number` (bare integer, **not** a date — a date needs the full `YYYY-MM-DD`); `2026-06` → `string` (not a complete `full-date`); `True` → `checkbox` (core accepts `true`/`True`/`TRUE`); `yes` / `on` → `string` (**not** core booleans); `"true"` / `"1.0"` → `string` (quoting demotes out of checkbox / number); `"2026-06-14"` → `date` (quoting does **not** demote a date); `555-1234` → `string`; `2026-06-14 deadline` → `string` (whole-string anchor fails).

**`list` element typing.** A sequence's type is `list`; **each element** is independently coerced by Step 3 (a list may be heterogeneous: `[1, true, hello, 2026-06-14]` → `[number, checkbox, string, date]`). A nested sequence-of-sequences element coerces to `string` (no list-of-lists in v0.1). The empty sequence `[]` is a `list` with zero elements. List membership queries (`contains`) compare against the per-element normalized forms.

**Tags and folders as pseudo-properties.** The folded `#tag` set (§3.7) ∪ frontmatter `tags:` and the `folder:` value (§3.6.1) are exposed by the index as queryable pseudo-properties alongside typed frontmatter properties, so a saved view can mix `hasTag` / `inFolder` scopes with property filters. Their identity folding (`§3.7.8 foldSegment`) is unchanged by this subsection — pseudo-properties reuse the existing tag/folder identity rules, not the property value-typing rules above.

The thirteen managed canonical fields (§3.6.1) are observed by this parse with their existing value-strict semantics intact (`trashed:` / `archived:` / `deleted:` / `done:` type as `date`/RFC 3339 when set, `template:` / `folder_index:` / `conflict:` type as `checkbox` only on canonical `true`, `kind:` as a `string` — queryable, e.g. an "all drawings" saved view — and `conflict_of:` / `cover:` as a `string`) — the coercion never relaxes or rewrites them. **`cover:` types as an ordinary `string` here and that is deliberate**: this parse is decrypt-free and non-mutating, so it can see the field's bytes but not whether the attachment they name still exists. The §3.6.1 grammar decides whether those bytes are a cover; the attachments catalog decides, at render time only, whether that cover can be drawn. The index is never asked the second question.

### 3.7 Inline-tag extension

Notes may contain inline tags — `#`-prefixed identifiers in body text that consumers (search, backlink, sidebar UI) treat as structured metadata distinct from the YAML frontmatter `tags:` list. The grammar below mirrors Obsidian's runtime behavior so an Obsidian-imported vault produces the same tag set in Myne as it does in Obsidian. Each rule is verified against observed Obsidian behavior in `agent-tooling/researches/2026-05-09-obsidian-inline-tag-behavior.md` (the Q-numbered findings cited per rule).

#### 3.7.1 Boundary

An inline tag begins at a `#` character preceded by either the start of a line OR a Unicode whitespace character. A `#` immediately following a non-whitespace character (e.g. `abc#tag`) is **not** an inline tag. (Research Q1.)

#### 3.7.2 Allowed character set

An inline-tag body consists of one or more Unicode code points, each of which is **not** in any of the following:

- U+2000 through U+206F (Unicode General Punctuation block)
- U+2E00 through U+2E7F (Unicode Supplemental Punctuation block)
- The ASCII characters: `'`, `!`, `"`, `#`, `$`, `%`, `&`, `(`, `)`, `*`, `+`, `,`, `.`, `:`, `;`, `<`, `=`, `>`, `?`, `@`, `^`, `` ` ``, `{`, `|`, `}`, `~`, `[`, `]`, `\`
- Any Unicode whitespace character

All other code points are permitted, including Unicode letters (Latin, Cyrillic, CJK, Arabic, etc.), digits, `_`, `-`, `/`, and emoji presentation. (Research Q2, Q4, Q14.)

This is a **deny-list** rather than the simpler positive allow-list given in the Obsidian Help documentation, because the runtime Obsidian regex (extracted from `app.js` and acknowledged by the Obsidian Help maintainer in `obsidianmd/obsidian-help` issue #816 as the actual behavior) is more permissive than the docs and is the authoritative source for compatibility with imported Obsidian vaults.

#### 3.7.3 Numeric-only reject (inline only)

An inline-tag body must contain at least one character that is not an ASCII digit. A body composed entirely of ASCII digits (e.g. `#1984`) is not a valid inline tag. The form `#y1984` is valid (`y` is non-digit). The form `#100-grit` is valid (`-grit` contains non-digit characters). The hex-string form `#00FFFF` is valid (hex letters are not ASCII digits).

This rule applies **only to inline tags**. YAML frontmatter `tags:` list entries are not subject to it; `tags: [1984]` produces a valid frontmatter tag value. The asymmetry is intentional and matches Obsidian's behavior — the inline `#1984` form is rejected because it is overwhelmingly a numbering convention (e.g. "Suite #200"), but a frontmatter list entry is an explicit user assertion that the value is a tag. (Research Q3, Q9; Obsidian core verbatim in `obsidianmd/obsidian-importer` issue #10.)

#### 3.7.4 Nested form

An inline-tag body may contain `/` characters, separating the tag into hierarchical segments. The number of segments is unbounded by this specification. (Research Q5.)

Index-layer derivation of parent-chain semantics (e.g., `#a/b/c` populating `#a` and `#a/b` as well as `#a/b/c` in a tag index) is not the parser's responsibility — the parser exposes the full tag string verbatim; the consuming index layer decides whether to expand the parent chain.

#### 3.7.5 Exclusion zones

The inline-tag tokenizer **does not** match within the following nested syntactic zones:

1. Fenced code blocks (`` ``` `` and `~~~`)
2. Indented code blocks (4-space indent)
3. Inline code (`` ` ``)
4. The interior of a wikilink, including target, alias, heading anchor, and block-id components (`[[…]]`, `[[…|…]]`, `[[…#…]]`, `[[…^…]]`, `![[…]]`)
5. Raw HTML embeds (block and inline)
6. The YAML frontmatter block (per §3.6's line-1-anchored detection)

When the parser is built on a nested-node syntax tree (e.g., the `@lezer/markdown` reference implementation per §8), zones (1)–(6) are excluded structurally because the inline-tag tokenizer runs only at the outer-inline-text level and does not descend into nested nodes. (Research Q7, Q9.)

**Math zones (MYND-48, landed).** Math (`$…$`, `$$…$$`) now renders (§3.2). The exclusion is **structural**: `InlineMath` is a leaf node (no inline children parsed inside), and the inline-tag deny-list already excludes `$` (§3.7.2), so a `#tag` can neither contain a `$` nor extend into a math span — no separate tokenizer pass is needed.

**Comment zones (MYND-315, landed).** The `%%…%%` comment recognizer (§3.1 block / §3.2 inline) is subject to the **same** zones (1)–(6) above, and the exclusion is likewise **structural**: the inline `%%` tokenizer runs only at the outer-inline-text level (it never descends into a fenced/indented/inline-code span, a wikilink interior, an HTML embed, the math leaf, or the frontmatter block), and the block `%%` leaf-parser only attaches to a paragraph-class line that literally opens with `%%` (a code fence / blockquote / list / heading line opens its own block first; frontmatter is detected line-1-anchored). So a `%%` inside any zone (1)–(6) is literal text, not a comment — pinned by the `markdown-comment` golden vectors. The editor decoration additionally guards with the shared `isInCode` predicate (belt-and-suspenders).

#### 3.7.6 Frontmatter scope

The inline-tag tokenizer does **not** match within the YAML frontmatter block. Tags inside frontmatter are parsed as YAML 1.2 list values from the `tags:` key (per §3.6).

The numeric-only-reject rule (§3.7.3) applies only to inline tags. Frontmatter `tags:` entries may be entirely numeric. (Research Q3, Q9.)

**Read permissive, propose legal.** §3.7.2's deny-list constrains what a surface may **propose or write** as a tag, not what a user's file may **contain**. A frontmatter `tags:` entry is read and displayed as the YAML scalar it is, whatever characters it carries: an imported vault keeps `c++`, `node.js` and values with a parenthesis, and no reader rejects or normalizes them (§6 C1). The converse is equally load-bearing. Anything that offers a tag to the user (the AI tag-suggestion band is the first) MUST present only bodies §3.7.2 permits, and any write of a tag MUST land one: a proposal carrying `(`, `)` or a space becomes a tag that no inline `#tag` can ever match and that the user cannot type. (`decisions.md` 2026-11-04, myne-md/myne#1025.)

#### 3.7.7 Recognize-only

The inline-tag tokenizer **only recognizes** tag occurrences. It MUST NOT rewrite, normalize, or canonicalize the bytes of any matched tag. The byte-stability guarantee in §6 (C1) extends to inline-tag bytes alongside the existing list (non-canonical emphasis, alternate list markers, etc.).

A user who wants to programmatically rewrite tags (e.g., a "rename tag across vault" affordance) must invoke an explicit, transparent conversion command — the parser does not perform implicit rewrites on save or on load. (Spec discipline derived from §6 C1.)

**Editor decoration ships as the interactive-tag UNIT (SYNC-17).** Recognize-only means the decoration is purely visual — it never rewrites tag bytes (display casing comes from the index, never a buffer edit; C1 above). The editor `#tag` chip (a clickable, cursor-aware pill) may land ONLY together with the tag-browse/tag-click surface — never as a standalone editor-polish change, because a clickable-looking tag with nowhere to go is a dead affordance. As of the tag-system unit (`decisions.md` 2026-06-14 "Tag system: interactive tag unit", MYND-45/MYND-46 — supersedes 2026-06-08 "Interactive tags ship as ONE unit", MYND-200) both shipped together: an inline `#tag` renders as a chip and clicking it opens the tag browser filtered to that tag. The cursor-aware chip reveals the raw `#tag` text when the caret is inside it, so the byte-stable source stays directly editable.

#### 3.7.8 Case identity

The inline-tag tokenizer surfaces tag bytes verbatim — un-normalized, un-folded. Tag identity (whether `#Tag` and `#TAG` collide for index purposes) is determined by the consuming layer. In Myne v0.1, the tag index applies Unicode case-fold and NFC normalization at index-write time, matching Obsidian's globally case-insensitive behavior.

The parser exposes raw bytes to keep its output deterministic and to push encoding policy to one place; downstream consumers (search index, sidebar UI, backlink graph) all share the same fold/normalize rule by virtue of going through the index layer. (Research Q10.)

### 3.8 Inline task-field extension

A **line-task** is a task-list item (§3.3) whose content may carry **task inline fields** — the metadata saying when it is due, whether it repeats, when it was completed, how urgent it is, and when to be reminded. Task management rests on a task being plain markdown and nothing else, so this metadata lives in the line, never in a sidecar.

Myne **reads three dialects and writes one**. Reading recognizes Obsidian's emoji form and Obsidian's Dataview-style inline fields, so a vault imported from Obsidian lights up in whichever form the user already had; without that, an import "succeeds" and the user's tasks are silently gone. Writing emits a single form. Obsidian parity is a **read** goal, not a write goal.

#### 3.8.1 Recognized forms

Two syntactic forms, which may both appear on one line:

**Bracketed (Dataview-style).** `[key:: value]` — an opening `[`, a key, the two-character separator `::`, an optional run of spaces or tabs, the value, a closing `]`. A key is a non-empty run of `[A-Za-z0-9_-]`. This is deliberately narrower than Dataview, which tolerates spaces in keys: a permissive key rule makes every `[` in prose a parse candidate, and every key in the recognized vocabulary is a single word. A field never spans a line break, and an unterminated field is not a field.

**Emoji (Obsidian Tasks).** A marker emoji followed by its value. Markers carrying a value: `📅` due, `🔁` repeat, `✅` done, `⏰` remind, `⏳` scheduled, `🛫` start, `❌` cancelled, `➕` created, `🆔` id, `⛔` dependsOn. Markers that **are** their value: `🔺` highest, `⏫` high, `🔼` medium, `🔽` low, `⏬` lowest. A trailing variation selector (U+FE0F) is absorbed into the marker.

An emoji field's value ends at the **first** of: the next marker emoji, a `[` (so both dialects can share a line in a half-migrated vault), a token-initial `#` (so a trailing `#tag` stays a tag instead of being swallowed into a recurrence expression), or the end of the line.

Key identity is case-insensitive; the record carries the canonical spelling. Obsidian's `completion` is read as Myne's **`done`**.

#### 3.8.2 Emitted form

Myne emits **one** form: bracketed fields with Myne's key names, single-space separated, in a stable order — `due`, `priority`, `remind`, `repeat`, `done`, then recognized-but-untyped fields, then values that did not parse. The stable order is normative: an unstable one would make every edit produce a spurious diff on the line.

Five fields are written: **`due`** (may carry a time), **`repeat`**, **`done`**, **`priority`**, **`remind`** (absolute). Everything else Obsidian Tasks supports is read and preserved but never emitted.

Myne diverges from Obsidian's key names in exactly one place: `completion` becomes `done`, so the inline field and the frontmatter field for note-tasks share one word for one concept. The "third dialect" a reader must learn is a single key.

**Editing any field on a line converts the whole line** to the emitted form, including fields the user did not touch — following §6's rule that only directly-changed lines adopt canonical forms. The consequence is accepted and stated plainly rather than left to be discovered: a task imported from Obsidian and then edited in Myne drops out of that user's Obsidian Tasks view.

#### 3.8.3 Value typing

`due`, `done` and `remind` carry an instant: a **full-date** (the `YYYY-MM-DD` shape owned by §3.6.4) optionally followed by a wall-clock time, separated by a space or a `T` — `HH:MM` or `HH:MM:SS`.

**Times are local wall-clock.** No UTC offset and no IANA zone identifier is ever stored or emitted. "09:00" means 09:00 wherever the user is, which is what a personal reminder means, and it keeps a coarse geolocation datum out of a file that gets exported as plaintext.

A value carrying an offset (`2026-08-01T10:00:00Z`, `…+03:00`) therefore **does not type at all**: it is preserved verbatim and surfaced as unparsed. Stripping the offset would silently shift a due date; refusing is the safer failure. Dates passing the shape but not existing (`2026-02-31`) are likewise refused rather than corrected.

`priority` types from its word form — `highest` / `high` / `medium` / `low` / `lowest`, case-insensitive — or from a priority marker emoji. `repeat` carries a **recurrence rule expression**, whose vocabulary is frozen in §3.8.7.

Values that fail to type MUST be **preserved and surfaced as unparsed**, never discarded and never reported as a parse error.

#### 3.8.4 `onCompletion` is deliberately not recognized

Obsidian's `onCompletion` runs an **action** when a task completes. It is a miniature action language, and interpreting it crosses the no-code-eval line the dialect defends elsewhere (§3.6.4's extraction-and-typing-only rule; the closed-registry discipline of the template engine).

Myne assigns it **no meaning whatsoever**. Its bytes are nonetheless preserved: because editing a line converts the whole line (§3.8.2), anything absent from the parsed record is deleted by the next write. Preservation and non-interpretation are separate obligations, and both are normative.

#### 3.8.5 Recognize-only

The task-field recognizer **only recognizes**. It MUST NOT rewrite, normalize, or canonicalize the bytes of any matched field. The §6 C1 byte-stability guarantee extends to task-field bytes: a file imported and never edited round-trips byte-identically, and a line already in the emitted form is a **fixed point** — rewriting it produces no change, so opening a vault cannot dirty its task lines.

Emission happens only through the single writer seam (§3.8.2), never as an implicit rewrite on load or save.

#### 3.8.6 Scope of recognition

The recognizer operates on **inline** content and has no view of the enclosing block, so it recognizes fields on any line, not only on line-tasks — exactly as the inline-tag tokenizer does (§3.7). Restricting fields to line-tasks is the **consuming layer's** obligation: the task index and the editor's chip decoration each apply it. A conformant implementation MAY recognize more broadly than it consumes, but MUST NOT consume a field from a line that is not a line-task.

Frontmatter is out of scope for task fields, and that exclusion is enforced where §3.7.6's is — at the aggregator, not in the tokenizer. The remaining exclusion zones of §3.7.5 (code spans, fenced code, wikilink interiors, HTML) apply structurally, since inline parsing is never invoked inside a range those nodes have already consumed.

#### 3.8.7 Recurrence rule vocabulary

The `repeat` field's value is a **recurrence rule expression** drawn from a **CLOSED** vocabulary of three tiers. The list below is exhaustive and normative; an expression outside it is not a rule (see "Unrecognized rules" below). Closedness is the point rather than a limitation: a general implementation of a recurrence standard is an **evaluator**, and admitting one would put a second execution surface in a dialect that refuses `onCompletion` (§3.8.4) and keeps the template registry closed for the same reason. Nothing in this section requires a date library, and a conformant implementation MUST NOT need one.

**Tier 1 — plain intervals.** `every <unit>` and `every <n> <unit>s`, where `<unit>` is one of `day`, `week`, `month`, `year` and `<n>` is a decimal integer ≥ 1 of at most three digits. Both singular and plural unit spellings are read.

**Tier 2 — weekday sets.** `every <weekday>`, and sets joined by `and` and/or commas: `every tuesday and thursday`, `every monday, wednesday and friday`. Weekday names are the seven canonical English names, Monday-first. A set is **normalized** on parse — deduplicated and reordered to canonical Monday-first order — so two spellings of one set are one rule.

**Tier 3 — calendar positions in a month.** `<ordinal> <weekday> of every month`, where `<ordinal>` is one of `first`, `second`, `third`, `fourth`, `last`; plus `day <n> of every month` (1 ≤ n ≤ 31) and `last day of every month`.

Parsing is **case-insensitive and whitespace-tolerant** (runs of whitespace fold to one space), because the value may arrive from a file a human hand-wrote or an importer produced. The *vocabulary* is nonetheless closed: tolerance never extends to admitting an unlisted phrase.

**Storage is canonical English; display is localized.** The bytes in the file are always the canonical English form above. A file MUST NOT carry a localized rule: a vault opened on a differently-configured device would otherwise become unreadable to its own owner, and switching app language would strand the user's own rules. Since a rule is **chosen from a control, never typed**, the canonical form is not something a user is ever asked to produce.

**Two families, with deliberately different behaviour.** The user selects between them by selecting the rule, so no hidden setting and no remembered anchor is involved:

| Family | Rules | Behaviour |
|---|---|---|
| **interval** | tier 1, tier 2 | Counts from the previous date. **Clamps** into a short month and then counts from the clamped date, so it may drift. |
| **calendar** | tier 3 | Anchored to the nominal calendar position. **Clamps** into a short month for that occurrence only, then returns to the nominal position — it does not drift. |

The contrast is normative and is what makes the month-end question answerable without hidden state. `every month` from 31 January gives 28 February and then **28 March**. `day 31 of every month` from 31 January gives 28 February and then **31 March**. A user who wants the 31st kept says so with a calendar rule; nothing has to remember an original anchor day the file does not carry.

Where a tier-3 ordinal position does not exist in a month (a month holding only four of a weekday, addressed as `fourth`), the occurrence clamps **back** to the last one in that month rather than spilling into the next.

**Anchoring mode.** A rule may carry the suffix ` when done`, which is part of the expression and case-insensitive like the rest of it:

- **due-anchored** (the default, no suffix) — the next occurrence is computed from the previous **due date**, so a calendar obligation does not drift when it is handled late;
- **completion-anchored** (` when done`) — the next occurrence is computed from the **completion date**, so an interval-from-last-action task ("water the plants every 3 days") drifts, as it should.

Both are real needs, which is why the mode is carried in the expression rather than inferred: inferring it would mean guessing which of two correct behaviours the user wanted, with no way for them to correct the guess.

**Advance rule (normative).** In due-anchored mode, the next occurrence is produced by adding **whole intervals from the previous due date until the result is strictly after the current date**. This yields exactly **one** pending occurrence — a rule three years stale produces one date, not a thousand catch-up occurrences — while preserving the calendar anchor. Completion-anchored mode has no stale-date case by construction, since its anchor is the completion itself.

Advancing is reachable **only from a user action** on the task. Nothing in this section permits an implementation to advance a rule on its own; a missed occurrence stays where it is, overdue and visible, until the user acts.

**Reminder co-advance.** When a line carries both `due` and `remind`, `due` is the anchor; when it carries only `remind`, `remind` is the anchor. The anchor advances by the rule and the other field shifts by **the same number of days the anchor moved** — the gap is carried, not recomputed. Recomputing it would let "ten minutes before" drift into "three hours after" over enough cycles.

**Unrecognized rules.** An expression outside this vocabulary MUST be **preserved verbatim** and **surfaced as unrecognized**. It MUST NOT raise a parse error, MUST NOT be approximated, and — the load-bearing clause — MUST NOT fall back to any default rule. A rule Myne cannot read must *look* unread: silently treating it as non-recurring, or as "every day", is a data-loss-shaped surprise in which the user believes a task repeats, completes it, and discovers months later that it did not.

### 3.9 Task-query block

A fenced code block whose info string is exactly `tasks` is a **task-query block**: a live list of tasks matching a query, rendered in place of the code. Recognition is by info string alone — no parser extension is required, since the info string is already in the parse tree — and it sits beside the diagram block (`mermaid`), which is recognized the same way.

Rendering is **purely visual**. The block's bytes are never modified by rendering, so §6 C1 holds unchanged: a file carrying a task-query block round-trips byte-identically when it is not edited.

**Self-reference is impossible by construction.** Inline parsing never descends into a code node, so a `- [ ]` written inside a task-query block is not a line-task. A block therefore cannot match itself, and a conformant implementation needs no cycle guard.

#### 3.9.1 The roster

The query body is a sequence of lines, one clause each. Blank lines and lines beginning with `#` are ignored. The clause roster is **CLOSED and exhaustive**; the list below is normative.

| Clause | Form |
|---|---|
| completion state | `done` · `not done` |
| due comparison | `due before <value>` · `due after <value>` · `due on <value>` |
| no due date | `no due date` |
| path containment | `path includes <text>` |
| tag containment | `tag includes <text>` (also `tags include`; a leading `#` is not part of the value) |
| priority | `priority is <highest\|high\|medium\|low\|lowest>` |
| sort | `sort by <due\|priority\|path>` · optionally suffixed ` reverse` |
| limit | `limit <n>` (also `limit to <n> tasks`) |

Clauses are **AND**'d. Parsing is case-insensitive and whitespace-tolerant; tolerance never extends to admitting an unlisted phrase.

A `<value>` is one of exactly three things:

- an **absolute** full-date, `YYYY-MM-DD` (the shape §3.6.4 owns);
- a **named** day — `today`, `tomorrow`, `yesterday`;
- a **relative** parameterized constant — `in <n> <unit>` or `<n> <unit> ago`, where `<unit>` is `day`, `week`, `month` or `year`.

#### 3.9.2 The boundary

> **A field name may never appear where a value goes.**

That sentence is the whole of the closedness rule, and it is what keeps the block a filter rather than an expression language.

`in 3 days` is a **parameterized constant** — the same shape §3.8.7's recurrence intervals already admit — and is accepted. `due + 3d` is an **expression**: it reads a field and operates on it. Once that is representable, so is comparing one field to another, and from there a conformant implementation needs an evaluator — which the dialect refuses on the same grounds it refuses `onCompletion` (§3.8.4) and keeps the template registry closed.

The three **function-valued** clause forms of the upstream grammar — `filter by function`, `sort by function`, `group by function` — are **all** excluded. Naming one and silently accepting the others would break the closedness claim.

The value set therefore has no field-reference member, and a conformant implementation SHOULD make that unrepresentable in its type system rather than merely rejected at parse time.

#### 3.9.3 Unreadable clauses, and the widen guard

Parsing is **total**: it MUST NOT raise an error on any input, and it MUST NOT silently ignore anything.

- An unreadable clause is **dropped**, and the implementation MUST record the clause's source text verbatim so the surface can report it. The clauses it *could* read still execute.
- When **every** clause was dropped and at least one clause was written, the query **MUST refuse** — it MUST NOT be treated as matching everything. A misunderstood query that renders the whole vault presents as a correct enormous result, which is the worst available failure for this construct.
- A query with **no clauses at all** is a different case and is legitimately unfiltered.

Both conditions produce zero clauses; only one refuses. An implementation that conflates them renders the entire vault for a misread query.

Dropped clauses MUST be reported **persistently, in the rendered block** — not in a transient notification. The block re-renders on every note open: a notification would recur indefinitely, and a shown-once notification goes silent, which is the exact failure the visible-drop rule exists to prevent.

#### 3.9.4 English only

The roster is **English only** and is not localized. It is a specification artifact: translating it would mean one contract and one vector set per shipped language, and — decisively — a vault that stops being portable between a user's own devices, because a query written under one app language would be unreadable under another.

The cost is paid down two ways rather than argued away: a **builder** writes canonical query text from choices, so keywords are read rather than memorized, and an unreadable clause is surfaced visibly (§3.9.3) rather than silently ignored.

#### 3.9.5 Row bound

An implementation SHOULD bound the rendered rows, and MUST state the remainder when it does. A list quietly showing part of its matches is a wrong answer presented as a complete one. Myne's bound is 100 rows absent an explicit `limit` clause.

## 4. File extension and on-disk identity

- The post-decryption plaintext content of a note is stored as **UTF-8 markdown text**.
- The file extension when a note is exported, mirrored, or otherwise materialized as plaintext is **`.md`**.
- The encrypted blob extension on disk is `.myn` per [`protocol.md`](protocol.md) §9.1. `.myn` is **never** a markdown content extension; it is exclusively an encrypted-blob extension.
- A user who copies a Myne vault to another machine sees `.myn` files at the OS level, not `.md` files. The post-decryption `.md` form is what the user obtains by exporting from inside Myne or by walking away from Myne entirely (per `vision.md` portability commitment).

## 6. Round-trip stability with Obsidian-imported notes

**Hard rule (C1, from 2026-05-01 grill).** Notes imported from an Obsidian vault are preserved byte-for-byte in their original form. Myne never silently rewrites:

- non-canonical emphasis delimiters (`__bold__`, `_italic_`)
- alternate list markers (`* ` bullets, `1) ` ordered)
- Setext headings (`Heading\n======`)
- reference links (`[text][ref]` + later `[ref]: url`)
- indented code blocks
- task list `[X]` (uppercase) variants
- callout / admonition syntax (`> [!NOTE]`) — rendered since MYND-47 (decoration-only; bytes preserved, never rewritten)
- block ID markers (`^block-id`)
- HTML embeds
- inline `#tag` bytes (per §3.7 — recognizer-only; never rewritten)
- `%%…%%` comment bytes (per §3.1 / §3.2 — recognize-and-render-only; dimmed in the editor, stripped from lossy projections, but **never rewritten** in the buffer or in the `.md` export, MYND-315)

**Rendering does not weaken C1.** Several of the forms above are now *rendered* with cursor-aware decorations (Setext headings — MYND-146; reference links — MYND-148; definition lists — MYND-152, §3.1; and, since MYND-315, `%%…%%` comments — dimmed in the editor, stripped on export, §3.1 / §3.2). Rendering is purely visual: the decoration hides or restyles glyphs on screen but never mutates the buffer, and the cursor-aware reveal restores the raw source for editing. A note containing any of these forms that is rendered, focus/blur-cycled, and exported untouched is byte-identical. C1 binds every decoration in the editor — reaffirmed, not relaxed, by the rendering work.

**Unterminated `%%` is inert (normative, MYND-315).** A `%%` that opens a comment but has **no** closing `%%` after it (inline or block) is **not** a comment: it stays literal text, renders unchanged, and hides nothing. Both delimiters are required — terminated inline `%%…%%` and terminated block `%%`…`%%` comment normally; an unterminated `%%` comments nothing. This is a **deliberate divergence from Obsidian**, whose unterminated `%%` swallows the rest of the document into a comment — a footgun where typing one stray `%%` makes everything below it vanish from render and export. Myne's inert rule is the safe choice (no "half my note disappeared" surprise; the bytes are preserved per C1 regardless). It is the load-bearing cross-client tie-break, pinned by the `markdown-comment` golden vectors in the `myne-test-vectors` companion.

**Implication for Myne authoring.** When a user imports a vault and then edits a note, only the lines they directly change adopt canonical emit forms. Untouched lines stay as written by the original author.

**Implication for migration.** Lazy migration on edit (rewriting all non-canonical syntax in a touched file on save) is **explicitly forbidden** by C1. A user who wants to migrate an imported note's syntax to Myne canonical forms must invoke an explicit, transparent conversion command (the wikilink-specific R2 command is the only such command in v0.1; see [`wikilink.md`](wikilink.md) §7).

**Sanctioned importer transforms (the C1 allowlist).** Exactly five import-time mutations are explicit, *documented* exceptions to the "never silently rewrites" rule above, sanctioned transforms rather than the silent rewrites C1 forbids, and together they are the **only** changes the importer makes to imported content. They are not all in scope for every source: **transforms 1 to 3 apply to every source**, and are the whole of what the Obsidian importer does; **transforms 4 and 5 fire only when the source is another Myne vault** and can never fire on a path-based import:

1. **`folder:` frontmatter injection (MYND-51).** The importer writes the directory-derived folder into the Myne-managed `folder:` field (§3.6.2) via the same frontmatter surgery as note create/move; the body is untouched. A pre-existing user-authored `folder:` is **preserved, never overwritten**.
2. **Import-time media-ref rewrite (MYND-52; ingest allowlist dropped in MYND-173).** A *resolvable* + *in-cap* (≤ 64 MiB) local media ref (`![[image.png]]` / `![](assets/img.png)`) is ingested into the encrypted attachment store and the ref rewritten in place to form C `![[att:<id>|filename]]` — the same form + byte-surgery the post-import **import-&-convert** command produces. Ingest is **not** content-type-gated: the raster/SVG/PDF import allowlist was dropped in MYND-173, so any resolvable in-cap media target is carried through. Whether an ingested attachment then *renders inline* — raster/SVG via `attachment://`, PDF via pdf.js, WAV audio via the inline player (MYND-259), MP4/WebM video via the inline player (myne#168) — or shows as an export-only file card is a **serve-time** decision, not an ingest gate. Only genuinely non-ingestable refs (remote URL — never fetched; missing target; oversize > 64 MiB) are replaced with a placeholder comment and counted by type, never rewritten on a name-match guess. This is documented import behavior (`decisions.md` 2026-06-08 → 2026-06-14 MYND-173 → 2026-08-07 video-attachments → 2026-08-15 embed-layout), so it does **not** violate C1; every byte outside the rewritten ref spans is preserved.

   **Layout is carried, not dropped (myne#409).** An Obsidian image embed spends its alias on the DIMENSION rather than on a display name, so `![[photo.png|300]]` / `![[photo.png|300x200]]` is rewritten with that dimension preserved as [embed layout segments](wikilink.md) rather than with `300` mistaken for the display filename; a markdown image's alt text (`![A sunset | 2026](photo.png)`) is likewise carried into the terminal `alt=` segment, pipes included, so the importer never has to mutate or drop the author's words. A dimension the closed value grammar rejects stays an ordinary alias rather than being deleted. The **import-and-convert** command reports how many refs kept a size or an alt, because a transform nobody can see is a transform nobody can check; the whole-vault Obsidian importer does not count them yet.

   **Scope: media targets only.** The rewrite path takes a `![[…]]` embed *only* when its target names media, decided by the same extension whitelist the note graph uses to tell a media embed from a note embed (`isMediaTarget`; a whitelist rather than "any non-`.md`", so a dotted note title such as `![[2024.review]]` is not mistaken for a file). A **note embed** — `![[Some Note]]`, `![[Some Note#Heading]]`, `![[Some Note^block]]`, or the hand-typed `![[Some Note.md]]` — is not a media ref, is not in this allowlist, and is therefore preserved byte-for-byte like any other content. Note-embeds are first class elsewhere in the dialect (§3.5) and in the note graph, which keeps them as edges flagged `embed`; an importer that turned them into placeholder comments was destroying an edge under cover of a transform this list never sanctioned (myne-md/myne#223).
3. **`title:` frontmatter injection (MYND-53 / MYND-51).** When an imported file has **no** frontmatter `title:`, the importer writes the filename-derived title (the filename minus exactly one trailing `.md`) into the Myne-managed `title:` field (§3.6.1) via the same `patchTitleField` surgery as create/rename; the body is untouched. A pre-existing user-authored `title:` is **preserved, never overwritten**, and an illegal title is injected **verbatim and flagged** in the post-import "needs attention" report (never sanitized — the provenance-split rule). Rationale: in Obsidian the **filename is the title**, but Myne is frontmatter-only-title (`decisions.md` 2026-05-28), so without this injection every imported note lands "Untitled". This materializes Obsidian's filename-as-title into the canonical FM field — it is **not** the dropped read-time first-`# H1`/filename fallback. (`decisions.md` 2026-06-09.)

 (Skipping a non-note entry — §3.6.3 — writes nothing, so it is not a transform at all.)

4. **Attachment-embed id rewrite, vault-to-vault import (myne-md/myne#464).** When the source of an import is another **Myne vault**, every form-C embed `![[att:<id>|…]]` in an imported note has its id replaced with the id the same bytes received in the TARGET vault. This is not an optimisation and not optional: `protocol.md` §9.9 derives an attachment id as `HMAC-SHA-256(DeriveSubkey(root_key, "attachments-id-hmac"), file_plaintext_bytes)`, keyed under the vault's **own** `root_key`, so a source vault's id resolves to nothing in the target and the embed would render as a tombstone. **The alias is carried through byte-for-byte**, layout segments (§2.1) included, and that means values outside the closed grammar AND keys this client does not recognise: §5.1 requires an out-of-grammar value be dropped at *render* time rather than rewritten in the source, and an unrecognised key to be passed over silently because it means the note is newer, not wrong. **One id is deliberately NOT rewritten**: an embed whose id the SOURCE catalog no longer resolves keeps that id, so it renders as a tombstone in the target exactly as it did in the source. §5.1 built that tombstone specifically to distinguish an attachment that was deleted from a reference that was never valid, and says the note bytes are never rewritten in either case; flattening it to text here would destroy a distinction the spec went out of its way to keep. The cost, stated rather than hidden, is one foreign identifier surviving in the target's content, which is an HMAC under a key the target does not hold.

5. **Wikilink retarget on import rename (myne-md/myne#464).** Also vault-to-vault only. Wikilink resolution is **title-keyed** (`wikilink.md` §5.3), so when a Myne-source import renames an incoming note because its title collides with one the target already has AND something being imported links to it, every imported link that named the old title is rewritten to the new one, in every form, including aliased, heading-anchored, block-referenced and path-form links, with the folder segment and the anchor preserved. Without this the link resolves to the target's own note of that name: a single hit, no ambiguity to warn about, and a different note than the author meant. The rename itself lands in the note's own `title:` field through the same `patchTitleField` surgery as transform 3, so the note **is** the renamed note rather than a note the report claims was renamed. Both transforms are idempotent: a target id is not a source id, and a new title is not an old one, so re-running an import does not compound them.

Everything else in an imported note is byte-for-byte preserved per the list above.

**Sanctioned export transforms (the C1 allowlist, export side).** The following export-time mutations are documented exceptions; each applies only to the **derived export artifact** (a lossy projection), never to the stored note or to the byte-verbatim `.md` egress:

1. **Attachment-embed rewrite (MYND-115/MYND-211, `decisions.md` 2026-06-11).** In an **attachments-included** export (per-note or vault tree), each form-C embed `![[att:<id>|filename]]` in the *exported copy* — anywhere in the note plaintext, **frontmatter included**, so a `cover:` value (§3.6.1) is rewritten exactly like a body embed, since the span scan that drives the rewrite reads the whole plaintext and does not skip the frontmatter block — is rewritten to reference the attachment file actually written beside it (its final, collision-suffixed filename) — inverting importer transform 2's form-C rewrite: form-C embeds return to plain wikilink embeds `![[<final filename><layout suffix>]]` referencing the exported file, where the suffix carries whatever the paragraph below says travels (it is empty for an embed with no layout, which is every embed written before myne#409). Refs originally ingested from markdown-image form (`![](img.png)`) also come back out in wikilink form — they converge rather than byte-revert — so import → export → import round-trips (re-import re-ingests either form into form C), without the transform being byte-inverse for markdown-form ingests.

   **Layout segments travel with the embed (myne#409).** A pixel `w=` (optionally with `h=`) is translated into Obsidian's own `|300` / `|300x200` alias spelling, so the exported vault opens at the width the author chose. Every other segment, including a percentage width for which Obsidian has no slot, a height with no accompanying pixel width (Obsidian has no height-only spelling), and a value this transform cannot itself read, is **passed through rather than dropped**: refusing to export bytes the transform merely failed to understand is a silent loss of author intent. The translated dimension leads; the remaining segments keep their original relative order after it, and `alt=` stays last. An unkeyed segment contributes nothing, because the final export filename already stands in for the whole filename. `align=` has no Obsidian counterpart and is a deliberate Myne divergence (`decisions.md` 2026-08-15); it degrades to an ignored alias segment rather than corrupting anything.
2. **Comment removal (MYND-315).** `%%…%%` comments (§3.1 / §3.2) are an editor-only annotation, so the **lossy** projections strip them: HTML, PDF, and stripped-TXT exports omit every terminated `%%…%%` span, and document statistics exclude them (one canonical recognize-strip pass over the parsed tree, shared by all three surfaces — never re-implemented per surface). An **unterminated** `%%` is inert and is therefore NOT stripped (it is not a comment). This transform is scoped to lossy projections **only** — the byte-verbatim `.md` export keeps `%%` exactly as written (a walk-away `.md` is the source; comments are author content). The vault's encrypted blob is never modified.

The default (no-attachments) `.md` export writes the stored plaintext **byte-for-byte verbatim**, embeds and `%%` comments included; the vault's encrypted blob is never modified by any export path.

## 7. Out of scope for v0.1

The following syntax is **not** parsed or rendered in v0.1. Authoring affordances do not produce them; imported content containing them is preserved byte-for-byte and rendered as plain text:

- ~~**Math.**~~ **Now rendered since MYND-48** (`decisions.md` 2026-06-08) — `$inline$` + `$$display$$` LaTeX render via lazy-loaded KaTeX; the `$`-vs-currency disambiguation grammar is in §3.2. No longer out of scope.
- **Attribute syntax.** `{#id .class key=value}` Pandoc-style attributes. Not native to GFM; not in v0.1. (The multi-color highlight `<mark class="hl-*">` form, decisions.md 2026-06-15, is **not** an exception to this: it is fixed embedded HTML with a closed `hl-*` class vocabulary enforced at the sanitizer — no general `.class`/`key=value` parsing, no arbitrary attributes.) **Nor are the form-C [embed layout segments](wikilink.md) (`|w=300|align=center`, myne#409) an exception**, and for exactly the same reason: they live inside a single wikilink token rather than as a general construct attachable to any element, their key vocabulary is CLOSED (`w` / `h` / `align` / `alt`) and their value grammars are closed too, an unrecognised key is inert, and no arbitrary attribute is ever parsed or reachable. The rule this section states is that Myne does not gain a general attribute syntax; a closed vocabulary on one construct is not one.
- ~~**Callouts / admonitions.**~~ **Now rendered since MYND-47** (`decisions.md` 2026-06-08) — a `> [!TYPE]` blockquote promotes to a styled callout container (Obsidian-full ~12 types, case-insensitive, custom title; colored tint + icon + title), via a cursor-aware decoration that composes with the blockquote bars and does not modify `blockquote.ts`; the `[!TYPE]` bytes are preserved (§6 C1), revealed on-cursor. Unknown type → plain blockquote. The `/callout` slash command emits `> [!note] ` (§5). (Interactive fold `+`/`-` is recognized + round-trips; the collapse toggle is a follow-up.)
- **Iframes / embeds.** Raw `<iframe>` HTML. Recognized as raw HTML; rendered as plain monospace; sandboxing is out of scope in v0.1 (a separate concern from the now-shipped attachment pipeline).
- **Custom container blocks.** `:::` div containers (Pandoc / Djot syntax). Not in v0.1.
- ~~**Mermaid diagrams.**~~ **Now rendered since MYND-49** (`decisions.md` 2026-06-08): a ```mermaid fenced block renders as an SVG diagram via lazy-loaded Mermaid (`securityLevel:'strict'`, `htmlLabels:false`); parse-error / load-failure falls back to the monospace code card, carrying a single line naming mermaid's reason when it gave one; a diagram renders at its NATURAL size and scrolls inside its own card rather than being scaled to the column width (myne-md/myne#629); cursor-aware whole-block reveal, bytes preserved (§6 C1). **PlantUML remains out of scope** (recognized as fenced code, rendered as a code card).
- **Inline images.** `![alt](path)` and `![[image.png]]` are parsed and round-trip-stable. The attachment-encryption pipeline **ships in v0.1** (`protocol.md` §11.2; PR #53), so **attachment-form** refs (`![[att:<id>|filename]]`) render inline (raster/SVG via `attachment://`, PDF via pdf.js). **Raw-path** refs (`![[image.png]]` / `![alt](path)`) are still not rendered as images: the Obsidian importer (MYND-52) rewrites the ingestable ones to attachment form and leaves the residual as placeholder comments; a raw-path ref that survives in a note shows as a chip/text, not an `<img>`. **Reference-style images** (`![alt][ref]`) resolve against the same link reference definition table as reference links (§3.2); the rider that hides a definition line referenced only by an image **landed with MYND-164**.

## 8. Parser configuration (informative)

For the v0.1 reference implementation in the desktop client:

- Parser: `@codemirror/lang-markdown` configured with `markdownLanguage` (CodeMirror's GFM-bundled base language) plus a footnote `MarkdownConfig` extension plus the Wikilink `MarkdownConfig` extension defined in [`wikilink.md`](wikilink.md) plus a frontmatter-recognizer that tags the leading `---\n…\n---` block as a special node.
- Definition lists (§3.1) use a custom `MarkdownConfig` extension (a `LeafBlockParser`, the same hook CommonMark uses for setext headings and link references) that emits a `DefinitionList` block node with `DefinitionTerm` / `DefinitionMarker` (`:`) / `DefinitionDesc` children for the pinned tight subset. GFM has no definition-list node, so this extension is the sole producer; it is registered both in the shared serialization parser and in the editor's `markdown({ extensions })` so the editor's `syntaxTree` carries the node for decoration. Setext headings and reference links require **no** parser extension — `markdownLanguage` already produces `SetextHeading1`/`SetextHeading2` and reference-style `Link` nodes; MYND-146/148 are decoration-only.
- Comments (§3.1 / §3.2) use a custom `MarkdownConfig` extension (`src/dialect/lezer/comment.ts`, MYND-315) because GFM and `@lezer/markdown` ship no `%%` comment construct (the package's reserved `Comment`/`CommentBlock` nodes are for HTML `<!-- -->` comments, a distinct construct). It is hand-rolled (no new dependency, like the highlight config). Two hooks, both **terminated-only**: an inline `parseInline` delimiter (`%%`, registered `after: "Emphasis"` — the same slot family as highlight / strikethrough) emits a `DialectComment` node with `DialectCommentMark` (`%%`) children, and the delimiter resolver leaves an unmatched `%%` as plain text (no node — the inert rule, for free); a block `parseBlock` `LeafBlockParser` (the def-list / link-reference pattern) attaches to a paragraph-class line opening with `%%` (`endLeaf` so it interrupts an open paragraph), accumulates lines, and on the first line carrying a closing `%%` commits a `DialectCommentBlock` node (open + close `DialectCommentMark` children) — and on external termination (blank line / EOF / another block) with **no** closing `%%` seen, `finish` returns `false` so the run reverts to an ordinary paragraph (the inert rule). The node names are deliberately distinct from the reserved HTML-comment nodes so the strip targets them precisely. Like footnotes/definition-lists it is registered in both the shared serialization parser and the editor's `markdown({ extensions })`. Recognizer-only — emits nodes, never mutates bytes (§6 C1). The editor decoration (`src/editor/decorations/comment.ts`) applies a single de-emphasis (dim) `Decoration.mark` to both the inline span and the multi-line block — the comment stays visible-but-muted in the editor, never hidden (the 2026-06-17 UX revision: a fully-hidden comment is invisible-and-confusing); the strip happens only in the lossy projections, a single recognize-strip pass over the same nodes consumed by `emitNoteHtml` (HTML/PDF), `emitNoteText` (stripped-TXT), and the `extractBodyText` document-statistics projection.
- Footnotes (§3.4) use a custom `MarkdownConfig` extension (`src/dialect/lezer/footnote.ts`, MYND-153) because the `GFM` bundle (`[Table, TaskList, Strikethrough, Autolink]`) carries no footnote config and `@lezer/markdown` exports none. It emits an inline `FootnoteReference` node (registered `before: "Link"` so `[^…]` outranks standard link parsing) and a block `FootnoteDefinition` node (registered `before: "LinkReference"` so a `[^id]: text` line is claimed as a footnote rather than half-parsed as a CommonMark link reference definition), each exposing `FootnoteMark` (`[^`, `]` / `]:`) and `FootnoteLabel` (the identifier) children. The `FootnoteDefinition` is a **composite block**: its body parses as nested block content via a continuation rule (`NodeSpec.composite`), so multi-paragraph footnotes and fenced code / blockquotes *inside* a footnote render correctly. Like definition lists it is registered in both the shared serialization parser and the editor's `markdown({ extensions })`. The v0.1 subset: an identifier is a non-empty whitespace-free run with no `]`; a definition begins a block line (`[^id]:`, content optional — a bare `[^id]:` is an empty definition) and its body continues onto following lines that are blank or indented ≥4 columns (the Pandoc / GitHub continuation rule), ending at the first less-indented non-blank line; a footnote-definition line also interrupts an open paragraph (so consecutive `[^1]:`/`[^2]:` lines are distinct definitions). Recognizer-only — it emits nodes and never mutates bytes. The editor renders the reference as a superscript marker and collects definitions into a derived end-of-document list (a VIEW; in-source definition lines stay byte-stable in place); see `decisions.md` 2026-05-31.
- Inline task fields (§3.8) use a custom `MarkdownConfig` extension (`dialect/src/lezer/task-field.ts`, MYND-611). Both dialects are recognized in one pass and emit one node shape — `TaskField` with `TaskFieldKey`, optional `TaskFieldValue`, and (bracketed form only) `TaskFieldMark` children for `[`, `::` and `]` — so a consumer walks a single structure regardless of which dialect the file happens to use. The bracketed rule is registered **`before: "Link"`**, and that slot is load-bearing rather than incidental: `[due:: 2026-08-01]` collides with CommonMark link syntax, so without outranking `Link` the field is claimed as a link label first and never forms. This is the same slot, for the same reason, as the footnote reference (`[^id]`) and the wikilink config; the three coexist because each rejects immediately on its own second character. Emoji markers are up to two UTF-16 code units, so the two-unit form is matched first — otherwise a surrogate pair's lead unit is mistaken for a one-unit marker. Registered in both the shared serialization parser and the editor's `markdown({ extensions })`. Recognizer-only — emits nodes, never mutates bytes (§6 C1); typing lives in `dialect/src/taskFields.ts` and emission in `dialect/src/taskFieldWriter.ts`, which is the single writer seam.
- The frontmatter recognizer is single-pass and does not parse the YAML body; it only delimits the block. A **separate, read-only YAML-body parse** runs *outside* the editor recognizer to populate the derived property index (§3.6 + the value-typing ruleset §3.6.4; the `vault.indices` / `MYI1` projection, [`protocol.md`](protocol.md) §9.8, MYND-271): it parses the body for *indexing only*, is non-mutating (§6 C1 preserved), and is distinct from the still-deferred Properties *editing* UI. The editor's in-buffer recognizer stays single-pass and YAML-body-blind; the derived parse is a query-layer concern, not an editor-decoration concern.
- HTML embedded inside markdown is recognized via `@codemirror/lang-html` (forced transitive of `lang-markdown`). **Amended by MYND-209** (`decisions.md` 2026-06-08, supersedes the prior "no sanitization, no XSS surface" posture): a curated safe subset — inline `<kbd>`/`<mark>`/`<sub>`/`<sup>`/`<abbr title>` and block `<p>`/`<details>`/`<summary>` — is **rendered** by sanitizing the raw span through **DOMPurify** (lazy-loaded) under an ultra-tight allowlist (`ALLOWED_TAGS` = those 8; `ALLOWED_ATTR` = `[title, class]`; KEEP_CONTENT). **`class` is widened only for multi-color highlight** (decisions.md 2026-06-15) and immediately narrowed by an `uponSanitizeAttribute` hook: it survives ONLY as exactly one allowlisted token from the closed `hl-*` set AND ONLY on a `<mark>` — multi-class, unknown tokens, and `class` on any other tag are stripped (falling back to plain rendering; bytes still preserved per §6 C1). No `style`/`id`/`src`/`href` ever survives. Rendering is via `innerHTML` of the **sanitized output ONLY** — never raw note HTML — so the introduced XSS surface is bounded to DOMPurify's vetted output; CSP (`script-src 'self'`, no `'unsafe-inline'`) is defense-in-depth. Off-allowlist tags (`<script>`/`<iframe>`/`<img>`/etc.) and HTML inside code spans/fences are NOT rendered and stay plain text. This is the SYNC-5 trusted-input contract reused by mermaid (MYND-49) SVG sanitization.

This section is informative — a future Myne client implementation may choose any parser that produces an AST conformant to §3 and emits per §5. The dialect, not the parser, is what binds clients.

## 9. Versioning

This dialect specification covers Myne v0.1 only. A later version will pin its own dialect specification with its own magic-byte and AAD-prefix scheme per [`protocol.md`](protocol.md) §10. There is no provision for in-place dialect upgrades within v0.1.
