# AGENTS.md

Guidance to OpenCode when working in this repository.

Subdirectory `AGENTS.md` files cover their own domain in depth. OpenCode loads the nearest file when work enters that directory:
- `src-tauri/AGENTS.md` — Tauri 2 host, capability ACL, plugin pattern, Windows lib-name quirk
- `core/AGENTS.md` — `myne-core`, the shared backend crate: the host/IO/task seams, lifecycle hooks and plugin-core layout
- `protocol/AGENTS.md` — RustCrypto primitives, subkey derivation discipline and vectors
- `src/AGENTS.md` — React UI patterns, design tokens and mock-layer status
- `docs/AGENTS.md` — spec authoring rules
- `e2e/AGENTS.md` — tauri-driver desktop harness and scenario authoring rules
- `e2e-web/AGENTS.md` — browser web-E2E lane
- `mobile/AGENTS.md` — mobile client patterns
- `myne-agents/AGENTS.md` — agent, skill, feature and session layout

## Design context (pointer)

Three files at the repo root carry the visual + strategic system. Read in this order before designing any UI:

1. `PRODUCT.md` — strategy: register, users, voice, brand personality, anti-references, design principles. Cross-client (desktop + future mobile + web). Read before any new screen.
2. `DESIGN.md` + `DESIGN.json` — visual system in [Google Stitch DESIGN.md format](https://stitch.withgoogle.com/docs/design-md/format/). Frontmatter is the machine-readable token layer; `DESIGN.json` carries the live-panel components, tonal ramps, shadow + motion + focus extensions.
3. `docs/design/` — **the design canon itself**: `README.md` (voice + tactical rules), `colors_and_type.css` (the CSS-variable source — the binding values), `ui_kits/desktop/` (JSX primitives), `preview/` (token specimen tabs).

**The design canon lives in this repository.** There is no external design file that outranks it — `docs/design/` is canonical, `DESIGN.md`/`DESIGN.json` are its machine-readable projection (where the two disagree, the CSS is the value and `DESIGN.md` gets corrected), and `src/` is the implementation, binding to CSS variables rather than literals (`check-token-adoption.mjs` is the ratchet). When a shipped screen and the canon disagree, decide which side is wrong **on the merits** — fix the drifted screen, or update `docs/design/` in the same change when the screen genuinely improved on the system. Leaving the two silently disagreeing is the one option that is never right.

`/impeccable` commands (craft, polish, audit, etc.) read `PRODUCT.md` + `DESIGN.md` automatically. Do not duplicate their content into other docs.

**And what a change OWES the design system lives in `myne-agents/reference/design-system.md`**,
because this section is read and that file is where a skill's standing obligations point. The split is
deliberate and worth stating: `docs/design/` above stays the CANON for values and voice, and the
companion file holds the PROCESS and RATCHET rules a change has to satisfy, which is the half that
used to live only in `stories/README.md` and so was read by nobody with a skill loaded. It carries
the token sheet as the values layer and a literal as permanent, the specimen and description
ratchets, the nine-item story definition of done, the casing split (Title Case for a name in a list,
sentence case for product copy), the accessibility levels (`error` by default, `todo` to record,
`off` with a reason), the `--z-*` ladder, and the rule that an audit follows a symptom rather than a
calendar. `stories/README.md` is the human-facing copy of the same material.

## Session output convention (pointer)

OpenCode loads `.opencode/skills/adhd/SKILL.md` and `.opencode/skills/diverge/SKILL.md` through `opencode.json`. The pair is deliberate: `adhd` shapes how an answer is written, `diverge` shapes how it is arrived at, and the first without the second yields well-shaped first drafts of the obvious answer. OpenCode supplies the instructions for each request; `.opencode/plugins/compaction.ts` carries mutable session state through compaction. The convention shapes *how* an answer is written, never what it may claim: security, crypto, spec and data-loss content is exempt from every brevity rule, and each artefact-producing skill keeps its format. Read the skill for the full rules.

`WORK DISCIPLINE` is preserved as compaction state: after a repository change, the next action is `/pr-review`, then `/done`.

The convention applies to interactive OpenCode sessions. CI classifiers run their dedicated skills through `opencode run` and do not load this project configuration.

## How work runs here (pointer)

**Every change to a repository runs on the same lane, whatever the request looked like.** A session
that started from `/grill-me` and a session that started from a one-line "fix this" owe the identical
five things. This section exists because the rules behind them live in `myne-agents/reference/`, and
those files are read only through a skill's standing-obligations block: a session that invokes no
skill reads none of them, which is exactly the session that then skips them. This file is loaded for
every session in this tree, so the lane is stated here and the mechanics stay there.

1. **No issue, no work, and the setup is asked for.** Work that changes a repository binds to a
   tracked issue (`issue: myne-md/<repo>#<n>`), and when none exists the issue is filed through the
   `issue-pm` subagent. But before either the issue or the worktree is created, the skill asks a
   single yes/no question and takes no action until it has the answer: `"No tracker issue exists for
   this and I would work in a fresh worktree. File an issue and create the worktree? (y/n)"`. When
   the issue already exists it asks only about the worktree. The only exception to the gate is the
   user answering `n` to that question: silence is not it, "this is tiny" is not it, and neither is
   "we are in a hurry". Reading, explaining, reviewing, researching and answering a question are
   outside the gate, since none of them change anything. Move the issue to `status: in progress`
   through `issue-pm` when you start: on this lane nothing else will, because that transition
   belongs to `/do-work` and this lane skips it, so the issue would jump from `triage` straight to
   `ready to merge` and no second session would ever see it as taken.
   `myne-agents/reference/github-issues.md`.
2. **A session that changes a repository works in a worktree of it, never in the shared checkout.**
   The section below is that rule in full, including where a worktree lives and what it branches from.
3. **The planning front-half is sized, the tail is not.** Work that is large, contested or unclear
   goes `/grill-me` then `/write-a-prd` then `/prd-to-tasks` then `/do-work`, which produces the
   artefacts under `myne-agents/features/<feat>/`. Work that is small and already understood skips
   those four and is implemented directly. **Size is measured in consequence, not in lines**: a
   change touching cryptography, the on-disk format, sync, a capability ACL, an egress allowlist, or
   any guarantee `docs/threat-model.md` states is never small, however short the diff, because the
   threat model changes in the same PR and a design step is the only place that ordering can be
   enforced. And skipping the front half discharges none of the standing obligations: a protocol
   change still ships with its `myne-test-vectors` change, a user-facing change with its
   `myne-website` user-guide PR (`myne-agents/reference/github-issues.md`).
4. **The tail is `/pr-review`, then `/done`.** `/done` is the only committer and
   the only PR-opener, in every repo the work touched. A branch with commits on it and no PR is
   unfinished work, not finished work, and so is a clean checklist. `/pr-review` and `/done` both run
   against a plain branch with no feature directory, so ad-hoc work owes the same tail.
5. **Something coupled to the work in hand is fixed in the branch you are already in**, not filed as
   a new issue, and coupling decides that rather than size. Work that turns out to be genuinely
   distinct is the user's call: ask once, and never file without their answer. Two things always
   leave the branch instead, a legal or policy requirement (a `myne-ops` issue, and change nothing)
   and a decision the user owns, such as the threat model, the on-disk format, an anti-feature or a
   spec reversal (stop and ask). The full table, including what an unattended run does with a
   distinct discovery, is in `myne-agents/reference/github-issues.md`, "A discovery is implemented,
   not filed".

## Worktrees (pointer)

**Every session that changes this repository works in a worktree of it, unless the user says
otherwise.** Not the shared checkout, not "just this one file". That checkout's branch belongs to
every session sitting in the directory, so switching it puts their next commit on your branch, and
committing from it lands your work on whatever branch the last session left it on. The shared
checkout stays on the default branch and is for reading.

**And creating one is asked for, not assumed.** It is one half of the single yes/no question in lane
item 1 above: the skill asks `"No tracker issue exists for this and I would work in a fresh
worktree. File an issue and create the worktree? (y/n)"` before it creates either, and does nothing
until it has the answer. On `n` the work proceeds in the current checkout, and the session says once
that it is untracked and not isolated.

A worktree for this repo is created only with `git worktree add`, into
`.opencode/worktrees/<name>`, and never anywhere else. It branches from **`origin/develop`**:
`git worktree add .opencode/worktrees/<name> -b <branch> origin/develop`.
Branching from the current local HEAD instead carries whatever the working checkout happens to be
sitting on into the new branch, which is how a feature branch picks up an unrelated half-finished
change and a PR arrives with a diff nobody can explain. The session scratchpad under `/private/tmp` is
specifically wrong for one: it is per session and gets cleaned, so the worktree outlives the
directory `git worktree list` still points at, and `.opencode/worktrees/` stops being the roster of
what is in flight. Name it after the issue (`410-note-covers`) so the worktree, the branch and the
session read the same.

**The point is that finished work leaves nothing behind**: branch pushed, PR open, machine back to
where it started. So the worktree is removed once its PR is open, together with its local branch,
since the PR tracks the remote one. Never before the PR exists, and never on a dirty tree without
saying what is uncommitted.

One trap, because it has cost two sessions already: inside a worktree, a nested companion repo
(`myne-agents` and friends) is a **symlink** to the shared checkout, and that is correct. The Write
tool refuses to resolve through it; the answer is one Bash write to the absolute path, not cloning
the companion in. A copy lands the file in a tree nobody commits, so it looks written and is
invisible everywhere else. **And editing is the only thing that works through it**: git in a
companion repo is refused outright from a worktree session, `!` included, because a worktree
session's git may only target its own worktree. So a change spanning the main repo and a companion
cannot be closed out in one sitting. `/done` commits and PRs the main repo, Gate 5 removes the
worktree, and the companion PR is opened after that, from a session that is no longer isolated. Plan
the merge order around it rather than discovering it at the gate. Full rule:
`myne-agents/reference/worktrees.md`.

## OpenCode harness

This repo uses OpenCode only:

- **`AGENTS.md` is the single source of repository rules.** Subdirectory `AGENTS.md` files add their domain guidance when work enters that directory.
- **The agent tooling is clone-local, not tracked.** `workspace/link-skills.sh` symlinks every skill in the private `myne-agents` companion into `.opencode/skills/`, and the command wrappers in `.opencode/commands/` and the agent mirrors in `.opencode/agents/` are the same idea by hand: each one either points at, or carries the body of, a file in a repository this one does not publish, so `.opencode/.gitignore` excludes all three groups. A fresh clone therefore has no slash commands and no subagents until `./workspace/setup.sh` has cloned `myne-agents` and `link-skills.sh` has run. **Two exceptions are tracked and must stay that way**: `.opencode/skills/adhd/SKILL.md` and `.opencode/skills/diverge/SKILL.md` are authored here and loaded as `instructions` by `opencode.json` in every session, and `.opencode/agents/subworker.md` has no source in `myne-agents` and no second copy anywhere, so gitignoring it would delete the agent rather than de-publish somebody else's file.
- **Subagents are mirrored, not shared.** `.opencode/agents/issue-pm.md` and `.opencode/agents/legal-work.md` are body-copies of `myne-agents/agents/*.md` with an OpenCode `description` + `mode: subagent` frontmatter in place of the canonical `name`/`color`. Edit the canonical source, then re-copy the body. That refresh is a hand procedure with no machine check, and it had already rotted once: the `issue-pm` mirror had lost twenty lines of prose rules before the mirrors were untracked.
- **The adhd/diverge convention** is loaded by `opencode.json`; `.opencode/plugins/compaction.ts` preserves mutable state through compaction.
- **Permissions** are declared only in `opencode.json`. It deliberately configures no MCP servers.

Git hooks are managed by **lefthook** (`lefthook.yml`, which is the authoritative list). `pre-commit` runs the fast lint set (rustfmt-check, the SPDX header over every tracked Rust file (`scripts/check-spdx-headers.mjs`), `tsc --noEmit`, the seam/coverage guards + the i18n catalog check under `scripts/` (see "Repo guards" below), whitespace, EOF newline, single-`Cargo.lock` check, secret pattern guard); `pre-push` runs the local battery, **glob-gated** so a push touching neither Rust nor TypeScript skips it (Damm-32 table drift, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, `pnpm build`, `pnpm test`). The wasm-target clippy, the `myne-web-wasm` test run and the `--no-default-features` AI-free check are **CI-only** now: `.woodpecker/main.yml` already runs each at that strength (`wasm-protocol` carries both wasm clippys and `cargo test -p myne-web-wasm`; `tauri-compile` carries `cargo clippy -p myne-desktop --all-targets --no-default-features`, strictly stronger than the local `check`), and they were the slowest-throughput half of the battery; `commit-msg` rejects AI co-author/attribution trailers and requires a `Signed-off-by:` trailer (the DCO, `CONTRIBUTING.md`; a `Merge …` subject is exempt, since git writes it and there is no authorship decision in it). **`pre-push` also carries `protected-branch`**, which refuses a push whose REMOTE ref is `refs/heads/develop`, `refs/heads/main` or `refs/heads/release`, in this repo and in every companion (myne-md/myne#592). `release` is on that list because it is the branch that DEPLOYS: `myne-website`'s `.woodpecker.yml` maps `release` to production and `develop` to staging, so a `develop`-only guard protected the branch with no blast radius and skipped the one that publishes. It is hygiene rather than enforcement and says so in its own comment: the org's plan offers no server-side branch protection for private repos, so there is nothing on GitHub to lean on, and `--no-verify`, `LEFTHOOK=0` and `LEFTHOOK_EXCLUDE=protected-branch` each bypass it. Two hatches are sanctioned instead. `MYNE_ALLOW_PROTECTED_PUSH=1 git push ...` is the one-off; `git config myne.allowProtectedPush true` is for a repo whose normal workflow IS pushing to its default branch (`myne-range` documents exactly that in its own AGENTS.md, and `homebrew-tap` and `myne-branding` work the same way). Both hatches parse a VALUE (`1`, `true`, `yes`, `on`, case-insensitively) and refuse anything else, so `MYNE_ALLOW_PROTECTED_PUSH=0` keeps the guard ON rather than switching it off, which is what testing the variable for non-emptiness used to do. The flag is read with `git config --local`, deliberately: a plain `--get` reads the merged cascade, so one `--global` setting would switch the guard off in all eleven clones at once, which is the failure the flag exists to prevent. Each `lefthook.yml` also carries a `min_version`, because `lefthook run` and the real git hook path IGNORE an unknown key without a word (only `lefthook validate` rejects one, and hooks never call it), so an older binary would drop `use_stdin` and leave a guard printing a green tick while checking nothing. CI is self-hosted Woodpecker via the Forgejo mirror (`.woodpecker/`, Linux runner; `docs/decisions.md` 2026-05-01) — the hooks are the local pre-push net, CI is the remote gate. **The config is a DIRECTORY of two workflow files and the split is load-bearing**: `.woodpecker/main.yml` is the per-push pipeline, and `.woodpecker/e2e.yml` holds **both** end-to-end suites (the desktop tauri-driver suite and the browser web lane) and runs on a **manual trigger only**, carrying the variable `RUN_E2E=true`, before a release (myne-md/myne#579, `docs/decisions.md` 2026-08-23 entry 0529; procedure `docs/dev/e2e.md` "When CI runs these suites"). Two consequences worth stating rather than inferring. A green push pipeline is **not** evidence about a single E2E scenario, and the release runbook (`myne-ops/runbooks/release-checklist.md` phase 0) is what owes that claim. And the manual event now carries one intent at a time: `main.yml`'s manual entry is gated `RUN_E2E != "true"` so an E2E trigger does not also run the whole pipeline and, on `develop`, deploy `app.myne.md` through the `&web-deploy` anchor below. **Three lanes, one pipeline** (MYND-574; the third landed 2026-08-13): the desktop lane is one serial chain (`pnpm-build` → `vitest` → `tauri-compile` → `cargo-test-tauri`) because each of those runs `pnpm install` into the shared workspace `node_modules` (`e2e` was its tail until myne-md/myne#579 moved it out, so `web-build` and `sync-sim` now hang off `cargo-test-tauri` instead); the **web lane** hangs off the end of it (`web-build` — the web bundle plus the artefact greps, the seam contract against the web implementation, the bundle budget and the screen/surface/testid rosters) so it adds nothing to the desktop lane's wall-clock, alongside the early Rust wasm gates (`wasm-protocol`); the **mobile lane** (`mobile-build` → `npm-licenses` → `mobile-vitest` → `mobile-flow-logic`, plus `mobile-compile` for its Rust) hangs off `web-build` for the same reason and by the same rule. That mobile chain is **serial, and every edge into it and inside it is `optional: true`** (the three internal ones since myne-md/myne#515; the `web-build` edge already was): serial because all four run `pnpm install` into the shared workspace `node_modules` and raced as siblings, optional because a non-optional edge made one red step remove every step behind it, which is how a license-gate failure deleted the mobile Vitest suite and the whole Playwright flow-logic tier from the run. An optional edge still orders; it only stops requiring that the parent passed. The mobile lane replaced a *separate pipeline in a separate repo* that began by cloning this one and `git reset --hard`-ing it to `develop` tip — so a mobile commit was not reproducible, and a change here that broke mobile was invisible until somebody pushed there. Three of that pipeline's six steps simply vanished, absorbed by workspace-wide steps that already existed (`cargo fmt --all`, `cargo deny check`, the shared `pnpm install`). Every step that can go red is listed in `notify-failure` (the only thing that pushes a failure to the maintainer), and every compile/test step carries the `code-paths` filter, so a docs-only commit skips them. **Four steps deliberately carry no filter and must keep it that way**: `hooks-parity` (its EOF/whitespace/SPDX checks apply to docs too), `bundle-record` (the append-only hash record *is* a doc, so a docs-only commit is exactly when it must run), `twin-inventory` (its `--check` half holds a generated `docs/**` file to its roster, and a hand edit to that file is a docs-only commit) and `manual-test-roster` (same reason twice over: its `--check` half gates a generated `docs/**` file, and the roster records what a human must verify before a tag, which is a procedure a docs-only commit moves) — all four say so in their own `.woodpecker/main.yml` comments; adding `when: *code-paths` to any of them is a regression, not a cleanup. **The web deploy chain is no longer in this pipeline at all** (myne-md/myne#584): `web-docker-build`, `web-docker-deploy` and `web-smoke` are gone, because CI verifies and does not publish. What survives is `web-container-check`, which builds the image to ASK it questions rather than to ship it, runs `check-web-container-headers.sh` against the running container, and is path-filtered to `web/**` since that build is expensive and duplicative. Publishing `app.myne.md`, the `--has` bundle-hash precondition and the post-deploy smoke are one by-hand procedure in `myne-ops/runbooks/web-client-deploy.md`. The **whole mobile lane**, plus `web-build` and `sync-sim`, carries `status: [success, failure]` and aliases `*code-path-globs` rather than `*code-paths`: a `when` entry's implicit `status: success` is a *pipeline-wide* condition, not a `depends_on`-scoped one, so without it any red step anywhere skips gates that have no dependency path to it — which is how `mobile-vitest` and `npm-licenses` went unrun for the whole time the mobile client had been in-repo (myne-md/myne#458). Every step in `.woodpecker/e2e.yml` but its notifier carries the same key for the same reason, and one further one: that workflow exists to produce a pre-release inventory, and a skipped gate in an inventory is worse than a red one. It is written there ONCE, as a YAML anchor, because a hand-copy is a second place to drift and losing the key is silent. Bypass with `git commit --no-verify` only when you understand why.

**A new user-facing flow ships WITH its E2E coverage**: the same change carries the `data-testid` pass (`src/AGENTS.md` "Test observability") and a scenario on the right harness (`e2e/AGENTS.md`, procedure `docs/dev/e2e.md`). A PR that adds a flow without its E2E scenario gets rejected in review. **Which harness** — there are two lanes and they do not mirror each other: a flow in the **shared** `src/` tree owes ONE scenario to the tauri-driver suite in `e2e/` and nothing to the web lane, because it is literally the same code; a **web-specific** behaviour (capability gating, OPFS persistence, the single-tab lock, sync-required entry, crash recovery of the double-buffered blobs) owes a scenario to `e2e-web/`. Do **not** dual-drive the desktop suite against a browser: the premise that lets one suite cover both clients is "same tree, only the seam differs", and that premise is verified by the **seam contract tests** (`tests/platform/seam-contract.ts`, run against every implementation in both CI lanes), not by re-running every tauri-driver scenario file in `e2e/`. `docs/decisions.md` 2026-07-26 "Web E2E policy".

**And it ships with its MANUAL-test verdict**, which is the other half of the same obligation and the
one no compiler and no CI lane can supply. Every desktop E2E scenario runs in a Linux container
against WebKitGTK, so a flow that works there is verified on exactly one of the eight client surfaces the roster
counts (`CLIENTS` in `scripts/check-manual-test-roster.mjs`). One other lane exists, `e2e-web/`,
which drives the web client in Chromium. Between them they reach two of those eight, and no
count is given here on purpose, because this sentence has already been wrong three ways: what
matters is which surface is in which state, and a number invites a reader to trust the arithmetic
instead of the list. `desktop-linux` is covered. `web` is covered on Chromium alone, so its other
engine is not. `cli` and `clipper` have scenarios that the roster leans on by name
(`e2e/cli-thin-client.e2e.ts`, `e2e/clipper-install.e2e.ts`), but both execute only inside that same
Linux container, so what they lack is a second platform rather than a scenario. `desktop-macos`,
`desktop-windows`, `ios` and `android` have no automated UI coverage at all. So a
new file in any of the guard's six denominators (`src/screens/`, `src/components/settings/`, `web/src/screens/`, `web/src/components/settings/`, `mobile/src/app/flows/`, `e2e/*.e2e.ts`) owes a verdict in the
same change, and `scripts/check-manual-test-roster.mjs` fails the commit until it has one. Two
things discharge it and the guard's own message offers both: a roster entry claiming the file, or a
`NOT_A_SURFACE` record carrying the reason it is not a surface. A new `e2e/*.e2e.ts` file is the
third case and it is smaller: it owes a mention in an existing entry's `automatedBy`, not an entry
of its own.

Writing that verdict asks one question, and the answer decides where the work goes: **can a machine
honestly judge this?** If yes, it is not a manual item, it is an `e2e/` scenario you owe, and the
roster records the automation rather than the observation. If no, the entry carries what a human
must SEE and the mechanism that blocks a driver: the runner OS, the WebView engine, a physical
device, an OS event source, a perceptual judgement with a stated pass condition. The guard checks
that with a phrase denylist rather than a vocabulary, so it catches the sentences an author writes
instead of naming a mechanism and not every vague one. The reason it is one-directional is measured
and recorded in the guard's header. myne-md/myne#548.

`pnpm` is the canonical package manager (Tauri's `beforeDevCommand`/`beforeBuildCommand` invoke it). Pinned versions: Node `.nvmrc`, Rust `rust-toolchain.toml`. **Do not bypass the pinning** — CI and reproducible-build rely on it.

JS tests run on **Vitest** (`pnpm test` → `vitest run`; config `vitest.config.ts` — standalone, it does not extend `vite.config.ts` — specs under `tests/**/*.test.{ts,tsx}`). The other lanes have configs of their own, and they live under `.config/vitest/` rather than at the root so the root reads as manifests + docs: `e2e.config.ts` (desktop E2E), `web-e2e.config.ts` (web E2E), `stories.config.ts` (story catalogue), `capture.config.ts` (user-guide screenshots), `ui-pass.config.ts` (per-PR UI screenshots). (Note: `tests/` is outside `tsc`'s `include: ["src"]`, so Vitest is the only check that exercises test files.)

Two jsdom facts worth knowing before designing a test around them, both measured rather than assumed (myne-md/myne#732, 2026-10-15). jsdom keeps `color-mix(...)` and `var(...)` VERBATIM in `style.background`, so a token-derived colour can be asserted as the string the code set rather than as a resolved rgb. And jsdom provides `PointerEvent`, so a press or hover test can render a real element and dispatch real pointer events instead of calling handlers by hand. Both were probed with a five-line script before the spec was written, which is the cheap version of finding out that the whole approach was vacuous.

## Repo guards (what blocks a commit, and what blocks CI)

Most of `scripts/` is not tooling — it is the machine-checked half of the rules this file states in prose. Each guard exists because the failure it catches is invisible to every compiler: a TS string literal that no `match` arm answers, a `std::fs` call that compiles for wasm32 and dies at runtime, a value in the served bundle that should not be there. They are zero-dependency and hand-runnable (`node scripts/<name>.mjs`, `bash scripts/<name>.sh`); every one carries a header comment explaining the failure it prevents, which is the thing to read when it fires.

**This file carries no hand-typed counts, and the guard table below is where that rule comes from.** A number written here has no maintainer: it describes the tree on the day somebody measured it, nothing re-measures it, and it fails silently because the prose keeps reading as authoritative. `check-i18n-coverage.mjs`'s own row records the worked example: two sentences in this repository said the locale set was complete, hundreds of keys were missing from every catalog, and nothing contradicted either sentence for three weeks because nothing measured it. So name the roster, the guard, the command or the path instead, and let a number appear only where the guard itself prints it and a reader is expected to compare against it. **When one here has drifted, delete it rather than correct it**: a corrected number is a fresh promise with the same missing maintainer, and this file's counts have been wrong three separate times (`e2e` files, the scenario floor, the plugin directories) inside the same round that found the drift.

**Verifying a guard means breaking it, not running it.** Every guard above claims to catch something, and a guard that has never failed is a guard nobody has tested. Three consecutive reviews of one feature found a check that passed while the thing it checked was wrong — a matrix compared in one direction while the success line claimed two, a roster compared against a second copy of itself, a filter named in a test title and never exercised. In each case the check had just been *fixed*, and the fix was "verified" by the check passing afterwards, which proves nothing. **Inject the exact defect the guard now claims to catch, watch it name that defect, then restore.** It costs a minute and it is the only evidence that means anything.

**And an anti-drift assertion has to be scoped to the artifact it names.** The failure this catches is one step past the paragraph above, and injection is the only thing that finds it: a test written to hold two copies of a value together, over a file that contains that value TWICE, cannot fail on the drift it exists for. `expect(css).toContain(NEUTRAL_PRESS_BG)` was green while the button's own copy was edited, because an unrelated rule further down the sheet still carried the old string. The fix is to slice the sheet to the rule's own section and assert the value appears there exactly once, and the way to know it is the fix is to inject the drift and watch the test go red: myne-md/myne#732's 2026-10-15 review found this by injection, in the change whose stated thesis was removing one-value-two-places.

**An `#[ignore]` that names a defect is a deferral, and a deferral with no issue is a note.**
`docs/decisions/security/0614-unfixed-security-findings-ship-as-ignored-invariant-tests.md` states
the convention: when a verification pass establishes a security defect whose fix is not available in
the same change, the test asserts the **invariant** and carries `#[ignore = "unfixed: … see
<issue>"]`. `cargo test` stays green; `cargo test -- --ignored` is the standing record of what is
not fixed, and the day the fix lands the test is un-ignored and goes green. Three things follow
that the convention does not state on its own, and all three have been got wrong here:

- **Do not ship a test that asserts the DEFECT and passes.** It certifies the defect as intended
  behaviour, so every fix is gated on rewriting the test that documents it, and the first person
  to fix it concludes they broke something. That shape is a regression to the *previous* state of
  this file, and review caught it.
- **The reason must name an issue that is still OPEN.** Pointed at the issue the change closes, it
  reads on merge as an oversight rather than a deferral. `scripts/check-ignored-tests.mjs` holds
  that, and the roster, and the "says what is missing" half.
- **A right direction is not a working fixture.** A test whose fixture cannot reach the defective
  state passes with the defect present, which reads as rigor. The Tag-block carve-out in
  `core/src/plugins/memory/commands.rs` shipped that way twice: the fixtures spelled England's flag
  as `gb` and Wales' as `wls`, and the "smuggled payload" case put its payload in plain ASCII so a
  different arm caught it. Only injection tells the two apart.

**A guard that WRITES its own record has a second half nobody verifies: the seeding path.**
`--record` and `--emit` exist so a ratchet can be re-baselined, and the entry they write has to be
rejected by the same guard until a human replaces it. `check-ipc-binding-callers.mjs` seeded every
fresh entry with the string `REASON REQUIRED`, and its reason check rejected anything under twelve
characters. That string is fifteen. So the tool's own placeholder passed the tool's own gate, seven
entries sat in the record saying in words that their reason was missing, and the tree was green.
Nothing catches this: injecting the defect the guard checks FOR still passes, because the defect is
in the half that writes rather than the half that reads. Ask the other question instead: run
`--record` on a dirty tree and check that the guard then FAILS. A re-baseline that comes back green
is a re-baseline that licensed everything it found.

**Editing a guard is one of those changes, and the exemption logic is where it bites.** A guard fix
verified by "the tree is still green afterwards" is the same non-evidence as any other, because a
guard that has stopped checking is green by definition. myne-md/myne#411 corrected
`check-core-io-seam.mjs`'s `#[cfg(test)]` tracker, ran the tree, saw green, and shipped a version
that reported nothing for a production `std::fs::read` the pre-fix guard caught: closing one blind
spot opened another, one line away. Both directions have to be injected, and the second one is the
one nobody thinks to try: prove the guard still catches what it caught BEFORE, not only what it
missed.

- **`cargo check --no-default-features` never compiles test code, so the AI-free gate is blind to a
  dead-code break in a test-only helper.** `cargo check` without `--all-targets` skips `#[cfg(test)]`
  entirely, so a helper gated `#[cfg(test)]` whose only caller sits behind a feature is dead when that
  feature is off, and only a `--all-targets` clippy sees it. myne-md/myne#510 shipped exactly that for
  one review round, because the `--no-default-features` gate in `.woodpecker/main.yml` was a bare
  `cargo check`. The same change closed it: that step now also runs
  `cargo clippy -p myne-desktop --all-targets --no-default-features -- -D warnings`, so CI covers this
  and there is nothing left to run by hand. The paragraph is kept rather than deleted because the
  REASON is what generalises: any gate spelled `check` rather than `clippy --all-targets` is blind to
  the test tree, and this repository has more than one.
  Gate such a helper on the FEATURE its caller needs rather than on `cfg(test)`, and run that clippy
  line by hand when a change adds one. Gating on the feature has a second payoff: the caller can then
  leave the test module, so a `const _: () = assert!(...)` comparing two duplicated constants runs on
  every build rather than only under `cargo test`.

**A fixture that cannot hold the defective state is not a test, and injection alone does not
catch that.** The rule above says to inject the defect and watch the guard name it. That leaves one
way for a test to be vacuous and still look rigorous: the injection lands, the test passes anyway,
and the reason is that the fixture never reached the state the defect needs. myne-md/myne#613 shipped
it twice in one afternoon, in tests written for the same finding. The first built its fixture by
running the FIXED code, so the over-cap blob the defect requires was never constructed. The second
asserted the invariant directly, but on a view that starts EMPTY, where the term the injection
removes is zero by definition, so the injected line was never consulted. Both passed with the fix
reverted. The question to ask of a fixture is not "does this exercise the code" but "could this
input be wrong in the way the code is meant to prevent", and only the injection answers it: a
revert-and-run that STILL passes is the finding, not a formality to tick.

- **`String.replace`'s replacement STRING expands `$1`, `$&`, `` $` `` and `$$` — which defeats a quote sanitizer placed before it.** A theme value of `$1 onload=…` filtered clean of `["'<>]` still expanded to the captured group, whose own quote closed the attribute it was being interpolated into and landed a live event handler. `$` cannot be filtered (a legitimate CSS value may contain one), so the fix is a replacer **function**, to which no `$` sequence means anything. Any `replace(re, `…${untrusted}…`)` has this shape; `myne-themes/tools/render-preview.mjs` carries the worked example.
- **`git add -N` to widen a diff leaves a zero-byte index entry behind, and deleting the file does not clear it.** Intent-to-add is how you get new files into `git diff HEAD` so a review or a guard can see them, and it is the right tool for that. What it also does is stage an empty blob (`e69de29`) for each path. Delete or rename such a file afterwards and the entry survives in the index while `git status` shows only ` D`, so a plain `git commit` lands an empty file named after work that moved elsewhere, and `git diff HEAD` shows neither the path nor the problem. The mirror-image failure costs more: a file created AFTER the `add -N` is untracked, so it is absent from that same diff, and a commit lands the imports that reference it without the module itself, with `pre-commit`'s `tsc` green because it reads the working copy rather than the index. Both shapes landed together on one branch. `git ls-files --stage | grep e69de29` finds the first, `git status --porcelain | grep '^??'` the second, and both are worth a look before any commit that followed an `add -N`.
- **A cancelled subagent leaves the tree exactly as dirty as its last command, and a reviewer that ran an injection leaves it reverted.** `/pr-review` reviewers are told to prove a finding by injecting the defect and restoring it, and a reviewer that is cancelled mid-experiment (the batch was killed to save wall clock on a long review) never gets to the restore. What is left is a file reverted to the pre-fix state, with every test that measured the fix still green in the report because they were measured before the cancel, and nothing in the working tree saying so: `git status` shows the file as modified, which is what it looked like when the reviewer started. The dimension reviewers caught it here (both `mountZoom` call sites reading as still on the old wheel mode, against a source file the session had edited an hour earlier), but only because the tree happened to be read fresh rather than trusted. Two cheap habits close the class: after any cancelled or interrupted subagent, `git diff` the files that reviewer was pointed at before believing any green result, and let `/done` Gate 2's read of the staged diff be the last word on what the commit contains. The lesson generalises past reviewers: any subagent permitted to edit the shared tree is permitted to be interrupted mid-write, and "the tests passed" is a claim about a moment, not about the bytes that get committed.

  ordinary CSS. When a component gains a second mount shape, mount the scoping element in it too (a
  plain wrapper) or re-scope the rules onto a class the new shape does carry, and assert the wrapper

- **A sink that resolves on a refused write makes the surface above it lie, and the lie compounds.**

  behaviour the review then removed), which is right
  for a checkbox (a box that does not move is self evident) and wrong for a field editor: the
  surface above it holds its own copy of the line so that a second edit in the same session can pass
  the writer a line that still matches disk, and the swallowed refusal made that copy advance to
  bytes that were never written. The menu then showed "Edit due date" for a field the note did not
  carry, and every later edit in it was refused `line-changed` and swallowed in turn. Two rules
  follow. A refusal is not an error to be silenced at the boundary; if the surface needs to know, the
  boundary must let it through (the wizard's own commit handler catches it, so nothing escapes as an
  unhandled rejection). And a surface that keeps a local copy of remote state owes it a way to learn
  that the write did not land, or it will report a value nobody can find on disk.

These name bytes on disk today: `docs/spec/protocol.md` §10.3.1 makes v0.2 the birth format and §10.4.1 has the migration write all of them except `MYO5` and `MYU5`, which are the two `NTV6`-only families and are created by their first write rather than by that cut (an absent file reads as the empty map in both), so reading one as an unallocated placeholder is the mental model behind myne-md/myne#638, where a reader taught only `MYA1` returned `None` for every body on a migrated vault and stopped attachment sync in both directions. **Genuinely still reserved**: `NT05` (per-note; what it now means beside `NC05` is deliberately unanswered, `protocol.md` §10.3) + `MYS5`/`MYW5`/`MYI5`/`MYB5`/`MYQ5`/`MYE5`/`MYH5`/`MYK5`/`MYG5`/`MYF5`/`MYL5` (search / workspace / vault-indices / backup-container / quick-unlock / attachment-text / sync-baseline / pending-capture / graph-layout / share-import / sealed-label-store): placeholder values the next major version finalizes. `MYR5` is no longer among them: the AI-embeddings family was retired (`docs/decisions/ai/0703-*.md`), which returned `R` to the free `MY?5` letter pool. `MYL5` is reserved against a future revision of its own family's layout, not against a version cut: `vault.label` is generation-independent and stays `MYL1` inside a v0.2 vault (`protocol.md` §9.22, §10.3). The `MY?5` letter pool held exactly two free letters at the allocation that minted `MYO5` and `MYU5` (`O` and `U`), so a later family wanting one needed a human decision; the retirement of the AI-embeddings family has since returned `R` to the pool.

**One next-major family is no longer a placeholder: `NC05` is allocated as a v0.2 format** (the CRDT note-type, `automerge-sync-migration` #418; `docs/decisions.md` 2026-08-09 format-commitment entry). It pins **three new load-bearing v0.2 identifiers** — AAD prefix `"myne.v0.2|"`, HKDF context prefix `"myne.v0.2 "`, header `protocol_version` byte `0x02` — plus the `NC05` per-note magic. Each is a major-version-event constant exactly like its v0.1 counterpart; the byte layout is normative in `docs/spec/protocol.md` §10.7 (an `NC05` blob is the §9.2 envelope with magic/version/AAD-prefix swapped, opaque Automerge `save()` payload, no new `SubkeyRole`). Pulling these two prefixes forward is the one exception to "the next major's prefixes are not pre-allocated"; the rest of v0.2 (its KDF, other blob families) is still unallocated.

The next major's **AAD prefix and HKDF context prefix are otherwise not pre-allocated** in v0.1 (it defines its own; the v0.1 values `"myne.v0.1|"` / `"myne.v0.1 "` are untouched, and only the `"myne.v0.2 …"` note-type prefixes above are pinned) — see the normative magic-allocation table in `docs/spec/protocol.md` §10.3 (which is the single source of truth for magic allocation; `MYI1`/§9.8 VaultIndices landed with MYND-271). v0.1 and a later major version are **forward-incompatible by design** — no extension points, no algorithm-agility headers; cross-major reads happen only via explicit user-initiated migration. (The next major was formerly drafted as "v005"; that codename is retired — see `docs/decisions.md` 2026-08-01 and the glossary "next major version" entry. In prose, deferrals read as "later"; parked items as "icebox".)
