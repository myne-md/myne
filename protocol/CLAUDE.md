## Subkey derivation discipline (LOAD-BEARING)

All subkey derivations MUST go through the canonical helper:

```rust
pub fn derive_subkey(root_key: &[u8; 32], role: SubkeyRole) -> Zeroizing<[u8; 32]>
```

The helper constructs `info = "myne.v0.1 " || role` from the registered `SubkeyRole` enum (matches `protocol.md` §3.4); the output is `Zeroizing` so callers deref (`*subkey`) rather than owning a bare array. The underlying `hkdf::Hkdf::expand` call is **module-private** — `subkey.rs::derive_with_context` is `pub(crate)`.

**Code review must reject any direct call to `hkdf.expand` outside this helper.** This recovers the structural API guarantee that BLAKE3's `derive_key` would have offered natively. Outside the crate the guarantee is **structural, not linted**: `hkdf` is never `pub use`d from `lib.rs`, so `derive_subkey` + `SubkeyRole` are the only reachable path. Inside the crate, review is the only backstop — there is no clippy lint and no grep guard.

Adding a role is gated the same way, by compilation rather than by memory: a new `SubkeyRole` variant fails to compile in `subkey.rs` (`all_covers_every_registered_role`) until it is listed in `SubkeyRole::ALL`, then fails `--test vectors` until it has a companion-repo vector.

**Why it matters:** an ad-hoc `info` string that drifts from the registered role table silently produces a different subkey, but the AEAD tag check might still pass with another caller's wrong-key blob. The only defense is making it impossible to construct an `info` outside the registry.

## `_raw` suffix convention (caller-supplied randomness)

Public functions in this crate that accept caller-supplied nonces, item keys, or other randomness — rather than pulling from `getrandom` internally — carry a `_raw` suffix. Three properties travel with that suffix at every call site:

1. **Caller sources all randomness from a CSPRNG-grade source.** Passing low-entropy or attacker-influenced bytes to a `_raw` function is a security-fatal contract violation owned by the caller, not by the crate.
2. **Nonce reuse is catastrophic and is the caller's contract.** The crate cannot detect cross-call nonce collisions; the suffix is the visible reminder that the caller is on the hook.
3. **Legitimate consumers are well-defined.** `_raw` functions exist for the `myne-test-vectors/` companion (byte-level cross-implementation vector generation) and for crate-internal deterministic tampering / golden tests. Production callers SHOULD use the non-`_raw` convenience wrapper that pulls randomness internally.

A code reviewer seeing a production import of a `_raw` function from outside this crate has a clear reason to question the change. The convention is greenfield-applied — first instance is `blob.rs` (MYND-25). Backporting to existing functions that match the property (e.g., `aead.rs::aead_seal_ctx`) is a separate decision, not implicit. See `decisions.md` 2026-05-06 entry for the full rationale.

## AAD helper naming discipline (`vault_` / `note_` prefix)

AAD-builder functions in `aead.rs` are prefixed with `vault_` (vault-singleton context) or `note_` (per-note context) to retire a one-letter near-collision footgun: spec §5.2 distinguishes `AAD_wrap_items_key` (singleton itemsKey wrap, no per-note UUID) from `AAD_wrap_item_key` (per-note item_key wrap, with note_uuid). The `items_key` / `item_key` token pair differs by a single trailing `s` — visually indistinguishable at a glance, type-confusable in import statements, and historically a documented hazard class for crypto code (the kind of footgun the subkey discipline rule above exists to prevent at the subkey level).

The discipline:

- `aad_vault_*_wrap` → AAD for an AEAD operation in the vault-singleton scope (e.g., `aad_vault_items_key_wrap` wraps the singleton `itemsKey` under `itemsKey_wrap_key`).
- `aad_note_*_*` → AAD for an AEAD operation in the per-note scope (e.g., `aad_note_item_key_wrap` wraps a per-note `item_key` under `itemsKey`; `aad_note_content_encrypt` encrypts note content under `item_key`).

The three-letter `vault_` / `note_` prefix is visible at a glance in any import or call-site — same defense shape as the subkey-derivation single-helper rule, applied at the AAD-builder layer. This discipline replaces the earlier `aad_items_key_wrap` (singleton-only) name at MYND-25; the rename is recorded in `decisions.md` 2026-05-06 entries that pin the per-note codec design.

**Code review must reject** any new AAD-builder function whose name relies on a one-character distinction (e.g., `aad_item_key_wrap` next to `aad_items_key_wrap`); collapse to the prefix-disambiguated form.

Variable `ciphertext_len` with a 16 KiB plaintext cap → `CiphertextLenOverflow` (contrast MYQ1's fixed 64 → `CiphertextLenInvalid`). 11 cases (2 encrypt / 1 decrypt_ok / 3 decrypt_aead_fail incl. cross-`capture_id` / 5 parse_fail). NOT re-exported at the crate root — the runner imports via `protocol::capture_blob::*`. Generator: `emit_capture_blob_vectors_for_paste` (`capture_blob.rs`); runner `pending_capture_vectors`.
- `vectors/saved-view/` + `vectors/paired-extension/` — the two canonical-JSON **array decoders** embedded in `vault.prefs` (§9.5.2): `parse_saved_views_array` (`saved_view.rs`) and `parse_paired_extensions_array` (`paired_extension.rs`). Both are deterministic pure functions `&[u8] → (Vec<T>, consumed)`; the vectors pin `parse_ok` (the decoded set as its canonical re-encoding via `canonical_encode_saved_views` / `canonical_encode_paired_extensions` — NFC fold + key order + sort + unknown-field drop — plus the `consumed` cursor-advance count) and `parse_fail` (the closed error surface). Generators: `emit_saved_view_vectors_for_paste` / `emit_paired_extension_vectors_for_paste`; runners: `saved_view_vectors` / `paired_extension_vectors`. These closed the two deterministic-but-unvectored prefs-embedded parse surfaces (the bytes are decoded only after the `vault.prefs` AEAD verified, so they sit in the `note-template` non-codec class).

- `vectors/vault-themes/` (MYND-486: `MYT1` `themes_blob.rs` codec, §9.21) + `vectors/vault-head-state/` (`MYH1` `vault_head.rs` baseline envelope, §9.16) + the `embeddings` runner + the four missing `hkdf-sha256` roles + `aad_custom_themes_blob` — the 2026-07-26 registry audit. Two shapes of gap: a generator that existed but whose output was never pasted into the companion repo (`vault-themes`), and vectors that existed but which no runner read (`embeddings`). **The structural fix matters more than the vectors**: `hkdf_sha256_vectors` now iterates [`SubkeyRole::ALL`](src/subkey.rs) instead of restating the registry as a string literal — the old hand-maintained list had fallen four roles behind (`vault-head-mac`, `server-auth`, `custom-themes-key`, `themes-sync-id` were all deriving in production with no cross-impl vector) while still *reading* as exhaustive. Adding a `SubkeyRole` variant now fails to compile in `subkey.rs` (`all_covers_every_registered_role`) until it lands in `ALL`, then fails `--test vectors` until it has a companion-repo case. The `aad-construction` / `ctx-aead` builder lists stay literal (they name functions, not enum variants) but now carry explicit rationale for each exclusion — `aad_capture_blob` / `aad_share_import_blob` are device-local and vault-agnostic, so "absent" reads as *by design* rather than *by omission*. `MYH1` is the only §10.3 family that is not AEAD-encrypted, so `vault-head-state` pins a `mac_fail` case kind where its siblings pin `decrypt_aead_fail`. Generators: `emit_themes_blob_vectors_for_paste` (`themes_blob.rs`), `emit_head_state_vectors_for_paste` (`vault_head.rs`, self-asserting at mint).

- `vectors/vault-label/` (myne-md/myne#411: `MYL1` `vault_label_blob.rs` codec, §9.22). The `embeddings` shape again. The companion repo carried 18 cases and **nothing in this repo read them**, so a codec edit would have broken byte parity with no test noticing, which is precisely the failure the vectors exist to prevent. Closed with the standard four edits: generator `emit_vault_label_blob_vectors_for_paste` (`vault_label_blob.rs`, self-asserting at mint: its output is byte-identical to the committed `cases.json`, which is also the evidence the two sides agree), runner `vault_label_vectors`, and the `mod embedded` row. Six case kinds rather than the device-local four, and the two extras are the family's two divergences from `MYK1`/`MYF1`: `encode_fail` for the write-side 4 KiB cap refusal (paired with an at-cap `encrypt` case, which is what pins the boundary as inclusive rather than off by one), and `aad_construction` for `aad_vault_label_blob`, which is device-local and therefore outside the vault-scoped `ctx-aead` / `aad-construction` enumeration families, so it is pinned inside its own family exactly as `MYK1` and `MYF1` pin theirs. `parse_fail` covers all **7** decode variants including two no sibling has: `vault_id_mismatch` (the AAD binds the `VaultId` the READER expected) and `trailing_bytes` (§10.3.1 strict-trailing is enforced here, not inherited leniently). The runner additionally **derives** the cross-vault split from the `vault_id_mismatch` fixture (relabel its header to the expected id and, under that fixture's own real `wrap_key`, the outcome must move from `VaultIdMismatch` to `CannotDecrypt`), so the "these two MUST differ" MUST is a claim about the codec rather than about two case files agreeing with each other.

- Categories that never got a bullet here because they landed **with** their code rather than as retroactive debt — listed so this log stops reading as the registry it is not: `vectors/attachment-text/` (`MYE1`, §9.15; generator `emit_attachment_text_vectors_for_paste`), `vectors/graph-layout/` (`MYG1`, §9.19; `emit_graph_layout_vectors_for_paste`), `vectors/share-import/` (`MYF1`, §9.20; `emit_share_import_blob_vectors_for_paste`), `vectors/manifest/` (`sync-protocol.md` §4.2 `manifest_hash` input; `emit_manifest_vectors_for_paste` — the manifest is computed **client-side only**, so these vectors bind client ports to each other and the absent Go runner is not a coverage gap), `vectors/scram-auth/` (`scram.rs` client proof + server signature — the one family whose counterpart really is the Go server's `internal/auth/scram`), `vectors/head-fingerprint/` (`head_fingerprint`, `vault_head.rs` — the human-readable head-id rendering), `vectors/damm32-table/` (the frozen quasigroup table, `account_number.rs`; `emit_damm32_table_vectors_for_paste`), `vectors/phrase_normalize/` (NFKD phrase normalization, `phrase.rs::normalize_user_phrase`), `vectors/color-group/` (the `color_groups` canonical-JSON array decoder, `color_group.rs`; `emit_color_group_vectors_for_paste`), `vectors/tls-exporter/` (the two frozen RFC 9266 §3 exporter parameters — **no generator by design**, and its runner is the one outside this crate, `core/src/plugins/sync/enroll.rs::tls_exporter_vectors`), and the three TS-runner task categories `vectors/task-inline-format/` · `vectors/task-recurrence/` · `vectors/task-query-grammar/` (`tests/dialect/taskVectors.test.ts`, regenerated by `GEN_TASK_VECTORS=1`). **The registry is `tests/vectors.rs`**, not this log — one runner per category, and the browser lane's embedded table has to name the same set (see "Two lanes" below).

**All cross-impl-relevant deterministic surfaces are now vectored.** The remaining unvectored public functions are randomized (`generate_account_number`, `generate_recovery_phrase`), `getrandom`-pulling convenience wrappers — **every `encode_*` that has a `_raw` sibling**, which today means `encode_new_note` + `encode_update` plus one per blob family (prefs, search, workspace, vault-indices, attachment, attachments-catalog, dictionary, quick-unlock, attachment-text, embeddings, themes, graph-layout, share-import, pending-capture) — whose deterministic `_raw` siblings carry the contract, or host-policy conveniences (`read_or_empty` — call-site fallback over the vectored catalog codec).

When you change a primitive: regenerate the relevant vector file in the companion repo and bump it in the same PR.

**Adding a *category* is four edits, not three.** (1) a generator — an `emit_*_for_paste` test in the owning module for most families, though a few (`scram-auth`, `phrase_normalize`, `head-fingerprint`) carry no `emit_*` in this crate at all, (2) the emitted `cases.json` pasted into `myne-test-vectors/`, (3) a runner in `tests/vectors.rs` — and (4) a `(category, version, include_str!(…))` row for it in that file's `mod embedded` table. Skipping (4) does not degrade to a skip: `cases_json_for` **panics** in the browser lane ("no embedded fixture … has fallen behind the runners"), deliberately, because natively a missing fixture means "companion not checked out" while in a browser it can only mean the table drifted. `the_browser_lane_carries_every_category` covers the other direction — a table row left behind after a runner was renamed or removed.

**The row's key carries the version, and dropping it is a silent-wrong-answer bug rather than a skip.** The table was keyed by category name alone while `crdt-note-blob` was the only next-major family; that stopped being safe when `vault-meta` and `vault-themes` landed a `v0.2/` beside their `v0.1/`, because a name-keyed lookup handed both v0.2 runners their v0.1 bytes — real, well-formed, schema-valid vectors for the wrong version. A name-keyed table could not have carried both rows anyway (the duplicate check forbids it). So the third assertion in `the_browser_lane_carries_every_category` reads `schema` + `protocol_version` back out of each row's bytes and compares them to that row's key: the key is hand-written and the `include_str!` path beside it is hand-written, so the two can disagree, and this is what notices. It replaced a hardcoded row count that had drifted two rows behind reality without anyone noticing — because nothing runs this lane in CI (see below), a count nobody executes is not a guard.

**Two lanes, one source.** The same `tests/vectors.rs` also compiles for wasm32: `wasm_bindgen_test_configure!(run_in_browser)` puts those runners inside a real browser's wasm engine, with the fixtures baked in at compile time behind the **`browser-vectors`** Cargo feature. That feature is OFF by default and must stay off — the arm it enables is a table of `include_str!`s into the companion repo, and `include_str!` of an absent file is a *compile error*, not a skip, so a contributor without the companion has to be able to build these tests without it. `scripts/browser-vectors.sh` supplies the driver and the fixtures (headless Chrome; `CHROMEDRIVER=…` to override). Unlike the native lane it **fails** rather than skips when either is missing, and `the_browser_lane_actually_has_fixtures` fails a run that forgot `--features browser-vectors` — a lane that skipped every runner would otherwise report green having asserted nothing. Why bother: cross-implementation agreement is a property of compiled code *on its execution target*, and the web client's target is a wasm engine no amount of native green speaks for. This does **not** contradict the `getrandom` gotcha below: `wasm-bindgen-test` is a wasm-only **dev**-dependency, so it never appears in the `cargo tree -e normal` graph `scripts/wasm-csprng-check.sh` inspects — and the test binary, being a root artifact, registers a `getrandom` hook of its own that deliberately *refuses*, since every byte of a vector run comes from the fixture and a runner reaching for entropy is testing the wrong thing.

CI's `vector-verification` step (`.woodpecker.yml`) runs both lanes, but is **commented out** as of 2026-07-29 (MYND-635): it references a `vectors_token` secret this repo does not yet have, and a `from_secret:` naming an absent secret fails config-compile, which kills *every* step in the pipeline rather than just this one. Re-enabling is a two-part change whose first half is not in git — provision the secret, confirm a pipeline still compiles, then uncomment. Until then the gate is local, with the companion checked out.

## Gotchas

- **`getrandom` on wasm32 uses the `custom` backend, NOT `js`.** wasm32 is now a supported target of this crate (`phase3-web-client` task 9): `[target.'cfg(target_arch = "wasm32")'.dependencies]` enables `getrandom`'s **`custom`** feature. Do **not** switch it to `js` — `js` pulls **wasm-bindgen** and a codegen step into a `#![no_std]` primitive crate, and `scripts/wasm-csprng-check.sh` fails the build if wasm-bindgen appears in this crate's wasm graph. **`custom` is not self-sufficient**: it declares an `extern "Rust"` hook (`__getrandom_custom`) that the **embedder** must register. That registration lives in exactly one file — **`web/wasm/src/csprng.rs`** (`register_custom_getrandom!(fill_from_web_crypto)` → `globalThis.crypto.getRandomValues`, task 81) — and it can only live there: getrandom requires it in the **root cdylib** crate, which `myne-web-wasm` is. Unregistered, the symbol stays undefined and the final wasm link fails with `rust-lld: … undefined symbol: __getrandom_custom` — verified by deleting the macro call and rebuilding, not assumed. The trap that protects against: an **rlib** link never resolves undefined symbols, so `cargo build --target wasm32-unknown-unknown` of this crate alone passes with **no entropy source at all**. "wasm32 builds green" is therefore not evidence the randomness path works; `scripts/wasm-csprng-check.sh`'s symbol-level check is, and the entry crate's `csprng_self_check()` startup gate is what proves the registered backend also *answers* at runtime rather than merely linking.
- **Argon2id memory cost is 256 MiB.** Tests that exercise it need extra heap; CI runners must have ≥1 GiB free or tests panic. For unit tests that don't care about real KDF strength, use a test-only fixture with `m=8 KiB, t=1, p=1` — never check that fixture into a production code path.
- **Nonce reuse is catastrophic** — `getrandom` is the only acceptable source for nonces in v0.1. There is no counter-mode fallback.
- **CTX commitment ≠ Poly1305 tag.** On disk we store the 32-byte SHA-256 outer; the Poly1305 tag is recomputed at decrypt and discarded. Don't expose the bare Poly1305 tag in any public type.
- **Adding a `PrefsView` field is four edits, and the parser is positional.** `prefs.rs` hand-rolls a canonical-JSON codec that walks keys in canonical order via a monotonic forward cursor — and its blocks are **not** in canonical order in the source file, so reading top-to-bottom puts your insertion in the wrong place (a first attempt at `attachment_ocr_enabled` landed ~60 lines early, in the `archive_disabled` block). Locate the site by its chain variable (`post_<preceding-key>`), never by reading order. **A `None =>` arm must return its own block's predecessor cursor, and rewinding further back is safe only when every field AFTER the block is located by search (`find_top_level_marker`, via `parse_optional_*_field`) rather than by `strip_prefix`.** Two arms rewind legitimately — `ai_provider`'s and `auto_lock_seconds`'s, both to `post_ai_excluded` — because only search-located fields follow them. The `archive_disabled` arm is *not* in that class: `archived_folders`, `attachment_compression_enabled`, `attachment_ocr_enabled` and `auto_lock_seconds` all `strip_prefix`, so an early start makes all four miss and silently take their defaults. It shipped rewound one block too far when `ai_provider_model` landed, and the round-trip test written to catch it passed anyway because it left every following field absent (see `the_model_does_not_swallow_the_preferences_that_follow_it`). Then: the destructure, the **separate `ALL_FIELDS` list** the conformance test counts (updating only the destructure still fails), and the ~27 deliberately-exhaustive struct literals across `protocol` and `myne-core` tests — they are exhaustive as a drift lock, so backfill them rather than reaching for `..Default::default()`.
- **Bumping a version constant silently inverts the tests that used the next value as "the future".** `extractor_version` `0x02`→`0x03` turned two rejection tests into false negatives, because both asserted that `0x03` is rejected. Grep `0x0` in the touched files after any bump. The same shape bites when a format graduates from unsupported to supported: a test using `image/png` as the archetypal unsupported MIME type stopped testing anything the moment PNG started dispatching (moved to `application/zip`).
