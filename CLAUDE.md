# CLAUDE.md

Guidance to Claude Code (claude.ai/code) when working in this repository.

Subdirectory CLAUDE.md files cover their own domain in depth — they lazy-load when Claude reads files there:
- `src-tauri/CLAUDE.md` — Tauri 2 host, capability ACL, plugin pattern, Windows lib-name quirk
- `core/CLAUDE.md` — `myne-core`, the shared backend crate: the host/IO/task seams, the lifecycle-hooks seam, plugin-core layout, three-layer command shape
- `protocol/CLAUDE.md` — RustCrypto primitives, subkey derivation discipline, vector-verification
- `src/CLAUDE.md` — React UI patterns, design tokens, mock-layer status
- `docs/CLAUDE.md` — spec authoring rules (decisions.md append-only, glossary discipline)
- `e2e/CLAUDE.md` — tauri-driver desktop harness, scenario authoring rules, the green-3×-consecutive gate
- `e2e-web/CLAUDE.md` — browser web-E2E lane: what belongs in it and what does not
- `agent-tooling/CLAUDE.md` — agent + skill + feature/session/plan layout

## Design context (pointer)

Three files at the repo root carry the visual + strategic system. Read in this order before designing any UI:

1. `PRODUCT.md` — strategy: register, users, voice, brand personality, anti-references, design principles. Cross-client (desktop + future mobile + web). Read before any new screen.
2. `DESIGN.md` + `DESIGN.json` — visual system in [Google Stitch DESIGN.md format](https://stitch.withgoogle.com/docs/design-md/format/). Frontmatter is the machine-readable token layer; `DESIGN.json` carries the live-panel components, tonal ramps, shadow + motion + focus extensions.
3. `docs/design/` — **the design canon itself**: `README.md` (voice + tactical rules), `colors_and_type.css` (the CSS-variable source — the binding values), `ui_kits/desktop/` (JSX primitives), `preview/` (token specimen tabs).

**The design canon lives in this repository.** There is no external design file that outranks it — `docs/design/` is canonical, `DESIGN.md`/`DESIGN.json` are its machine-readable projection (where the two disagree, the CSS is the value and `DESIGN.md` gets corrected), and `src/` is the implementation, binding to CSS variables rather than literals (`check-token-adoption.mjs` is the ratchet). When a shipped screen and the canon disagree, decide which side is wrong **on the merits** — fix the drifted screen, or update `docs/design/` in the same change when the screen genuinely improved on the system. Leaving the two silently disagreeing is the one option that is never right.

`/impeccable` commands (craft, polish, audit, etc.) read `PRODUCT.md` + `DESIGN.md` automatically. Do not duplicate their content into other docs.

## Session output convention (pointer)

Every Claude Code session in this repo loads `.claude/skills/adhd/SKILL.md` at start, injected by the checked-in SessionStart hook `.claude/hooks/adhd.mjs --session`, together with `.claude/skills/diverge/SKILL.md`, and the same file in `--turn` mode, wired as a UserPromptSubmit hook, re-injects a compact restatement of both on **every** turn (all wired in `.claude/settings.json`). The pair is deliberate: `adhd` shapes how an answer is written, `diverge` shapes how it is arrived at, and the first without the second yields well-shaped first drafts of the obvious answer. The second layer exists because the first decays: in a long session the start-of-session injection sits further back, survives compaction only as a summary, and the shape quietly stops being applied without anything reporting it. It shapes *how* answers are written — action first, numbered steps, state restated each turn, no preamble/recap/closers — and never what they are allowed to claim: security, crypto, spec and data-loss content is exempt from every brevity rule, and each artefact-producing skill (`/grill-me`, `/pr-review`, `/summarize`, …) keeps its own format. Read the skill for the full list of where the shape yields.

**The turn injection carries a third block that is not about shape**, `WORK DISCIPLINE`: when the turn changed a repository, it names the tail (`/simplify`, `/pr-review`, `/done`) from the lane in "How work runs here" below. It is a separate block rather than a clause inside a shape rule, and it rides in the hook rather than in prose because the hook is re-injected at the submit of **every** turn, so it is in context for the turn that makes the change and is still there when that turn writes its closing line. Prose in this file is read once at session start and sits further back with every turn after it. The measurement behind that placement is in `.claude/hooks/adhd.mjs`.

On by default and per-clone opt-out: `touch .claude/.adhd-off` (gitignored), `MYNE_ADHD_OFF=1` for one invocation, or "stop adhd mode" mid-session. The hook is a no-op when `CI` is set, so the unattended lanes — Woodpecker, the runner jail, the issue-triage and PR-review bots — keep their fixed-format English output.

## How work runs here (pointer)

**Every change to a repository runs on the same lane, whatever the request looked like.** A session
that started from `/grill-me` and a session that started from a one-line "fix this" owe the identical
five things. This section exists because the rules behind them live in `agent-tooling/reference/`, and
those files are read only through a skill's standing-obligations block: a session that invokes no
skill reads none of them, which is exactly the session that then skips them. This file is loaded for
every session in this tree, so the lane is stated here and the mechanics stay there.

1. **No issue, no work.** Work that changes a repository binds to a tracked issue
   (`issue: myne-md/<repo>#<n>`), and when none exists the first action is to file one through the
   `issue-pm` subagent. The only exception is the user saying "no issue for this" in so many words:
   silence is not it, and neither is "this is tiny". Reading, explaining, reviewing, researching and
   answering a question are outside the gate, since none of them change anything. Move the issue to
   `status: in progress` through `issue-pm` when you start: on this lane nothing else will, because
   that transition belongs to `/do-work` and this lane skips it, so the issue would jump from
   `triage` straight to `ready to test` and no second session would ever see it as taken.
   `agent-tooling/reference/github-issues.md`.
2. **A session that changes a repository works in a worktree of it, never in the shared checkout.**
   The section below is that rule in full, including where a worktree lives and what it branches from.
3. **The planning front-half is sized, the tail is not.** Work that is large, contested or unclear
   goes `/grill-me` then `/write-a-prd` then `/prd-to-tasks` then `/do-work`, which produces the
   artefacts under `agent-tooling/features/<feat>/`. Work that is small and already understood skips
   those four and is implemented directly. **Size is measured in consequence, not in lines**: a
   change touching cryptography, the on-disk format, sync, a capability ACL, an egress allowlist, or
   any guarantee `docs/threat-model.md` states is never small, however short the diff, because the
   threat model changes in the same PR and a design step is the only place that ordering can be
   enforced. And skipping the front half discharges none of the standing obligations: a protocol
   change still ships with its `myne-test-vectors` change, a user-facing change with its
   `myne-website` user-guide PR (`agent-tooling/reference/github-issues.md`).
4. **The tail is `/simplify`, then `/pr-review`, then `/done`.** `/done` is the only committer and
   the only PR-opener, in every repo the work touched. A branch with commits on it and no PR is
   unfinished work, not finished work, and so is a clean checklist. `/pr-review` and `/done` both run
   against a plain branch with no feature directory, so ad-hoc work owes the same tail.
5. **Something coupled to the work in hand is fixed in the branch you are already in**, not filed as
   a new issue, and coupling decides that rather than size. Work that turns out to be genuinely
   distinct is the user's call: ask once, and never file without their answer. Two things always
   leave the branch instead, a legal or policy requirement (a `operations` issue, and change nothing)
   and a decision the user owns, such as the threat model, the on-disk format, an anti-feature or a
   spec reversal (stop and ask). The full table, including what an unattended run does with a
   distinct discovery, is in `agent-tooling/reference/github-issues.md`, "A discovery is implemented,
   not filed".

## Worktrees (pointer)

**Every session that changes this repository works in a worktree of it, unless the user says
otherwise.** Not the shared checkout, not "just this one file". That checkout's branch belongs to
every session sitting in the directory, so switching it puts their next commit on your branch, and
committing from it lands your work on whatever branch the last session left it on. The shared
checkout stays on the default branch and is for reading.

A worktree for this repo is created **only** with `EnterWorktree`, or with `git worktree add` into
`.claude/worktrees/<name>`, and never anywhere else. It branches from **`origin/develop`**, always:
that is what `worktree.baseRef: fresh` in `.claude/settings.json` pins (the setting is checked in so
a fresh clone inherits it), and a hand-made `git worktree add` passes `origin/develop` explicitly.
Branching from the current local HEAD instead carries whatever the working checkout happens to be
sitting on into the new branch, which is how a feature branch picks up an unrelated half-finished
change and a PR arrives with a diff nobody can explain. The session scratchpad under `/private/tmp` is
specifically wrong for one: it is per session and gets cleaned, so the worktree outlives the
directory `git worktree list` still points at, and `.claude/worktrees/` stops being the roster of
what is in flight. Name it after the issue (`410-note-covers`) so the worktree, the branch and the
session read the same.

**The point is that finished work leaves nothing behind**: branch pushed, PR open, machine back to
where it started. So the worktree is removed once its PR is open, together with its local branch,
since the PR tracks the remote one. Never before the PR exists, and never on a dirty tree without
saying what is uncommitted.

One trap, because it has cost two sessions already: inside a worktree, a nested companion repo
(`agent-tooling` and friends) is a **symlink** to the shared checkout, and that is correct. The Write
tool refuses to resolve through it; the answer is one Bash write to the absolute path, not cloning
the companion in. A copy lands the file in a tree nobody commits, so it looks written and is
invisible everywhere else. **And editing is the only thing that works through it**: git in a
companion repo is refused outright from a worktree session, `!` included, because a worktree
session's git may only target its own worktree. So a change spanning the main repo and a companion
cannot be closed out in one sitting. `/done` commits and PRs the main repo, Gate 5 removes the
worktree, and the companion PR is opened after that, from a session that is no longer isolated. Plan
the merge order around it rather than discovering it at the gate. Full rule:
`agent-tooling/reference/worktrees.md`.

Git hooks are managed by **lefthook** (`lefthook.yml`, which is the authoritative list). `pre-commit` runs the fast lint set (rustfmt-check, SPDX headers on `protocol/`, `tsc --noEmit`, the seam/coverage guards + the i18n catalog check under `scripts/` (see "Repo guards" below), whitespace, EOF newline, single-`Cargo.lock` check, secret pattern guard); `pre-push` runs the full battery (Damm-32 table drift, `cargo clippy --workspace --all-targets -- -D warnings`, the same clippy for `wasm32-unknown-unknown` over `myne-core` + `protocol`, `cargo test -p myne-web-wasm`, `cargo test --workspace`, `pnpm build`, `pnpm test`); `commit-msg` rejects AI co-author/attribution trailers. **`pre-push` also carries `protected-branch`**, which refuses a push whose REMOTE ref is `refs/heads/develop`, `refs/heads/main` or `refs/heads/release`, in this repo and in every companion (myne-md/myne#592). `release` is on that list because it is the branch that DEPLOYS: `myne-website`'s `.woodpecker.yml` maps `release` to production and `develop` to staging, so a `develop`-only guard protected the branch with no blast radius and skipped the one that publishes. It is hygiene rather than enforcement and says so in its own comment: the org's plan offers no server-side branch protection for private repos, so there is nothing on GitHub to lean on, and `--no-verify`, `LEFTHOOK=0` and `LEFTHOOK_EXCLUDE=protected-branch` each bypass it. Two hatches are sanctioned instead. `MYNE_ALLOW_PROTECTED_PUSH=1 git push ...` is the one-off; `git config myne.allowProtectedPush true` is for a repo whose normal workflow IS pushing to its default branch (`internal-service` documents exactly that in its own CLAUDE.md, and `homebrew-tap` and `myne-branding` work the same way). Both hatches parse a VALUE (`1`, `true`, `yes`, `on`, case-insensitively) and refuse anything else, so `MYNE_ALLOW_PROTECTED_PUSH=0` keeps the guard ON rather than switching it off, which is what testing the variable for non-emptiness used to do. The flag is read with `git config --local`, deliberately: a plain `--get` reads the merged cascade, so one `--global` setting would switch the guard off in all eleven clones at once, which is the failure the flag exists to prevent. Each `lefthook.yml` also carries a `min_version`, because `lefthook run` and the real git hook path IGNORE an unknown key without a word (only `lefthook validate` rejects one, and hooks never call it), so an older binary would drop `use_stdin` and leave a guard printing a green tick while checking nothing. CI is self-hosted Woodpecker via the Forgejo mirror (`.woodpecker/`, Linux runner; `design-notes.md` 2026-05-01) — the hooks are the local pre-push net, CI is the remote gate. **The config is a DIRECTORY of two workflow files and the split is load-bearing**: `.woodpecker/main.yml` is the per-push pipeline, and `.woodpecker/e2e.yml` holds **both** end-to-end suites (the desktop tauri-driver suite and the browser web lane) and runs on a **manual trigger only**, carrying the variable `RUN_E2E=true`, before a release (myne-md/myne#579, `design-notes.md` 2026-08-23 entry 0529; procedure `docs/dev/e2e.md` "When CI runs these suites"). Two consequences worth stating rather than inferring. A green push pipeline is **not** evidence about a single E2E scenario, and the release runbook (`operations/runbooks/release-checklist.md` phase 0) is what owes that claim. And the manual event now carries one intent at a time: `main.yml`'s manual entry is gated `RUN_E2E != "true"` so an E2E trigger does not also run the whole pipeline and, on `develop`, deploy `app.example.com` through the `&web-deploy` anchor below. **Three lanes, one pipeline** (MYND-574; the third landed 2026-08-13): the desktop lane is one serial chain (`pnpm-build` → `vitest` → `tauri-compile` → `cargo-test-tauri`) because each of those runs `pnpm install` into the shared workspace `node_modules` (`e2e` was its tail until myne-md/myne#579 moved it out, so `web-build` and `sync-sim` now hang off `cargo-test-tauri` instead); the **web lane** hangs off the end of it (`web-build` — the web bundle plus the artefact greps, the seam contract against the web implementation, the bundle budget and the screen/surface/testid rosters) so it adds nothing to the desktop lane's wall-clock, alongside the early Rust wasm gates (`wasm-protocol`); the **mobile lane** (`mobile-build` → `npm-licenses` → `mobile-vitest` → `mobile-flow-logic`, plus `mobile-compile` for its Rust) hangs off `web-build` for the same reason and by the same rule. That mobile chain is **serial, and every edge into it and inside it is `optional: true`** (the three internal ones since myne-md/myne#515; the `web-build` edge already was): serial because all four run `pnpm install` into the shared workspace `node_modules` and raced as siblings, optional because a non-optional edge made one red step remove every step behind it, which is how a license-gate failure deleted the mobile Vitest suite and the whole Playwright flow-logic tier from the run. An optional edge still orders; it only stops requiring that the parent passed. The mobile lane replaced a *separate pipeline in a separate repo* that began by cloning this one and `git reset --hard`-ing it to `develop` tip — so a mobile commit was not reproducible, and a change here that broke mobile was invisible until somebody pushed there. Three of that pipeline's six steps simply vanished, absorbed by workspace-wide steps that already existed (`cargo fmt --all`, `cargo deny check`, the shared `pnpm install`). Every step that can go red is listed in `notify-failure` (the only thing that pushes a failure to the maintainer), and every compile/test step carries the `code-paths` filter, so a docs-only commit skips them. **Four steps deliberately carry no filter and must keep it that way**: `hooks-parity` (its EOF/whitespace/SPDX checks apply to docs too), `bundle-record` (the append-only hash record *is* a doc, so a docs-only commit is exactly when it must run), `twin-inventory` (its `--check` half holds a generated `docs/**` file to its roster, and a hand edit to that file is a docs-only commit) and `manual-test-roster` (same reason twice over: its `--check` half gates a generated `docs/**` file, and the roster records what a human must verify before a tag, which is a procedure a docs-only commit moves) — all four say so in their own `.woodpecker/main.yml` comments; adding `when: *code-paths` to any of them is a regression, not a cleanup. **The web deploy chain is no longer in this pipeline at all** (myne-md/myne#584): `web-docker-build`, `web-docker-deploy` and `web-smoke` are gone, because CI verifies and does not publish. What survives is `web-container-check`, which builds the image to ASK it questions rather than to ship it, runs `check-web-container-headers.sh` against the running container, and is path-filtered to `web/**` since that build is expensive and duplicative. Publishing `app.example.com`, the `--has` bundle-hash precondition and the post-deploy smoke are one by-hand procedure in `operations/runbooks/web-client-deploy.md`. The **whole mobile lane**, plus `web-build` and `sync-sim`, carries `status: [success, failure]` and aliases `*code-path-globs` rather than `*code-paths`: a `when` entry's implicit `status: success` is a *pipeline-wide* condition, not a `depends_on`-scoped one, so without it any red step anywhere skips gates that have no dependency path to it — which is how `mobile-vitest` and `npm-licenses` went unrun for the whole time the mobile client had been in-repo (myne-md/myne#458). Every step in `.woodpecker/e2e.yml` but its notifier carries the same key for the same reason, and one further one: that workflow exists to produce a pre-release inventory, and a skipped gate in an inventory is worse than a red one. It is written there ONCE, as a YAML anchor, because a hand-copy is a second place to drift and losing the key is silent. Bypass with `git commit --no-verify` only when you understand why.

**A new user-facing flow ships WITH its E2E coverage**: the same change carries the `data-testid` pass (`src/CLAUDE.md` "Test observability") and a scenario on the right harness (`e2e/CLAUDE.md`, procedure `docs/dev/e2e.md`). A PR that adds a flow without its E2E scenario gets rejected in review. **Which harness** — there are two lanes and they do not mirror each other: a flow in the **shared** `src/` tree owes ONE scenario to the tauri-driver suite in `e2e/` and nothing to the web lane, because it is literally the same code; a **web-specific** behaviour (capability gating, OPFS persistence, the single-tab lock, sync-required entry, crash recovery of the double-buffered blobs) owes a scenario to `e2e-web/`. Do **not** dual-drive the desktop suite against a browser: the premise that lets one suite cover both clients is "same tree, only the seam differs", and that premise is verified by the **seam contract tests** (`tests/platform/seam-contract.ts`, run against every implementation in both CI lanes), not by re-running every tauri-driver scenario file in `e2e/`. `design-notes.md` 2026-07-26 "Web E2E policy".

**And it ships with its MANUAL-test verdict**, which is the other half of the same obligation and the
one no compiler and no CI lane can supply. Every desktop E2E scenario runs in a Linux container
against WebKitGTK, so a flow that works there is verified on exactly one of the eight client surfaces the roster
counts (`CLIENTS` in `scripts/check-manual-test-roster.mjs`). One other lane exists, `e2e-web/`,
which drives the web client in Chromium. Between them they reach two of those eight, and no
count is given here on purpose, because this sentence has already been wrong three ways: what
matters is which surface is in which state, and a number invites a reader to trust the arithmetic
instead of the list. `desktop-linux` is covered. `web` is covered on Chromium alone, so its other
engine is not. `cli` and `clipper` have scenarios that the roster leans on by name
(`e2e/cli-thin-client.e2e.ts`, `e2e/clipper-install.e2e.ts`), but both execute only inside that same
Linux container, so what they lack is a second platform rather than a scenario. `desktop-macos`,
`desktop-windows`, `ios` and `android` have no automated UI coverage at all. So a
new file in any of the guard's six denominators (`src/screens/`, `src/components/settings/`, `web/src/screens/`, `web/src/components/settings/`, `mobile/src/app/flows/`, `e2e/*.e2e.ts`) owes a verdict in the
same change, and `scripts/check-manual-test-roster.mjs` fails the commit until it has one. Two
things discharge it and the guard's own message offers both: a roster entry claiming the file, or a
`NOT_A_SURFACE` record carrying the reason it is not a surface. A new `e2e/*.e2e.ts` file is the
third case and it is smaller: it owes a mention in an existing entry's `automatedBy`, not an entry
of its own.

Writing that verdict asks one question, and the answer decides where the work goes: **can a machine
honestly judge this?** If yes, it is not a manual item, it is an `e2e/` scenario you owe, and the
roster records the automation rather than the observation. If no, the entry carries what a human
must SEE and the mechanism that blocks a driver: the runner OS, the WebView engine, a physical
device, an OS event source, a perceptual judgement with a stated pass condition. The guard checks
that with a phrase denylist rather than a vocabulary, so it catches the sentences an author writes
instead of naming a mechanism and not every vague one. The reason it is one-directional is measured
and recorded in the guard's header. myne-md/myne#548.

`pnpm` is the canonical package manager (Tauri's `beforeDevCommand`/`beforeBuildCommand` invoke it). Pinned versions: Node `.nvmrc`, Rust `rust-toolchain.toml`. **Do not bypass the pinning** — CI and reproducible-build rely on it.

JS tests run on **Vitest** (`pnpm test` → `vitest run`; config `vitest.config.ts` — standalone, it does not extend `vite.config.ts` — specs under `tests/**/*.test.{ts,tsx}`). The other lanes have configs of their own: `vitest.e2e.config.ts` (desktop E2E), `vitest.web-e2e.config.ts` (web E2E), `vitest.capture.config.ts` (user-guide screenshots). `tsc` via `pnpm build` is the typecheck; for Rust use `cargo test`. (Note: `tests/` is outside `tsc`'s `include: ["src"]`, so Vitest is the only check that exercises test files.)

## Repo guards (what blocks a commit, and what blocks CI)

Most of `scripts/` is not tooling — it is the machine-checked half of the rules this file states in prose. Each guard exists because the failure it catches is invisible to every compiler: a TS string literal that no `match` arm answers, a `std::fs` call that compiles for wasm32 and dies at runtime, a value in the served bundle that should not be there. They are zero-dependency and hand-runnable (`node scripts/<name>.mjs`, `bash scripts/<name>.sh`); every one carries a header comment explaining the failure it prevents, which is the thing to read when it fires.

**Verifying a guard means breaking it, not running it.** Every guard above claims to catch something, and a guard that has never failed is a guard nobody has tested. Three consecutive reviews of one feature found a check that passed while the thing it checked was wrong — a matrix compared in one direction while the success line claimed two, a roster compared against a second copy of itself, a filter named in a test title and never exercised. In each case the check had just been *fixed*, and the fix was "verified" by the check passing afterwards, which proves nothing. **Inject the exact defect the guard now claims to catch, watch it name that defect, then restore.** It costs a minute and it is the only evidence that means anything.

**Editing a guard is one of those changes, and the exemption logic is where it bites.** A guard fix
verified by "the tree is still green afterwards" is the same non-evidence as any other, because a
guard that has stopped checking is green by definition. myne-md/myne#411 corrected
`check-core-io-seam.mjs`'s `#[cfg(test)]` tracker, ran the tree, saw green, and shipped a version
that reported nothing for a production `std::fs::read` the pre-fix guard caught: closing one blind
spot opened another, one line away. Both directions have to be injected, and the second one is the
one nobody thinks to try: prove the guard still catches what it caught BEFORE, not only what it
missed.

**And when a test can assert either a return value or a state, assert the state.** The same feature's
first plaintext-fallback test checked `expect_err` before walking the disk, which is the weaker fact:
a fallback could report either result while the name sat on the medium. A failure message may not
claim more than its inputs can prove either, which is why a cross-vault assertion run under an
all-zero key cannot say "the AAD refused" when a wrong key would have failed identically.

**Two measurements that agree can both be wrong, and agreement is not evidence when they can share
a defect.** myne-md/myne#472's review reported that a roster claim ("two shared token names carry
different values") was invented, having measured 247 of 247 shared declarations byte-identical. A
second, independent measurement agreed. Both were wrong: `--_paper-2-amoled` really is `#000000`
against `#0c0c0b`. Each probe matched token names with a character class that excluded the
underscore, so every `--_private` token was invisible to both, and acting on the agreement would
have replaced a true statement in a published record with a false one. When two probes concur,
check whether they could have concurred for the same wrong reason before treating the concurrence
as confirmation.

**A generated document that a `--check` compares may carry no value that moves on an edit its
subject does not cover.** The same feature's projection printed a per-row line count, so `--check`
failed on any one-line edit to any of the 192 files it covered, in `pre-commit` and in CI, under a
message telling the author the document had been hand-edited. It had not. A tree-derived value is
fine when it moves only when the record itself should be regenerated: that projection still prints
how many pairs differ, and a pair starting or stopping differing is exactly the event that should
force a re-emit. The line count was not that. Ask what edit moves the number, not where the number
came from.

Three shared libraries sit under `scripts/lib/` and exist because the drift they prevent is invisible: `shared-roots.mjs` is the ONE roster of shared trees (each guard kept a private copy, and `check-i18n.mjs`'s never learned about `editor/`, `dialect/` or `copy/` — 226 live `i18n.t()` keys outside its scope); `scanned-assets.mjs` inverts the artefact-scan filter so a guard **fails on an extension nobody classified** instead of skipping it (the four web greps read `.js`/`.css`/`.html` and never opened the 1.2 MB `.mjs` chunk or the 3.9 MB `.wasm` the bundle actually ships); and `surface-files.mjs` is the ONE recursive walk that turns a directory into a roster's denominator, which is the same failure one question over. `check-web-screens.mjs` records in its own header why its walk recurses (a prefix rule swallowed `ProvisioningStep.tsx`), `check-manual-test-roster.mjs` was written later with a private shallow copy, and the fix did not travel: 88 files exist under its two `src/` denominators and the shallow walk returned 61, so 27 of them, `src/screens/vault-creation/` and `src/screens/vault-recover/` and `src/components/settings/search/` entire, sat outside a denominator whose whole premise is that every file in it is accounted for. A guard that needs a directory's files imports this; one that deliberately wants a shallow listing says so in its own header.

## The spec is the source of truth

Read `docs/` before changing anything that touches cryptography, on-disk format, key handling, or sync. Order:

1. `docs/vision.md` — phased plan, anti-features (commitments, not "maybe later")
2. `docs/threat-model.md`. The adversary, asset and trust-boundary tables. Cite a row by its id from that document; the ranges are not restated here, because the line that used to do so said A1 to A15 and TB1 to TB11 while the tables had already grown past both, and the boundaries it stopped short of are the two that carry decrypted note plaintext off the device. **Normative**: marketing copy and code may not exceed its guarantees.
3. `docs/spec/protocol.md` — v0.1 cryptographic protocol
4. `docs/spec/account-number.md` — 20-character Crockford-base32 + Damm-32 identifier
5. `docs/glossary.md` — canonical terminology, one A–Z entry per term. Every new term in any doc gets a glossary entry in the same change.
6. `design-notes/` — the append-only decision log, one file per decision under a topic directory, numbered `NNNN` in one global chronological sequence. `design-notes.md` is the **generated index** over it and is never hand-edited. A new decision gets the next number; reversals get a new entry whose *title* says "supersedes <date> — <title>". Never renumber, reorder, delete, or rewrite a past entry.

See `docs/CLAUDE.md` for spec-authoring discipline in depth.

## Cryptographically load-bearing identifiers

**The Phase 3 web client adds nothing to this table and removes nothing from it** — it runs the same `protocol/` crate compiled to wasm, reads and writes byte-identical blobs, and introduces no magic, AAD prefix, HKDF context or subkey role of its own. Its only on-disk divergence is the *container layout* around those blobs in OPFS (`decisions.md` 2026-07-26), which is not an identifier.

Identifiers and constants whose change is a major-version event. Most are bound into AEAD tags or magic-byte checks; some (e.g. the account-number display prefix, the Damm-32 table) are load-bearing through account identity or presentation rather than an AEAD/magic boundary — the mechanism is noted per row.

**Read the table as a pointer, not as a registry.** The two per-role registries — subkey context strings (`protocol.md` §3.4, mirrored in code by `SubkeyRole::ALL`) and AAD role strings (§5.2) — are complete and normative *there*, and every registered role in them is a major-version-event constant. They get **one** row below instead of one row per role, so shipping a new role never owes this table an edit. That is deliberate: the per-role rows this table used to carry had fallen behind the registries while still reading as exhaustive — `itemsKey-wrap`, the KEK at the root of every note's key lineage, had no row at all — which is the failure mode a partial copy always has. ## Crypto primitives baseline (summary)

**KDF** Argon2id `m=256 MiB, t=3, p=2` v1.3 · **AEAD** XChaCha20-Poly1305 + CTX commitment SHA-256 outer (32-byte tag on disk) · **Subkey derivation** HKDF-SHA-256 via single canonical `DeriveSubkey` helper · **Recovery** BIP-39 24 words → fed **directly** to Argon2id (no PBKDF2 step) · **Library** RustCrypto stack, no custom primitives on any client.

Full primitive details, audit anchors, and subkey derivation discipline rule (which forbids direct `hkdf.expand` calls outside the canonical helper): see `protocol/CLAUDE.md`. Cross-implementation byte-level compatibility validated by `myne-test-vectors/` companion.

## Hard architectural commitments (don't quietly walk these back)

- **No email at signup, no email recovery — ever.** Adding email recovery silently invalidates the zero-knowledge claim.
- **No plaintext mode, no encryption opt-in.** Privacy is the default for every user.
- **No persistent server-side IP logging.** Abuse via per-account counters, not per-IP.
- **User-meaningful timestamps live inside the encrypted blob.** Server uses opaque per-note version counter for conflict detection; resolution is client-side after decryption.
- **Self-hosted and hosted servers share the exact same trust boundary (TB5).** Same protocol, same security model.
- **Reproducible builds where they ship (web bundle and server image, not desktop), minisign-signed release hashes, hash-pinned lockfiles, minimal direct-dependency surface.** Credible substitute for the missing third-party audit (`threat-model.md` §6, which is the authority on which half of this is shipped; this line read "reproducible signed builds" until 2026-08-25 and desktop has neither). **Adding a dependency is a security decision** — including the choice of Vite + React over Next.js.

## Gotchas

- **`@tauri-apps/*` may only be imported from a guarded tree's own `platform/` directory.** The platform seam is what lets one `src/` tree compile for both the desktop and the web client; a direct import anywhere else breaks the web build rather than degrading it. Enforced by `scripts/check-platform-seam.mjs` in `pre-commit` **and** in CI (so `--no-verify` does not slip one through). Eight roots are guarded: `src` (seam `src/platform/`) and `mobile/src` (seam `mobile/src/platform/`) are Tauri hosts and get a seam directory; `editor/`, `dialect/`, `copy/`, `ornaments/`, `preview/` and `web/src` get the strictest form, `seam: null`, which bans `@tauri-apps/*` outright because **not every** consumer is a Tauri host: the web client compiles the shared packages too, and `ornaments/` plus `preview/` reach further still, into the website and the myne-themes gallery renderer. A module-scope `@tauri-apps` import lands in those bundles whether or not the call ever fires, so it breaks their build rather than degrading it. `editor/`, `dialect/` and `copy/` were added by MYND-574 task 76; `mobile/src` and `web/src` joined in myne#492, and `mobile/src` had accumulated 41 direct imports while the guard reported ok, which is why the guard now also derives a coverage claim over `scripts/lib/shared-roots.mjs` rather than trusting a prose comment (`design-notes/clients/0497-*`). If an export you need is missing, add it to the seam module rather than reaching around it.
- **A new `web/wasm/src/dispatch.rs` arm needs its `capability::DISPATCHED` entry in the same change, and only `cargo test -p myne-web-wasm` tells you.** Without it, `classify` reports a command the router *does* answer as unported — the exact wrong answer the capability system exists to prevent. `cargo clippy --target wasm32-unknown-unknown` is green either way, and so is every `scripts/check-web-*.mjs` guard. The crate is a workspace member (so `cargo test --workspace` in `pre-push` covers it), but CI's Rust steps name `-p protocol` and `-p myne-desktop -p myne-core`; the wasm lane now runs the crate's tests too (MYND-574 task 77).
- **A `[target.'cfg(…)'.dependencies.…]` table must go at the END of a `Cargo.toml`, never beside the crate it overrides.** Inserted next to `tracing = "0.1"` inside `[dependencies]`, it TERMINATES that section, and every crate declared after that line silently becomes part of the target table — `sha2`, `unicode_normalization` and friends disappear from both builds with `unresolved import` errors that name the wrong file. TOML sections have no closing brace, so nothing about the edit looks wrong.
- **`web/wasm/pkg/` is a derived artefact and goes stale, and in a fresh worktree it is not there at all.** Adding a `#[wasm_bindgen]` export needs `./scripts/build-wasm.sh` before `pnpm web:build`, or the bundler fails with `MISSING_EXPORT` on the new name. In a worktree the failure is different and reads like a broken branch: the directory is gitignored (`.gitignore:89`), so a fresh checkout has none and `pnpm web:build` dies with `UNRESOLVED_IMPORT` on `../../wasm/pkg/myne_web_wasm.js` before it compiles a line. On a branch that touches no Rust the shared checkout's copy is the same artefact this branch would produce, so copying it in is legitimate and costs nothing; on a branch that does touch Rust, run the build script. Same family as the sidecar staging a worktree needs before `cargo` will run (`agent-tooling/reference/worktrees.md`).
- **A comment stripper that spans Rust and TypeScript has a `'` problem in BOTH directions, and fixing one direction is how you create the other.** In Rust `'` opens a char literal (`'x'`) and also a lifetime (`'a`), which never closes; reading a lifetime as a string opener desyncs the walk and swallows everything to the next tick, so `check-twin-inventory.mjs` preserved 163 lines of doc comment in one file and reported comment-only differences as drift. The fix, requiring the closing tick within a short window, was then applied to every file including `.ts`, where `'` is an ordinary string quote with no length bound: a single-quoted string longer than the window stops being a string, the `//` inside every single-quoted URL strips the rest of the line, and two files differing only inside such a string compare EQUAL. The window has to be language-scoped, and both directions have to be injected, because the second one is the one nobody thinks to try.
- **A guard parameter with a default value is an opt-in guard, and the default is the arm that never fires.** `settleStep(result, epoch = runEpoch)` reads as though every caller is checked. It is not: a default is evaluated at the call, so an omitted argument compares the CURRENT epoch against itself and matches unconditionally, which makes the one call site that forgot to thread the epoch precisely the site running unguarded. `tsc` is happy, because the signature is satisfied, and nothing else looks at it. myne-md/myne#533's agent store shipped that shape: the epoch exists to drop a step that lands after a vault lock, a vault switch or a "New chat", each of which repopulates the proposal with anchors and replacements copied verbatim out of note bodies, and the default excused every future call site from the check in advance. Make the parameter REQUIRED and let the compiler name every site (five, here), then verify the way a guard is verified: delete the comparison and watch a test fail by name (`tests/notes/agentUndoLifetime.test.ts`). The same shape hides in a Rust argument defaulted to the ambient value and in a script flag whose absence means "check nothing".
- **A negative lookahead after `\s*` is not a guard, because `\s*` backtracks into it.** `/["'](data-[a-z0-9-]+)["']\s*:\s*(?!["'`])/` looks like "the value must not be a string literal" and matches every string literal: the engine tries the lookahead after the space, fails, gives the space back, re-tries at the space, and a space is not a quote. Written into `check-web-testids.mjs` it made the object-form leak detector report clean on exactly the input it was added for. Capture the first non-space character and test it instead, since a capture cannot backtrack past itself. The same shape is a hazard in any guard that reads a value's first token.
- **`Cargo.lock` is single-shared at workspace root** (TB9 audit anchor). Do not split into per-crate locks.
- **Vite `strictPort: 1420`** — `pnpm dev` fails fast if port taken; this is intentional (Tauri expects exact port).
- **Vite `clearScreen: false`** — keep it; otherwise Rust errors get hidden during `pnpm tauri dev`.
- **CLAUDE.md HTML comments are stripped** before injection. Block comments (`<!-- ... -->`) outside code blocks vanish silently. Use code blocks if you need a literal comment.
- **`String.replace`'s replacement STRING expands `$1`, `$&`, `` $` `` and `$$` — which defeats a quote sanitizer placed before it.** A theme value of `$1 onload=…` filtered clean of `["'<>]` still expanded to the captured group, whose own quote closed the attribute it was being interpolated into and landed a live event handler. `$` cannot be filtered (a legitimate CSS value may contain one), so the fix is a replacer **function**, to which no `$` sequence means anything. Any `replace(re, `…${untrusted}…`)` has this shape; `myne-themes/tools/render-preview.mjs` carries the worked example.
- **Tauri lib must keep `_lib` suffix** (`myne_desktop_lib`) to avoid Windows lib-vs-bin collision (rust-lang/cargo#8519). See `src-tauri/CLAUDE.md`.
